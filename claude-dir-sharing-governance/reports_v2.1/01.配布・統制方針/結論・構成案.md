## §0 エグゼクティブサマリ

### 結論

**`.claude/` をひとつの Git リポジトリにし、そのリポジトリを作業リポジトリの `.claude/` ディレクトリとして clone する。作業種別はブランチで切り替える。**（＝**案C-1**。詳細は [§5](#recommend)）

```txt
<共有 .claude リポジトリ>              ← メンテナー 1〜2 名が管理
├── main                              ← チーム全体で常に要る資産
├── java/base                        ← java 系リポジトリ群で共通
├── java/design ・ java/coding ・ java/ut
└── python/base ・ python/…

<作業リポジトリ>
├── .claude/        ← 上記リポジトリのクローン。作業リポ側では .gitignore 対象
├── CLAUDE.md       ← このリポジトリ固有の指示（.claude/ の外）
└── start_claude_code.ps1   ← ランチャー（fetch → switch → reset --hard → 起動）
```

この形なら **`--add-dir` も `--settings` も環境変数も要らない**。資産は作業リポジトリの `.claude/` にそのまま**実体として存在する**ので、Claude Code から見れば「ごく普通の project スコープ」であり、条件付きロードにも起動フラグにも依存しない。

本書では「作業リポ」は作業リポジトリ、「共有リポ」は共有 `.claude` リポジトリの略として使う。

### 3 つの問いへの回答

| 問い | 回答 |
|---|---|
| **問1**: `<Prjルート>\.claude` を Marketplace の仕組みで配布できるか | **No（部分的にのみ可）**。marketplace で配れるのは機能資産と plugin 専用コンポーネントに限られ、`CLAUDE.md` / `rules` / `permissions` は plugin では運べない（[§2](#where)） |
| **問2**: 最小・ポータブルな `.claude/` を「Marketplace のように」共有する単一ベストプラクティスは存在するか。無ければ設計せよ | **単一の既製ベストプラクティスは存在しない**。単一チャネルで全資産を運ぶ手段がないため。**設計した答えが案C-1**（[§5](#recommend)）。**この「存在しない」は、公式ドキュメントが記載する配布機構を全経路棚卸しした範囲での結論**である（検討して外した経路は [付録 3](./結論・構成案【別紙】付録.md#appendix-c)。**公式以外のコミュニティ事例・他社事例は調査していない**＝[§8-1](#sec-8-1)） |
| **問3**: 作業種別ごとに必要な資産だけをロードさせる出し分けは、条件付きロードで実現できるか | **保証が要る出し分けには使えない**。理由は 3 つある（[§3-3](#sec-3-3)）。①発火しない読み方が残る（Grep ツール、パイプ付きや複数ファイルの Bash コマンド【実測】）②発火するかどうかが CLI の版・モデル・資産の種類で変わる ③条件の単位はファイルの場所と種類であって、作業種別ではない。「ロードされなくても作業が止まらない補足」には使えるが、**確実に届ける必要がある資産は「実体の置き場所」＝ブランチで分ける** |

### なぜこの形を選ぶのか

1. **条件付きロード（`paths:` 付き rule・サブディレクトリの `CLAUDE.md`／`skills`）は「必要なときにロードされる」保証がない** —— 読み方によっては発火せず、発火する条件は CLI の版・モデル・資産の種類で変わる【実測】。しかも条件の単位はファイルの場所と種類で、作業種別ではない（[§3-3](#sec-3-3)）
2. だから**出し分けは「条件」ではなく「実体の置き場所」で行う**。**置き場所の切替を既存の道具で賄える**のが **git のブランチ**である（新しい機構をチームに持ち込まずに済む）
3. **実体を「作業リポジトリの `.claude/`」に置くのは、`--add-dir` では `permissions` が届かないから** —— 追加ディレクトリの `settings.json` から読まれるのは `enabledPlugins` / `extraKnownMarketplaces` の 2 キーだけで、`deny` を効かせるには `--settings` による二重化が要る（[§6-2](#sec-6-2)）
4. **`.claude/` を作業リポジトリから gitignore して入れ子 clone しても、資産は普通どおりロードされる**【実測】—— この一点が案C-1 の土台

## §1 前提情報：Claude Code が読む資産と、その置き場所

配布設計の前に、どんな資産があり、どこに置けるのかを押さえる。**ここでは種類と配置場所の把握だけを目的**とし、どう配るかは [§2](#where) 以降で扱う。

> 急ぐ読者は [§3](#load) か [§5](#recommend) へ。本節は資産の所在を確認したい時の参照用。

<a id="prereq-assets"></a>

### §1-1 資産の一覧

Claude Code が読む資産の全種類である。「置ける場所」の丸数字は [§1-2](#prereq-places) の番号を指す。

| 資産 | 役割 | 置ける場所 |
|---|---|---|
| `CLAUDE.md` | セッションの開始時に context へロードされる指示文 | ①②③④ |
| `CLAUDE.local.md` | `CLAUDE.md` と一緒に読まれる個人用の指示文 | ③ |
| `AGENTS.md` | ほかのコーディングエージェントと共用する指示文 | ②③ |
| rules | トピックごとに分けた指示文。`paths:` を付けるとファイルの種類で絞れる | ①② |
| settings | permissions・hooks・環境変数・モデルの既定値などの設定 | ①②④⑤ |
| skills | `/名前` で呼ぶか、Claude が作業に合わせて起動する手順。補助ファイルを同梱できる | ①②④⑥⑧ |
| commands | 1 ファイルのプロンプト。skills の旧い形式 | ①②⑥ |
| subagents | 独自のシステムプロンプトとツールを持ち、別の context で動くエージェントの定義 | ①②④⑥ |
| subagent の永続メモリ | subagent がセッションをまたいで残すメモ | ①② |
| output styles | システムプロンプトに足す、応答の作法の定義 | ①②④⑥ |
| workflows | 多数の subagent を起こして束ねるスクリプト | ①②⑥ |
| hooks | セッションの決まった時点で走るスクリプトの設定 | settings の中（①②④⑤）、⑥ |
| MCP サーバーの定義 | 外部のツールへつなぐサーバーの設定 | ③④⑥⑦⑧ |
| plugin 専用の資産 | manifest・LSP サーバー・monitors・実行ファイル・channels | ⑥ |
| themes | 端末の配色の定義 | ①⑥ |
| keybindings | キーの割り当て | ① |
| auto memory | Claude がセッションをまたいで残すメモ | ① |
| `.worktreeinclude` | 新しい worktree へ写す gitignore 済みファイルの指定 | ③ |

- `AGENTS.md` が読まれるのは、作業ディレクトリとその上位に `CLAUDE.md`・`.claude/CLAUDE.md`・`CLAUDE.local.md` のどれも無いときだけである（v2.1.277 以降）[\[42\]](./結論・構成案【別紙】出典一覧.md#ref-42)。案C-1 は `.claude/CLAUDE.md` を配るので、既定では読まれない
- hooks は独立したファイルではなく、settings の `hooks` キー、plugin の `hooks/hooks.json`、skill と subagent の frontmatter に書く
- skills は、起動した場所より下のサブディレクトリの `.claude/skills/` にも置ける（[§3-2](#conditional)）
- ④の rules は、managed の `CLAUDE.md` に書くしかない（rules を置く仕組みが無い）。④の commands は skill で代える

### §1-2 置き場所の一覧

資産を置ける場所の全部である。「配布での呼び名」は [§2-1](#sec-2-1) の P1〜P6 との対応を表す。

| # | 置き場所 | 誰に効くか | 性質と制約 | 配布での呼び名 |
|---|---|---|---|---|
| ① | `~/.claude/` | 本人。その端末の全プロジェクト | **チームが配る経路は無い**[\[1\]](./結論・構成案【別紙】出典一覧.md#ref-1)。Windows は `%USERPROFILE%\.claude`。`CLAUDE_CONFIG_DIR` で場所を変えられる | P5 |
| ② | プロジェクトの `.claude/` | そのリポジトリで起動したセッション | commit すればチームで共有できる。**案C-1 が使う場所**で、共有リポのクローンをここに置く | P1 |
| ③ | プロジェクトの中で `.claude/` の外 | 同上 | ルートとサブディレクトリの指示文、ルートの `.mcp.json` など。リポジトリ固有の内容を置く | P2 |
| ④ | managed settings のディレクトリ | その端末の全ユーザー | 組織が配る。**個人の設定で上書きも除外もできない**。置くには管理者権限が要る | P4 |
| ⑤ | OS のポリシー | 同上 | macOS の plist（`com.anthropic.claudecode`）、Windows のレジストリ（`HKLM\SOFTWARE\Policies\ClaudeCode`・`HKCU\...`）。settings だけを運ぶ | P4 |
| ⑥ | plugin | plugin を有効にしたセッション | 実体は別のリポジトリにあり、install すると `~/.claude/plugins/` にキャッシュされる[\[3\]](./結論・構成案【別紙】出典一覧.md#ref-3)。**`.claude/` の下には置けない** | P3 |
| ⑦ | `~/.claude.json` | 本人 | home の直下の 1 ファイル（`~/.claude/` と同じ階層）。アカウントの情報、フォルダごとの trust の記録、個人用の MCP サーバー、UI の設定を持つ | P5 |
| ⑧ | claude.ai のアカウント | そのアカウントでサインインしたセッション | 有効にした skill が同期される。Organization settings からの plugin の配布もここに入る | P6 |

> **`.claude/` が無くても Claude Code は起動する。** 公式に "The rest of the directory is optional" とある [\[2\]](./結論・構成案【別紙】出典一覧.md#ref-2)。marketplace で `.claude/` 全体を配れないのは「起動に必須だから」ではなく、**marketplace の配布単位が plugin だから**である。

以下の §1-3〜§1-7 は、置き場所ごとに、置ける資産を tree の図で示す。図の `// (n)` は、図の下の表の番号である。

### §1-3 `~/.claude/` に置ける資産

```txt
~/.claude/
├── CLAUDE.md                     // (1)
├── settings.json                 // (2)
├── keybindings.json              // (3)
├── rules/                        // (4)
├── skills/<skill-name>/          // (5)
├── skills/synced/                // (6)
├── commands/                     // (7)
├── agents/                       // (8)
├── agent-memory/<agent-name>/    // (9)
├── output-styles/                // (10)
├── workflows/                    // (11)
├── themes/                       // (12)
├── projects/<project>/memory/    // (13)
└── plugins/                      // (14)
```

| # | 内容 |
|---|---|
| (1) | 全プロジェクト共通の個人の指示文 |
| (2) | 個人の既定の settings（permissions・hooks・env・モデル） |
| (3) | 個人のキーの割り当て。ここにしか置けない |
| (4) | 全プロジェクト共通のトピック別の指示文（`*.md`）。**project の rules より先に読まれる**。どちらかが優先されるわけではなく、食い違うとどちらに従うかは決まらない[\[14\]](./結論・構成案【別紙】出典一覧.md#ref-14) |
| (5) | 個人の skill。`SKILL.md` と補助ファイルを 1 フォルダに置く [\[5\]](./結論・構成案【別紙】出典一覧.md#ref-5) |
| (6) | claude.ai から同期された skill の保存先。Claude Code が書き込む場所で、自分では置かない |
| (7) | 個人のコマンド（1 ファイルの `*.md`） |
| (8) | 個人の subagent の定義 |
| (9) | `memory: user` を指定した subagent の永続メモリ |
| (10) | 個人の output style |
| (11) | 個人の workflow（`*.js`） |
| (12) | 個人のテーマ（`*.json`） |
| (13) | auto memory。プロジェクトごとのフォルダに分かれる。ここにしか置けない |
| (14) | install した plugin と、clone した marketplace のキャッシュ [\[3\]](./結論・構成案【別紙】出典一覧.md#ref-3) |

- `synced` と `anthropic-skills` は予約された名前である。`synced` という名前の skill フォルダは、個人・プロジェクト・managed のどこに置いてもエラー無しで読み飛ばされる。plugin の外では、`anthropic-skills` という名前と `anthropic-skills:` で始まる名前の skill フォルダ・コマンドファイルもロードされない [\[5\]](./結論・構成案【別紙】出典一覧.md#ref-5)
- (6) が同期されるセッションの条件は [付録 3](./結論・構成案【別紙】付録.md#appendix-c) に書いた

### §1-4 プロジェクトの `.claude/` に置ける資産

**案C-1 が使う場所はここ。**

```txt
<プロジェクトのルート>/
└── .claude/
    ├── CLAUDE.md                     // (1)
    ├── settings.json                 // (2)
    ├── settings.local.json           // (3)
    ├── rules/                        // (4)
    ├── skills/<skill-name>/          // (5)
    ├── commands/                     // (6)
    ├── agents/                       // (7)
    ├── agent-memory/<agent-name>/    // (8)
    ├── output-styles/                // (9)
    └── workflows/                    // (10)
```

| # | 内容 |
|---|---|
| (1) | プロジェクトの指示文。ルートの `./CLAUDE.md` に置いてもよい（[§1-5](#prereq-c)）[\[11\]](./結論・構成案【別紙】出典一覧.md#ref-11) |
| (2) | permissions・hooks・env・モデルの既定値。スコープと優先順位の全体像は settings ページの一覧にある [\[24\]](./結論・構成案【別紙】出典一覧.md#ref-24) |

| (6) | 1 ファイルのプロンプト。**旧い形式**で今も動くが、**新しく作るなら skills**（`name` と `paths` 以外の frontmatter は skill と共通）[\[5\]](./結論・構成案【別紙】出典一覧.md#ref-5) |
| (7) | subagent の定義 |
| (8) | `memory: project` を指定した subagent の永続メモリ。**commit すればチームで共有できる** |
| (9) | システムプロンプトに足す output style |
| (10) | workflow（`*.js`） |

- (3) の gitignore は自動ではない。Claude Code が*自分で書き込んだ*ときにだけ、global の git excludes へ追記する
- `AGENTS.md` を `.claude/` に置くこともできる（読まれる条件は [§1-1](#prereq-assets)）

### §1-6 managed settings のディレクトリに置ける資産

ディレクトリは、macOS が `/Library/Application Support/ClaudeCode/`、Linux と WSL が `/etc/claude-code/`、Windows が `C:\Program Files\ClaudeCode\` である [\[41\]](./結論・構成案【別紙】出典一覧.md#ref-41)。

```txt
<managed settings のディレクトリ>/

    ├── skills/<skill-name>/      // (5)
    └── output-styles/            // (6)
```

| # | 内容 |
|---|---|
| (1) | 組織が配る、上書きできない設定 |
| (2) | (1) に足す分割ファイル（ドロップイン） |
| (3) | 組織が配る MCP サーバーの定義。置くと、起動時に MCP を渡すフラグが使えなくなる（[§4-3](#sec-4-3)） |
| (4) | 組織共通の指示文。**個人の設定では除外できない**[\[17\]](./結論・構成案【別紙】出典一覧.md#ref-17)。`managed-settings.json` の `claudeMd` キーに本文を直接書く方法もある |
| (5) | 組織が配る skill [\[5\]](./結論・構成案【別紙】出典一覧.md#ref-5) |
| (6) | 組織が配る output style [\[37\]](./結論・構成案【別紙】出典一覧.md#ref-37) |

- OS のポリシー（[§1-2](#prereq-places) の⑤）は settings だけを運び、ファイルの資産は運ばない

<a id="prereq-plugin"></a>

### §1-7 plugin に入れられる資産

plugin のルートからの既定の場所である [\[4\]](./結論・構成案【別紙】出典一覧.md#ref-4)。★ は plugin でしか配れない資産を表す。

```txt
<plugin のルート>/
├── .claude-plugin/plugin.json    // (1) ★
├── skills/<skill-name>/          // (2)
├── commands/                     // (3)
├── agents/                       // (4)
├── output-styles/                // (5)
├── themes/                       // (6)
├── workflows/                    // (7)
├── hooks/hooks.json              // (8)
├── .mcp.json                     // (9)
├── .lsp.json                     // (10) ★
├── monitors/monitors.json        // (11) ★
└── bin/                          // (12) ★
```

| # | 内容 |
|---|---|
| (1) | manifest（plugin のメタデータと設定）。channels は、この中の `channels` フィールドで宣言する（★。plugin が持つ MCP サーバーに結び付けて、会話へ内容を差し込む） |
| (2)〜(7) | [§1-3](#prereq-a)・[§1-4](#prereq-b) と同じ形の資産 |
| (8) | hooks の設定。settings の `hooks` キーでも定義できる |
| (9) | MCP サーバーの定義 |
| (10) | 言語サーバーの設定 |
| (11) | バックグラウンドの監視の定義 |
| (12) | 実行ファイル。plugin が有効な間、Bash ツールの `PATH` に加わる |

- **plugin のルートに置いた `CLAUDE.md` はロードされない**。指示を入れたいなら skill にする [\[39\]](./結論・構成案【別紙】出典一覧.md#ref-39)
- **`bin/` を持つ plugin は、claude.ai と Cowork が install しない**（claude.ai の Organization settings から配る plugin を含む）[\[4\]](./結論・構成案【別紙】出典一覧.md#ref-4)
- plugin のルートの `settings.json` は、`BS` の標準レイアウトの表に無い。旧い版の公式ドキュメントは「`agent` と `subagentStatusLine` の 2 キーだけ対応」としていたが、`subagentStatusLine` は設定ごと削除され、plugin の `agent` は非推奨になった（どちらも v2.1.323）[\[39\]](./結論・構成案【別紙】出典一覧.md#ref-39)。この仕組みが今も働くかは実機で確かめていない。**plugin で settings を配る前提の設計はしない**

<a id="where"></a>

## §2 資産をどこに置くか（配置先と、そこで運べるもの）

**「どのチャネルで配るか」ではなく「どこに実体を置くか」で整理する。** 配布チャネルという抽象を先に立てると、層の外側にある経路（claude.ai の同期・Organization settings）が常に例外になるため、本書は**置き場所を主語にする**。[§1-2](#prereq-places) の 8 つの場所を、配る主体と強制力でまとめると 6 つになる。

<a id="sec-2-1"></a>

### §2-1 置き場所は 6 つ

| # | 置き場所 | 実体の所在 | 誰が更新するか | 強制力 |
|---|---|---|---|:---:|
| **P1** | **作業リポジトリの `.claude/`（＝案C-1 の共有リポジトリのクローン）** | 共有 `.claude` リポジトリ | メンテナー（1〜2 名） | なし |
| **P2** | 作業リポジトリの root `CLAUDE.md` / `.mcp.json` | 作業リポジトリ | そのリポジトリの担当者 | なし |
| **P3** | plugin（marketplace 経由 or `@skills-dir` 型） | plugin リポジトリ | plugin の管理者 | 弱（`enabledPlugins` で誘導） |
| **P4** | managed settings ディレクトリ（層3） | 組織の配布基盤 | 組織の IT 管理者 | **最高（上書き不可）** |
| **P5** | `~/.claude/` | 各自の端末 | 各自 | 各自の自由 |
| **P6** | claude.ai アカウント（同期 skill・同期 plugin・Organization settings） | claude.ai | 本人（自分で有効にした skill）と組織（組織が提供する skill・plugin） | プラン依存 |

> **「層」との対応** —— 本書は、強制力の段階を指す語として 層1・層2・層3 を使う（配布経路の分類としては使わない）。
>
> | 層 | 置き場所 | 備考 |
> |---|---|---|
> | 層1（commit） | **P1 ＋ P2** | **案C-1 は P1 の実体だけを別リポジトリへ外出しする** |
> | 層2（plugin） | **P3** | そのまま対応する |
> | 層3（managed） | **P4** | そのまま対応する |
> | （層の外） | **P5 ・ P6** | 層の 3 つに収まらない経路 |
>
> P6 のうち同期 skill は、claude.ai のアカウントでサインインした端末のセッションでも設定なしで同期される（v2.1.273 以降）。同期される skill には、組織が claude.ai で提供する skill が含まれる [\[5\]](./結論・構成案【別紙】出典一覧.md#ref-5)。同期 plugin（`@synced`）も端末のセッションに届く [\[43\]](./結論・構成案【別紙】出典一覧.md#ref-43)。どちらも、自分の組織で提供できるかを確かめていないので、配布の柱には数えない（[付録 3](./結論・構成案【別紙】付録.md#appendix-c)・[§8-2](#sec-8-2) の V1）。

## §3 どう届くか（ロード機構）—— 本書の中核

**置いただけではロードされない。** どの資産が「起動時に必ずロードされる」のか、どれが「条件付きでしかロードされない」のか、そして**その条件が実際には何を指すのか**を確定させる。

### §3-1 無条件ロード（起動時に必ずロードされる）

<a id="sec-3-1"></a>
<a id="unconditional"></a>

| 資産 | 経路 | 根拠 |
|---|---|---|
| 起動ディレクトリと**その全上位ディレクトリ**の `CLAUDE.md` / `CLAUDE.local.md` | project | ✅ 公式 [\[11\]](./結論・構成案【別紙】出典一覧.md#ref-11)。root→cwd の順に連結され、後ろほど優先 |
| `.claude/CLAUDE.md` | project | ✅ 【実測】 |
| `.claude/rules/*.md`（**`paths:` なし**） | project | ✅ 公式：「`paths` frontmatter の無い rule は起動時にロードされ、`.claude/CLAUDE.md` と同じ優先度を持つ」[\[14\]](./結論・構成案【別紙】出典一覧.md#ref-14)。【実測】でも確認 |
| `.claude/settings.json`（**gitignore されていても**） | project | ✅ 【実測】`env` ブロックの値が実際に適用された |
| `.claude/skills/` `agents/` `commands/` `output-styles/` `workflows/` | project | ✅ 【実測】skills を確認。他は同一の project 発見経路 |
| 起動ディレクトリの**上位**にある `.claude/skills/` | project | ✅ 公式：リポジトリルートまで遡って探す [\[7\]](./結論・構成案【別紙】出典一覧.md#ref-7) |
| linked worktree から起動したときの `.claude/skills/` `agents/` `commands/` | project | ✅ 公式：探すのは worktree のルートまで。**worktree のルートに `.claude/skills` が無ければ、本体の checkout の skills・agents・commands を読む**（v2.1.277 以降）[\[45\]](./結論・構成案【別紙】出典一覧.md#ref-45)。作業リポジトリが `.claude/` を gitignore する案C-1 では、新しい worktree に `.claude/` が作られないので、この読み先になる |
| `--add-dir <dir>` の `.claude/skills/` `commands/` `agents/` | 追加ディレクトリ例外 | ✅ 公式 [\[19\]](./結論・構成案【別紙】出典一覧.md#ref-19)。**`permissions.additionalDirectories` 設定値経由では一切読まれない**[\[20\]](./結論・構成案【別紙】出典一覧.md#ref-20) |
| `--add-dir <dir>` の `CLAUDE.md` / `.claude/rules/`（`paths:` なし） | 追加ディレクトリ例外 | △ **`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` のときだけ**（all-or-nothing）[\[13\]](./結論・構成案【別紙】出典一覧.md#ref-13) |

> **⚠ 探索範囲は資産ごとに非対称** —— **案C-1 で「どこから起動するか」を縛る根拠**
>
> | 資産 | どこまで探すか | 出典 |
> |---|---|---|
> | `CLAUDE.md` / `CLAUDE.local.md` | **起動ディレクトリと、その全上位ディレクトリ** | [\[11\]](./結論・構成案【別紙】出典一覧.md#ref-11) |
> | `.claude/skills/` | **起動ディレクトリから、リポジトリルートまで遡る** | [\[7\]](./結論・構成案【別紙】出典一覧.md#ref-7) |
> | `.claude/settings.json` | **起動ディレクトリの `.claude/` のみ。親へは遡らない** | [\[22\]](./結論・構成案【別紙】出典一覧.md#ref-22)（前半） |
>
> **`settings.json` だけが遡らない。** そのため作業リポジトリのサブディレクトリから `claude` を起動すると、**`CLAUDE.md` と skills はロードされるのに `permissions` だけが丸ごと効かない**という分かりにくい状態になる。[§5-7](#cautions) で「起動は必ず作業リポジトリのルートから」と定めるのはこれが理由である。
>
> なお `settings.local.json` は **git リポジトリルート基準**（v2.1.211+。ただし Windows など Claude Code がリポジトリルートを使わないケースは例外）であり、`settings.json` とは基準そのものが違う [\[22\]](./結論・構成案【別紙】出典一覧.md#ref-22)。

> **【実測】案C-1 の実形状での確認**
>
> 上表のうち project スコープ行は、**案C-1 の実形状**（= `.claude/` が別リポジトリのクローンであり、かつ作業リポジトリ側では `.gitignore` 対象）で測り直した。**「入れ子の git リポジトリ」「作業リポから見て ignore 済み」のどちらもロードを妨げない。**
>
> 手法: 作業リポジトリ（`git init` 済み・`.gitignore` に `.claude/`）の `.claude/` に共有リポジトリを clone し、リポジトリルートから `claude --model haiku -p` を実行。合言葉をそれぞれ別ファイルに埋め、回収できるかを見た。skill は自己申告ではなく **Skill ツールの起動成否**で判定した。
>
> | 対象 | 合言葉 | 結果 |
> |---|---|:---:|
> | `.claude/CLAUDE.md` | `NESTCLONE-CM7701` | ✅ 回収 |
> | `.claude/rules/plain-rule.md`（`paths:` なし） | `NESTCLONE-RU7702` | ✅ 回収 |
> | `.claude/settings.json` の `env` | `NESTCLONE-EV7703` | ✅ `printenv` で確認 |
> | `.claude/skills/probeskill/SKILL.md` | `NESTCLONE-SK7704` | ✅ Skill ツールで起動成功 |
>
> 作業リポジトリ側の `git status --short` は**空**（`.claude/` は完全に無視され、作業リポのコミットを一切汚さない）。

> **この実測が示す範囲**: 測ったのは上表 4 資産が**入れ子クローンからロードされること**である。**`permissions.allow` が実際に適用されるかは測っていない** —— `claude -p` は workspace trust のダイアログを出さない [\[23\]](./結論・構成案【別紙】出典一覧.md#ref-23) ため、**非対話（`claude -p`）では原理的に確認できない**。入れ子リポジトリと trust の関係は [§3-4](#sec-3-4) で扱い、対話セッションでの確認を未検証項目 **V7**（[§8-2](#sec-8-2)）に置いた。

### §3-2 条件付きロード —— 発火するかは、読み方・資産の種類・モデルで変わる

**本書で最も重要な事実。** 条件付きロードが起きることを、本書では「発火」と呼ぶ。

公式は 3 つの資産について「条件付きでロードされる」仕組みを説明している。発火の条件の書き方は、資産によって違う。

| 資産 | 公式の表現（原文） | 出典 |
|---|---|---|
| `paths:` 付き rule | "A path-scoped rule loads when Claude uses the **Read, Write, or Edit tool** on a matching file. It also loads when Claude views a matching file with a **Bash command that counts as a read**, such as `cat` or `head` on a single file." | [\[15\]](./結論・構成案【別紙】出典一覧.md#ref-15) |
| サブディレクトリの `CLAUDE.md` | "Instead of loading them at launch, Claude Code loads each one once Claude **reads, writes, or edits** another file in that subdirectory. Reading includes viewing the file with a **Bash command that counts as a read**, such as `cat` or `head` on a single file." | [\[12\]](./結論・構成案【別紙】出典一覧.md#ref-12) |
| サブディレクトリの `.claude/skills/` | "They load the first time Claude **reads or edits a file** in that subdirectory and stay available for the rest of the session." | [\[7\]](./結論・構成案【別紙】出典一覧.md#ref-7) |

「読み取りに数える Bash コマンド」は、`cat`・`nl`・`bat`・`batcat`・`head`・`tail`・`sed -n 'X,Yp'`・`grep`・`egrep`・`fgrep`・`rg` を、**1 つのファイルに対して、パイプもリダイレクトも付けずに**実行したものである [\[44\]](./結論・構成案【別紙】出典一覧.md#ref-44)。skills の説明には、Write と Bash コマンドへの言及が無い。

実測の結果は次のとおりで、公式の記述と合っている。

> **【実測】発火の判定**
>
> **手法**: 1 つのサブディレクトリ `sub/` に、`paths: ["**/*.probefile"]` の rule がマッチする対象ファイル・`sub/CLAUDE.md`・`sub/.claude/skills/subskill/` の 3 つを同時に置き、**先行操作の種類だけを変えて 1 セッションずつ**起動した（`claude --model haiku -p`。`haiku` は Claude Haiku 5.5 に解決された）。各セッションは**先行操作に使うツールと `Skill` ツールだけを許可**し、合言葉（資産ごとに埋めた固有の文字列）を読みに行けないようにした。rule と `CLAUDE.md` は合言葉の完全一致で、skill は **`Skill` ツールの起動成否**で判定した。

| 先行操作 | `paths:` 付き rule | サブディレクトリの `CLAUDE.md` | サブディレクトリの `.claude/skills/` |
|---|:---:|:---:|:---:|
| **なし（対照群）** | ❌ | ❌ | ❌ |
| **Read ツールで読む** | ✅ **発火** | ✅ **発火** | ✅ **発火** |
| **Write ツールで新しいファイルを作る** | ✅ **発火** | ✅ **発火** | ✅ **発火** |
| **Edit ツールで編集する**（Read を許可しない。Claude Haiku 5.5） | ✅ **発火** | ✅ **発火** | ✅ **発火** |
| **Edit ツールで編集する**（同上。Claude Haiku 4.5） | —（Edit 自体が失敗する） | —（同上） | —（同上） |
| **Bash で 1 ファイルを `cat` する** | ✅ **発火** | ✅ **発火** | ❌ |
| **Bash で 1 ファイルを `head` する** | ✅ **発火** | ✅ **発火** | ❌ |
| **Bash で 1 ファイルを `grep` する** | ✅ **発火** | ✅ **発火** | ❌ |
| **Bash でパイプを付けて読む**（`cat <ファイル> \| head -1`） | ❌ | ❌ | ❌ |
| **Bash で複数のファイルを読む**（`cat <ファイル 1> <ファイル 2>`） | ❌ | ❌ | ❌ |
| **Grep ツールで検索する** | ❌ | ❌ | ❌ |

この表から言えることは 3 つある。

- **発火しない読み方が残っている。** Grep ツール、パイプ付きの Bash コマンド、複数のファイルを対象にした Bash コマンドでは、3 つとも発火しない。どれも、コードベースの調査やログの解析で普通に使う読み方である
- **資産の種類で違う。** サブディレクトリの skills は、Bash コマンドでは発火しない（Read・Write・Edit ツールでだけ発火した）
- **モデルで違う。** Edit ツールが事前の Read 無しで通るかは、モデルで決まる。Claude Haiku 4.5 では `File has not been read yet. Read it first before writing to it.` で Edit が失敗し、何も発火しなかった。公式も「Claude Opus 4.6・Claude Haiku 4.5 とそれより古いモデルは必ず Read を要する。新しいモデルは、読んでも permission の確認が要らず Read ツールが使えるとき、未読のファイルを編集できる」と書いている [\[44\]](./結論・構成案【別紙】出典一覧.md#ref-44)

> **Bash での書き換えは発火の条件に入っていない。** 公式が挙げる Bash コマンドは読み取りの 11 種だけで、`sed -i`・リダイレクト・スクリプトによる書き換えは含まれない [\[44\]](./結論・構成案【別紙】出典一覧.md#ref-44)。一括置換やコード生成を Bash で回す運用では、ファイルを編集していても `paths:` 付き rule がロードされないことがありうる（この形は実測していない）。

**条件付きロードを待たずに、サブディレクトリの skills をロードする方法**:

| 方法 | 結果 | 測った日と版 |
|---|:---:|---|
| 起動時に `--add-dir <サブディレクトリ>` を付ける | ✅ | 【実測】2026-11-21・CLI 2.1.330 |
| セッションの途中で `/add-dir <サブディレクトリ>` を実行する（v2.1.257 以降）[\[21\]](./結論・構成案【別紙】出典一覧.md#ref-21) | 公式の記載による（対話セッションでは測っていない） | — |
| 非対話（`claude -p`）で `/add-dir` を渡す | ❌ `/add-dir isn't available in this environment.` | 【実測】2026-11-21・CLI 2.1.330 |
| `/reload-plugins` を実行する | ❌（plugin とその同梱の資産しか扱わない） | 【実測】2026-09-14・CLI 2.1.266。今の版では測り直していない |

実測で判定を誤りやすい点（`--debug` のログ、モデルの自己申告）は [実測記録の別紙](./結論・構成案【別紙】実測記録.md#repro) に書いた。

### §3-3 この章の結論

> ### **届けたい資産は、条件ではなく「実体の置き場所」で分ける。**

条件付きロードは「context を節約するための最適化」としては使える。だが**「必要なときに必ずロードされる」ことを前提にした設計の基盤にしてはならない。** 理由は 3 つある。

1. **発火しない読み方が残る。** Grep ツール、パイプ付きや複数ファイルの Bash コマンドでは発火しない【実測】。検索とパイプを主に使う作業（コードベースの調査・ログの解析）では、**`paths:` 付き rule が一度もロードされないまま 1 セッションが終わりうる**
2. **発火するかどうかが、CLI の版・モデル・資産の種類で変わる。** rule とサブディレクトリの `CLAUDE.md` が Bash コマンドや Write・Edit ツールで発火するようになったのは v2.1.288 と v2.1.293 からで [\[44\]](./結論・構成案【別紙】出典一覧.md#ref-44)、skills には今も及んでいない。Edit ツールが単独で通るかはモデルで決まる。メンバーの CLI の版とモデルがそろっていないチームでは、配る側が「必ずロードされる」と言えない
3. **条件の単位が、作業種別ではない。** 条件付きロードの条件は「どのファイルを読んだか」（ファイルの場所と種類）である。出し分けたいのは「設計・実装・テストのどの作業をしているか」で、同じファイルを別の作業種別で読むことは普通にある。**発火が確実になっても、作業種別ごとの出し分けには合わない**

1 と 2 は CLI の版が上がれば解消しうる。3 は条件付きロードの仕組みそのものの性質で、版では変わらない。

**設計上の帰結:**

| やりたいこと | ❌ 使ってはいけない | ✅ 使う |
|---|---|---|
| 作業種別ごとに資産を出し分ける | `paths:` 付き rule、サブディレクトリ `.claude/` | **共有 `.claude` リポジトリのブランチ切替**（[§5](#recommend)） |
| ファイル種別ごとに補足指示を足す | —— | `paths:` 付き rule で**可**（**読み方によっては発火しない**ので、ロードされなくても作業が止まらない内容に限る） |
| 常に効かせたいチーム規約 | `paths:` 付き rule | `paths:` **なし**の `rules/*.md` か `CLAUDE.md` |

> **この制約は、使う方向によって重さが違う。**
>
> - **削減方向（ロードされる量を減らしたい）には安全** —— 条件付きロードが不発でも結果は「ロードされない」だけで、context が予想外に増えることはない。**最悪でも意図した削減が効きすぎるだけ**である
> - **保証方向（必ずロードさせたい）には使えない** —— 不発の結果が「指示が届いていないのに、届いている前提で作業が進む」になる。**失敗が静かで、事後に検知する手段も無い**
>
> したがって `paths:` 付き rule を禁止するのではなく、**「ロードされなくても作業が止まらない内容」に限る**という線引きにする。

> **⚠ `rules/` の symlink 共有も、配る手段には採らない**: `.claude/rules/` は symlink に対応しているが、**作業ディレクトリ外を指す symlink は「外部 import」扱い**になり、プロジェクトで外部 import を承認するまでロードされず、**承認後も `paths:` を持つ rule はロードされない**[\[16\]](./結論・構成案【別紙】出典一覧.md#ref-16)。承認は、対話セッションの開始時にダイアログで 1 プロジェクトにつき 1 回尋ねられる。UNC などネットワーク上のパスを指す symlink はロードされない。共有の手段としては、承認の手間と非ロードの 2 つの穴がある。

<a id="sec-3-4"></a>

### §3-4 ロードされる前に「実行される」もの（trust の前後）

配布設計では**「いつ trust するか」が挙動を変える**。公式は trust 前後で何が動くかを表で明示している [\[23\]](./結論・構成案【別紙】出典一覧.md#ref-23)。**列は「そのフォルダ自体を trust していない 2 つの状況」**である。

| リポジトリが供給するもの | 親フォルダしか trust していない場合 | `claude -p` / SDK 実行（ダイアログが出ない） |
|---|---|---|
| `settings.json` の **hooks**・**`env` ブロック**・`apiKeyHelper` 等のヘルパーコマンド、および project skill の `hooks` / `allowed-tools` | **実行される**（"Used"） | **実行される** |
| **`permissions.allow` ・ `additionalDirectories`** | **使われない。** trust ダイアログが改めて表示され、内容が列挙される | **使われない。** stderr に `this workspace has not been trusted` 警告 |
| project subagent の frontmatter hooks、project の `@skills-dir` plugin、**`extraKnownMarketplaces`** | **使われない。しかもダイアログも出ない** | **使われない** |
| subagent frontmatter のインライン `mcpServers` | **使われない。ダイアログも出ない** | **使われない** |
| `.mcp.json` のサーバー | 接続前に**確認される**（リポジトリ自身の承認は数に入らない） | **確認せず接続される**（"Connected without asking, approved or not"） |
| `.mcp.json` サーバーの `headersHelper` | trust を承認するまで**実行されない**（静的 `headers` だけで接続） | **実行されない**（stderr に `headersHelper not run`） |

> **⚠ trust は「git リポジトリルート」を鍵にし、入れ子リポジトリはそこから除かれる。** 公式は trust の単位を **「そのリポジトリの中に入れ子になった git リポジトリ（submodule など）を除いた、git リポジトリのルート」**と定義している [\[23\]](./結論・構成案【別紙】出典一覧.md#ref-23)。**案C-1 の `.claude/` はまさにその「入れ子になった git リポジトリ」の形状**であり、作業リポジトリを trust しても**その trust には含まれない**。
>
> **ただし公式は、この場合の扱いも書いている。**「上表の**『親フォルダしか trust していない』列は入れ子リポジトリの内側には適用されない**。対話セッションでは Claude Code が**その入れ子リポジトリについて trust ダイアログを表示**し、そこでの `claude -p` / SDK 実行は `claude -p` 列に従う」[\[23\]](./結論・構成案【別紙】出典一覧.md#ref-23)。
>
> **したがって公式仕様上の想定はこうなる。**
>
> | 起動の仕方 | 共有 `.claude/settings.json` の `permissions.allow` |
> |---|---|
> | **対話セッション** | **`.claude/` について trust ダイアログが出る。承認すれば適用される**（＝メンバーは trust ダイアログを 2 回見る） |
> | **`claude -p` / SDK** | **適用されない**（ダイアログが出ないため。stderr に警告が出る） |
>
> **`deny` / `ask` はこの影響を一切受けない** —— trust 非依存で常に適用される [\[23\]](./結論・構成案【別紙】出典一覧.md#ref-23)。**「危険なコマンドを塞ぐ」という統制側の主張は、trust の不確定性から独立している。**
>
> **実測は未了である。** `claude -p` は trust ダイアログを出さない [\[23\]](./結論・構成案【別紙】出典一覧.md#ref-23)ため、**非対話（`claude -p`）では検証できない**。対話セッションでの確認手順を未検証項目 **V7**（[§8-2](#sec-8-2)）に置いた。**ダイアログが実際に出るか・1 回の承認で足りるかは、展開前に確認すること**（周知文言と CI 運用が変わる）。
>
> **逃げ道**: どうしてもダイアログを経ずに trust させたい場合、`~/.claude.json` の `projects["<パス>"].hasTrustDialogAccepted` を `true` にする手段が公式に案内されている [\[23\]](./結論・構成案【別紙】出典一覧.md#ref-23)。**onboarding スクリプトに組み込める**。

> **trust に関わるそのほかの挙動**
>
> - `--add-dir`・`/add-dir` で、trust が及んでいないフォルダを足すと trust を尋ねられる（v2.1.326 以降）[\[47\]](./結論・構成案【別紙】出典一覧.md#ref-47)。案A（`--add-dir` 方式）を評価するときに効く（[付録 2.2](./結論・構成案【別紙】付録.md#adddir-exceptions)）
> - `claude --bg` は trust を先に確かめる。端末ではダイアログが出て、スクリプトからの実行では `Workspace not trusted` で終了する [\[50\]](./結論・構成案【別紙】出典一覧.md#ref-50)
> - 対話セッションは、既定で auto mode で始まる（`claude -p`・SDK・`defaultMode` を指定した場合などを除く）。auto mode では、広すぎる `permissions.allow` の一部が無視される [\[53\]](./結論・構成案【別紙】出典一覧.md#ref-53)。配る予定の allow のどれが無視されるかは測っていない（[§8-2](#sec-8-2) の V9）。`deny` と `ask` は影響を受けない
> - プロジェクトのものでも trust 済みでもないリポジトリでは、読み取り専用の git コマンドにも確認が出る（v2.1.325 の changelog による）[\[51\]](./結論・構成案【別紙】出典一覧.md#ref-51)。入れ子クローンの `.claude/` がこれに当たるかは確かめていない（[§8-2](#sec-8-2) の V8）。ランチャーは Claude の外で git を実行するので、影響を受けない

> **⚠ `extraKnownMarketplaces` は trust 前に使われず、しかもダイアログも出ない**（上表 3 行目）。**案B（plugin 併用）を案C-1 と組み合わせるとき、共有 `.claude/settings.json` に置いた marketplace 宣言は trust 承認まで効かない。** plugin の導入は onboarding 手順に明示的に組み込む（[§5-2](#assignment)）。

> **案C-1 での意味（hooks）**: 共有 `.claude` リポジトリの `settings.json` に hooks を置くと、**ブランチを切り替えた直後・trust 前でも走る**。ブランチごとに hooks を変える設計は、切り替え事故が「知らないスクリプトが動く」に直結する。**hooks は原則 `main` ブランチに置き、作業種別ブランチでは増やさない**（[§5-7](#cautions)）。

> ### ⚠ 案C-1 では `settings.json` の性質が変わる —— 導入前にチームへ周知する
>
> 従来 `.claude/settings.json` は「そのリポジトリを触る人が、自分のために置いた設定」だった。**案C-1 ではそれが「共有リポジトリから全メンバーへ配られる設定」になる。** ファイル名も書式も同じまま、**影響範囲だけが 1 人から全員へ広がる。**
>
> 帰結として最も重いのが **`env` ブロック**である。
>
> - `env` の値は**上表のとおり trust 前でも `claude -p` でも適用・実行される**
> - 共有リポジトリに commit された `env` は**全メンバーの端末へ配られ、git 履歴に恒久的に残る**
>
> したがって **共有 `.claude/settings.json` の `env` に秘匿値を書いてはならない。**
>
> | 分類 | 例 | 置き場所 |
> |---|---|---|
> | **分類A: 秘匿値** | API キー・認証トークン・パスワード・組織外秘の内部 URL | **OS 環境変数**（各自の端末で設定。共有リポには入れない） |
> | 分類B: 非秘匿の共通値 | モデル既定値・タイムアウト・機能フラグ・公開ドキュメントの URL | 共有リポの `settings.json` の `env` に置いてよい |
> | 分類C: 個人ごとに異なる非秘匿値 | ローカルのツールパス等 | `.claude/settings.local.json`（gitignore 済み） |
>
> **この分類は既存ランチャーの方針（分類A は OS 環境変数）をそのまま継承する**（[§5-6](#sec-5-6)）。

## §4 どう絞るか（統制機構）

配ることと**絞ること**は別問題である。ここでは「ロードされる量を減らす」機構と「メンバーに上書きさせない」機構を分けて整理する。**チームが自前で握れるものと、組織の IT 基盤がないと握れないものの線引き**が本節の要点。

<a id="sec-4-1"></a>

### §4-1 ロードされる量を絞る機構

| 機構 | 効き方 | 誰が握れるか | 制約 |
|---|---|---|---|
| **置き場所そのもの（＝案C-1 のブランチ）** | 置いていないものは読まれない。**最も確実** | **チーム** | 設計とレビューの規律に依存 |
| `claudeMdExcludes` | `CLAUDE.md` / `rules` を**パス・glob 単位**で除外。**user / project / local / managed の全スコープで設定可・commit 可・配列はスコープ間でマージ**[\[18\]](./結論・構成案【別紙】出典一覧.md#ref-18) | **チーム（project へ commit）** | 静的（タスク単位の出し分け不可）。**managed policy の `CLAUDE.md` は除外できない**[\[17\]](./結論・構成案【別紙】出典一覧.md#ref-17) |
| `paths:` 付き rule | マッチしたファイルを読み書きしたときにロードされる。**読み方によっては発火しない** | チーム | **[§3-2](#conditional) の制約**。ロードされない前提で書く |
| `--setting-sources` から `project` を外す | フラグ追加ディレクトリの skills / commands / subagents は `project` setting source 経由なので全部落ちる [\[20\]](./結論・構成案【別紙】出典一覧.md#ref-20) | 起動側（ランチャー） | **作業リポジトリ自身の project 設定も同時に落ちる**（全か無か） |
| bare mode（`--bare`） | hooks / skills / commands / subagents / plugins / MCP / auto memory / `CLAUDE.md` の**自動発見を一括でスキップ**。**`--add-dir` ディレクトリだけは部分例外**で、その `.claude/skills/` はロードされ `commands` / `agents` はロードされない [\[36\]](./結論・構成案【別紙】出典一覧.md#ref-36)[\[20\]](./結論・構成案【別紙】出典一覧.md#ref-20) | 起動側（headless） | **対話運用向けではない**（CI・スクリプトで再現性を得るためのモード） |
| `--safe-mode` / `CLAUDE_CODE_SAFE_MODE=1` | `CLAUDE.md` / skills / plugins / hooks / MCP / commands / agents / output-styles / workflows を**一括で無効化**して起動 [\[34\]](./結論・構成案【別紙】出典一覧.md#ref-34)[\[10\]](./結論・構成案【別紙】出典一覧.md#ref-10) | 起動側 | **切り分け用。常用しない**（managed settings のポリシーは適用され続けるが、managed の plugin・skill・`CLAUDE.md`・MCP サーバーは読まれない） |
| `strictPluginOnlyCustomization` | skills / agents / hooks / MCP を **plugin ＋ managed 由来のみ**に制限（`true` で 4 種全部、配列で個別指定） | **層3（managed）のみ**[\[28\]](./結論・構成案【別紙】出典一覧.md#ref-28) | **Scope が Managed 固定。チームレベルでは使えない** |

> **チームが主体的に握れるのは上 3 つだけ。** 下 4 つは起動側または組織側の機構であり、チームの設計手段には数えない。

> **`paths:` 付き rule を書くときの注意**[\[49\]](./結論・構成案【別紙】出典一覧.md#ref-49)
>
> - **frontmatter の YAML が壊れている rule は、`paths` なしとして扱われ、起動時に無条件でロードされる。** 条件付きのつもりの rule が、エラー無しで常時ロードに変わる
> - `paths` のパターンは、その rule の基準ディレクトリからの相対で照合される。`*.md` のようにディレクトリを含まないパターンは、基準ディレクトリより下のどの階層のファイルにもマッチする
> - 条件付きでロードされるファイル（サブディレクトリの `CLAUDE.md`・`paths:` 付き rule）には 1 ファイルごとの文字数の上限があり、超えると先頭の部分だけが渡される（200K の context window では 40,000 文字。v2.1.309 以降）[\[11\]](./結論・構成案【別紙】出典一覧.md#ref-11)

> **📊 機構別の context コスト** —— 「どこに置くか」はロード経路だけでなく**常時消費する context 量**でも決まる。
>
> | 資産種別 | 常時消費する量 | 削減の効き |
> |---|---|---|
> | `CLAUDE.md` | **全文を常時**ロード | **最も効く**。`claudeMdExcludes` で絞る。公式も **1 ファイル 200 行以下**を推奨し、4 MiB 超はスキップされる [\[11\]](./結論・構成案【別紙】出典一覧.md#ref-11) |
> | `rules/*.md`（`paths:` なし） | **全文を常時** | **効く**。ブランチ分割（案C-1）で絞る |
> | `rules/*.md`（`paths:` あり） | マッチ時のみ全文 | 条件付き（[§3-2](#conditional)） |
> | `skills/` | **`name` ＋ `description` のみ**（本体は起動時に読む） | **薄い**。ただし**数が多いと description が切り詰められ選択精度が落ちる**とされる〔**未実測**——切り詰めが始まる件数も切り詰め方も本書では測っていない（[§8-2](#sec-8-2) V4）〕ため、精度維持の観点では分割に意味がありうる |
> | `commands/` ・ `agents/` | 呼ばれたときのみ | —— |
>
> **含意**: 「context 削減」を目的に skills を外出ししても効果は薄い。**削減が効くのは `CLAUDE.md` と `rules/`**。
>
> **⚠ `@path` import は削減にならない**: `CLAUDE.md` を `@path` で分割しても、**import されたファイルは、import した側のファイルと同時に context にロードされる**[\[11\]](./結論・構成案【別紙】出典一覧.md#ref-11)。整理には役立つが節約にはならない。

<a id="sec-4-2"></a>

### §4-2 上書きさせない機構（＝強制）

**強制できるのは層3（managed settings）だけ。** 層1（commit）と `--add-dir` は強制力ゼロ、層2（plugin）も弱い（`enabledPlugins` で誘導するのみで、install も無効化も各自の自由）。

> **⚠ ただし「層1 は強制力ゼロ」は `deny` には当てはまらない。** 層1 で配った `permissions.deny` / `ask` は、**メンバーが `settings.local.json` で明示的に上書きしない限り確実に効く**（しかも **trust 非依存**＝[§3-4](#sec-3-4)）。層3 が要るのは「**メンバーによる上書きを不可能にしたい**」ときであって、「deny を効かせたい」だけなら層1 で足りる。
>
> 逆に、**許可を事前に付与する方向（`permissions.allow`）は trust 依存**である（[§3-4](#sec-3-4)）。**塞ぐ統制は確実・あらかじめ許す利便は不確実**、という非対称を前提に設計する。

層3 には 3 系統あり、**必要な基盤コストが大きく異なる**。

| 系統 | 仕組み | 前提 | 基盤コスト |
|---|---|---|---|
| **(1) server-managed** | claude.ai admin console から中央 push | **Claude for Teams / Enterprise 契約**[\[31\]](./結論・構成案【別紙】出典一覧.md#ref-31)。設定操作には **Owner または Primary Owner ロール**が必要。**Bedrock / Google Cloud's Agent Platform / Microsoft Foundry / Claude Platform on AWS では非対応**[\[29\]](./結論・構成案【別紙】出典一覧.md#ref-29)。**Enterprise プランは、グループごとに別の configuration を配れる。Team プランは組織全体へ一律**。HIPAA を有効にした組織ではグループ別の配信を使えない。1 人に当たる configuration は 1 つで、configuration 同士はマージされない [\[30\]](./結論・構成案【別紙】出典一覧.md#ref-30) | **極低**（MDM 不要） |
| **(2) endpoint-managed** | MDM（Jamf / Kandji / Intune / GPO 等）で `managed-settings.json` を OS パスへ配布、または plist / レジストリへポリシー配布 [\[41\]](./結論・構成案【別紙】出典一覧.md#ref-41) | 管理者権限・MDM 基盤 | **高**（MDM 運用）〜中（手動配置） |
| **(3) gateway-managed** | 自ホスト型 Claude apps gateway が remote managed settings の同等配信を担う。gateway にサインインしたクライアントは `api.anthropic.com` ではなく gateway から取得。IdP グループ単位のポリシー割当も可 [\[30\]](./結論・構成案【別紙】出典一覧.md#ref-30) | 自ホスト gateway の運用。第三者プロバイダ（Bedrock / Agent Platform / Foundry）向け | **中** |

> **統制キーの全件一覧は [付録 1](./結論・構成案【別紙】付録.md#appendix-a)**。どのキーが managed 専用か、複数の managed ソースがあるときどれが勝つかをまとめてある。

> **(3) は (2) を不要にはしない。** gateway へ接続させる設定（`forceLoginMethod` / `forceLoginGatewayUrl`）自体は gateway から push できないため、**初期ブートストラップだけ endpoint-managed に残る**。

> **層3 が届いているかの確認**: `claude doctor` の **`Organization policy` 行**に、ポリシーをどこから読み込んだか（読み込めなかった理由）が出る（**v2.1.261+**）。セッション中は `/status` でも同じ行が見られる [\[26\]](./結論・構成案【別紙】出典一覧.md#ref-26)。

<a id="sec-4-3"></a>

### §4-3 層3 を重ねたときの相互作用 —— 「無視される」ではなく「起動時に落ちる」

層1+2 で組んだランチャーに後から層3 が重なると、**セッションが起動しなくなる経路が 2 本ある**。

| 層3 側の設定 | 起動時に拒否されるフラグ | 症状 |
|---|---|---|
| `disableSideloadFlags: true`（v2.1.193+）[\[26\]](./結論・構成案【別紙】出典一覧.md#ref-26) | `--plugin-dir` / `--plugin-url` / `--agents` / `--mcp-config`。環境変数 `CLAUDE_CODE_PLUGIN_DIRS`（v2.1.280+）と Agent SDK の `addPlugins`（v2.1.301+）で渡した plugin も対象 [\[28\]](./結論・構成案【別紙】出典一覧.md#ref-28) | 起動時に拒否。cloud セッションでは in-process `type: "sdk"` 以外の MCP サーバーを落として起動する |
| `managed-mcp.json` を配備 [\[35\]](./結論・構成案【別紙】出典一覧.md#ref-35) | `--mcp-config` / `--strict-mcp-config` | `You cannot dynamically configure MCP servers when an enterprise MCP config is present` で **exit** |

> **案C-1 はこの罠を踏まない。** 案C-1 のランチャーは**起動フラグを一切使わない**（`--add-dir` も `--settings` も `--mcp-config` も不要）。層3 を敷いている配布先でもそのまま成立する。これは `--add-dir` 方式に対する案C-1 の明確な優位点である（[§6](#alternatives)）。

**一方、起動はするが、配った資産の一部がエラー無しで効かなくなる組み合わせがある。こちらは案C-1 でも起きる。**

| 層3 側の設定 | 効かなくなるもの |
|---|---|
| `allowManagedPermissionRulesOnly` | リポジトリ・個人・`--add-dir`・skills ディレクトリ型の plugin に置いた permission rule に加えて、**そこに置いた skill の `allowed-tools` による事前承認も無効になる**（v2.1.282 以降）[\[46\]](./結論・構成案【別紙】出典一覧.md#ref-46)。案C-1 で配った skill が、層3 を敷いた配布先では確認を求めるようになる |
| `allowManagedHooksOnly` | plugin に同梱した hooks。managed が `enabledPlugins` で force-enable した plugin のものだけが残る（[§5-2](#assignment)） |
| `strictPluginOnlyCustomization` | user と project に置いた skills・agents・hooks・MCP（指定した種類）。案C-1 の `.claude/` に置いた資産がこれに当たる（[付録 1.1](./結論・構成案【別紙】付録.md#sec-a-1)） |

## §5 推奨構成（案C-1）

<a id="sec-5-1"></a>

### §5-1 全体像

**`.claude/` をひとつの Git リポジトリにし、それを作業リポジトリの `.claude/` として clone する。作業種別はブランチで切り替える。**

```txt
■ 共有 .claude リポジトリ（メンテナー 1〜2 名が管理）

  main                    チーム全体で常に要る資産
   ├── java/base         java 系リポジトリ群で共通
   │    ├── java/design
   │    ├── java/coding
   │    └── java/ut
   └── python/base
        └── python/…

  すべてのブランチは main を先祖に持つ。main が更新されたら rebase で取り込む。

■ 作業リポジトリ（各メンバーの手元）

  <work-repo>/
  ├── .claude/                  ← 共有リポジトリのクローン。作業リポの .gitignore 対象
  │   ├── CLAUDE.md             （切り替えたブランチの内容になる）
  │   ├── rules/*.md
  │   ├── skills/ agents/ commands/
  │   ├── settings.json
  │   └── settings.local.json   ← 個人設定。共有リポ側で gitignore（後述）
  ├── CLAUDE.md                 ← このリポジトリ固有の指示
  ├── .mcp.json                 ← このリポジトリ固有の MCP（要るなら）
  └── start_claude_code.ps1     ← ランチャー
```

**`--add-dir` / `--settings` / `--mcp-config` / `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` はいずれも不要になる。**

<a id="sec-5-2"></a>
<a id="assignment"></a>

### §5-2 資産の振り分け

| 資産 | 置き場所 | 理由 |
|---|---|---|
| チーム共通・作業種別を問わず要るもの | 共有リポの **`main`** | 全ブランチの先祖なので必ず届く |
| 作業種別ごとに要るもの | 共有リポの**対応ブランチ** | ロードさせたくないブランチには実体が無い |
| **作業リポジトリ固有の指示** | 作業リポの**ルート `CLAUDE.md`** | `.claude/` は共有リポなので、リポジトリ固有を混ぜるとブランチが破裂する |
| **作業リポジトリ固有の機能資産**（skill / agent / hooks） | **plugin**（P3） | 同上。plugin なら作業リポの `settings.json` から `enabledPlugins` で有効化できる。**ただし外部ソースの plugin は `enabledPlugins` だけでは入らず、メンバーの `claude plugin install` が要る**（[§6-2](#sec-6-2)）。また層3 で `allowManagedHooksOnly` が敷かれた環境では、**plugin 同梱の hooks は managed が `enabledPlugins` で明示的に force-enable したもの以外すべて落ちる**[\[28\]](./結論・構成案【別紙】出典一覧.md#ref-28) |
| 作業リポジトリ固有の MCP | 作業リポの root `.mcp.json` | `.mcp.json` は root 直下にしか置けない |
| **環境変数（非秘匿）** | 共有リポ `settings.json` の `env` | モデル既定値・タイムアウト等。**全メンバーへ配られ git 履歴に残る**ことを前提に選ぶ |
| **秘匿値**（API キー・トークン・パスワード・組織外秘 URL） | **OS 環境変数**（各自の端末） | **共有リポには絶対に置かない。** `env` は trust 前・`claude -p` でも適用される（[§3-4](#sec-3-4)）。既存ランチャーの分類A と同じ方針 |
| 個人設定 | `.claude/settings.local.json` | **共有リポ側の `.gitignore` に必ず入れる**（後述） |
| 作業ディレクトリの外への書き込みの制限 | 共有リポ `settings.json` の `permissions.blockWritesOutsideWorkingDirectories` | どの settings ファイルにも書けるキーなので、層3 が無くても commit して配れる（v2.1.314 以降）[\[48\]](./結論・構成案【別紙】出典一覧.md#ref-48)。メンバーが `settings.local.json` で戻せる点は、ほかの project の設定と同じである |

> **「作業リポジトリ固有」を `.claude/` に置かない**のがこの設計の肝。置いた瞬間、ブランチが「作業種別 × リポジトリ」の直積に膨らむ。

<a id="sec-5-3"></a>

### §5-3 ブランチ命名 —— 親ブランチ名をそのまま使ってはいけない

> **【実測】git の ref 仕様により、`java` ブランチと `java/design` ブランチは共存できない。**
>
> ```text
> $ git switch -c java
> $ git switch -c java/design
> fatal: cannot lock ref 'refs/heads/java/design': 'refs/heads/java' exists; cannot create 'refs/heads/java/design'
> ```
>
> `git branch <親の名前>` の後に `git branch <親の名前>/<子の名前>` を実行しても、同じエラーになる。
>
> ref は `refs/heads/<名前>` というパスで保持されるため、`refs/heads/java` がファイルとして存在すると `refs/heads/java/` をディレクトリにできない（**D/F コンフリクト**）。これは git の根本的な制約である。**packed-refs（ref を個別ファイルではなく単一ファイル内のテキスト行として持つ形式）でも回避できない**〔**公式仕様上の推定・未実測**——packed-refs 状態での再現は測っていない。D/F 判定は ref 名の名前空間に対する検査であり、格納形式に依存しないと理解している〕。

**規約**: **すべてのブランチ名を「葉トークン」で終える。名前空間セグメントをそのままブランチ名にしない。**

| ❌ 不可 | ✅ 可 | 備考 |
|---|---|---|
| `java` ＋ `java/design` | **`java/base` ＋ `java/design`** | 推奨。`java/` 配下にまとまり、多くの Git クライアントでフォルダとして畳まれる |
| `java` ＋ `java/design` | `java` ＋ `java-design` | 平坦。階層が視覚的に分かりにくい |
| `java/design` ＋ `java/design/ut` | `java/design/base` ＋ `java/design/ut` | 3 段目も同じ規約が必要 |

> `base` は「この名前空間の共通ぶん」を表す予約語として決め打ちする（`common` 等でもよいが**チームで 1 つに固定する**）。`base` は `coding` / `design` / `ut` といった作業種別名よりアルファベット順で先に来るので、ブランチ一覧でも自然に先頭へ並ぶ。
>
> **本リポジトリ（`cc-relative-info`）の `feature/<X>` 規約と同じ構造**である——`feature` というブランチは作らず、常に `feature/` 配下に葉を作る。

<a id="sec-5-4"></a>

### §5-4 親ブランチへの追従は `rebase`

**方針: 子ブランチは親の更新を `rebase` で取り込む（`merge` は使わない）。**

**理由**（作業指示者判断・2026-09-14 確定）:

1. 多段の親子関係で「**全ブランチが先祖の更新を取り込めているか**」を**ブランチグラフで視覚的に把握できる**。取り込み済みなら一直線に並ぶので、反映漏れが一目で分かる。`merge` だとブランチ数に比例してグラフがスパゲッティ化し、漏れの検知が難しくなる
2. メンテナーは **1〜2 名の選任担当**。force-push の衝突リスクが実質的に無い
3. commit ハッシュの書き換わりによって支障が出る作業・欠落する維持管理情報が無い

> **⚠ この方針は「共有 `.claude` リポジトリ限定」である。** 通常の開発リポジトリや、多人数が同じブランチを触るリポジトリには**そのまま適用しない**。

#### 多段の伝播は `rebase.updateRefs` で一括

git 2.38+ の `rebase.updateRefs`（`--update-refs`）を使うと、**rebase 対象のコミットを指す中間ブランチも一緒に前進する**。

```bash
# メンテナー側。java/design を rebase すると java/base も一緒に動く
git switch java/design
git -c rebase.updateRefs=true rebase main
git push --force origin main java/base java/design
```

> **【実測】** 上記 1 回の rebase で中間ブランチが更新されることを確認した。
>
> ```text
> Successfully rebased and updated refs/heads/java/design.
> Updated the following refs with --update-refs:
>         refs/heads/java/_base
> ```
>
> 実測の足場では、本文の `main` に当たるブランチが `master`、`java/base` に当たるブランチが `java/_base` という名前になっている（上の出力はそのまま引いた）。rebase 後、`git merge-base --is-ancestor` で、中間ブランチが `master` を、`java/design` が中間ブランチを先祖に持つことを確かめた。

> **⚠ 更新されるのは「ローカルに存在するブランチ」だけ。**【実測】中間ブランチ `java/base` を**ローカルに持たないクローン**で同じ rebase を実行すると、`Updated the following refs` の行そのものが出ず、**中間ブランチは黙って取り残される**（エラーにならない）。
>
> **メンテナーは全ブランチをローカルに持った状態で作業すること。** 運用に組み込むなら、rebase 前に `git fetch --all --prune` ＋ 全リモートブランチのローカル追跡ブランチ作成をスクリプト化する。

> **⚠ リモート側の force-push 保護を確認する。** GitHub の branch protection 等で force-push が禁止されていると、この運用は成立しない。共有 `.claude` リポジトリは**メンテナー限定の force-push を許可する**設定にする。

> **⚠ 恒久設定にする場合**: `git config --global rebase.updateRefs true` を全メンテナーに入れると付け忘れが無くなる。ただし**他リポジトリの rebase 挙動も変わる**ので、`git -c` での都度指定かリポジトリローカル設定（`git config --local`）を推奨する。

#### `main` を更新したときの定常手順（メンテナー）

`rebase.updateRefs` が連れて上がるのは**同一系列の中間ブランチだけ**である。系列が複数あるなら**系列ごとに rebase する**。

**① 全ブランチを fetch し、ローカル追跡ブランチを作る**

```bash
git -C <shared-claude> fetch --all --prune
for b in $(git -C <shared-claude> branch -r --format='%(refname:short)' \
           | sed 's|^origin/||' | grep -v '^HEAD$'); do
  git -C <shared-claude> branch --track "$b" "origin/$b" 2>/dev/null || true
done
```

**これを飛ばすと中間ブランチが黙って取り残される**（上の ⚠ のとおり、エラーにもならない）。

**② 系列ごとに、その系列の「葉ブランチ」で rebase する**（`--update-refs` が中間を連れて上がる）

```bash
git -C <shared-claude> switch java/ut
git -C <shared-claude> -c rebase.updateRefs=true rebase main
git -C <shared-claude> switch python/coding
git -C <shared-claude> -c rebase.updateRefs=true rebase main
```

葉が並列に複数ある系列（`java/design` と `java/ut` が兄弟など）は、**葉の数だけ rebase する**。

**③ 取り残しが無いことを検査する**

```bash
git -C <shared-claude> branch --no-merged main
```

**出力が空であること**を確認する。1 行でも出れば、そのブランチは `main` を取り込めていない。**この検査を省くと、そのブランチを使うメンバーは古い規約のまま作業し続け、しかも誰も気づかない。**

**④ まとめて force-push する**

```bash
git -C <shared-claude> push --force-with-lease origin \
    main java/base java/design java/ut python/base python/coding
```

`--force` ではなく **`--force-with-lease`** を使う（他のメンテナーの push を踏み潰さないため）。

> **`main` は rebase の対象にならない。** 上の手順で `main` は常に rebase の**土台**であり、書き換えられることがない。したがって**リモートで `main` だけ force-push を禁止しても、この運用は壊れない**（[§5-7](#cautions)）。

<a id="mirror"></a>

### §5-5 メンバー側のクローンは「読み取り専用ミラー」

メンバー側の `.claude/` は**編集しない前提**で運用する。更新は次の 3 コマンド。

```bash
git -C .claude fetch --all --prune
git -C .claude switch <ブランチ>
git -C .claude reset --hard "origin/<ブランチ>"
```

> **⚠ `git pull --ff-only` は使えない。**【実測】メンテナーが rebase するとハッシュが変わって分岐扱いになるため、`fatal: Not possible to fast-forward, aborting.`（**終了コード 128**）で**毎回失敗する**。壊れはせず止まるだけだが、定常運用が回らない。失敗後に `reset --hard` すれば正常に復旧することも確認済み。

**保護されるもの・されないもの**:

| 対象 | `reset --hard` 後 | 根拠 |
|---|---|---|
| `.claude/settings.local.json`（**untracked かつ ignore 済み**） | ✅ **残る**【実測】 | `reset --hard` は untracked / ignored ファイルに触らない |
| `.claude/settings.local.json`（**共有リポで 1 度でも commit されたことがある**） | ❌ **上書きされる** | tracked なので reset の対象になる |
| メンバーが `.claude/` 配下で加えたローカル変更 | ❌ **破棄される** | 設計どおり（ミラーなので） |

> **⚠ 共有リポジトリの `.gitignore` に `settings.local.json` を必ず入れること。** どこか 1 ブランチにでも commit された瞬間、次の `switch` で**全メンバーの個人設定が消える**。【実測】ignore 済み・untracked であれば `switch` と `reset --hard` を挟んでも残ることを確認した。git が追跡している `settings.local.json` には、permission の確認で選んだ「今後確認しない」も保存されない（v2.1.323 以降）[\[51\]](./結論・構成案【別紙】出典一覧.md#ref-51)。

> **⚠ `reset --hard` の前に `git status --porcelain` を確認する。** ローカル変更が残っている場合、**切替先ブランチと内容が衝突すれば `switch` はその時点で失敗する**。衝突しなければ `switch` は成功し、変更を持ち越す——**が、直後の `reset --hard` でその変更は結局失われる**。**どちらの結末も避けたいので、`switch` より前に検査し、変更があれば警告して中断する。**

> **detached HEAD 方式は採らない**: `git checkout --detach origin/<branch>` なら `reset --hard` を避けられるが、ブランチ名が `HEAD` になり、**statusline で現在の作業種別が見えなくなる**。取り違え防止のほうを優先する。

### §5-6 ランチャーの責務

**責務は 4 つだけ**: ①存在確認 ②ローカル変更の検査 ③同期 ④起動。**起動フラグを一切渡さない**のがこの設計の成果である。

以下は**最小例**であり、そのまま配布できる完成品ではない（既存ランチャーとの関係は後述）。**要点は「git の各呼び出しで終了コードを検査すること」**にある。

```powershell
# start_claude_code.ps1（Windows 版・最小例）
param([string]$Branch = "main")

# 作業リポジトリのルートを基準にする（§5-7「起動はルートから」）
Set-Location $PSScriptRoot

$ClaudeDir = Join-Path $PSScriptRoot ".claude"
$SharedUrl = "https://github.com/<org>/<shared-claude>.git"

# 1. 共有クローンの存在確認（無ければ clone）
if (-not (Test-Path (Join-Path $ClaudeDir ".git"))) {
    git clone --branch $Branch $SharedUrl $ClaudeDir
    if ($LASTEXITCODE -ne 0) {
        [Console]::Error.WriteLine("clone に失敗しました。中断します。")
        exit 1
    }
}

# 2. ローカル変更の検査（switch より前に）
$dirty = git -C $ClaudeDir status --porcelain
if ($LASTEXITCODE -ne 0) {
    [Console]::Error.WriteLine(".claude/ を git リポジトリとして読めません。中断します。")
    exit 1
}
if ($dirty) {
    [Console]::Error.WriteLine(".claude/ にローカル変更があります。更新を中止しました:`n$dirty")
    [Console]::Error.WriteLine("破棄してよければ: git -C .claude reset --hard; git -C .claude clean -fd")
    exit 1
}

# 3-a. fetch（失敗しても続行 ＝ オフラインでも起動できるようにする）
git -C $ClaudeDir fetch --all --prune
if ($LASTEXITCODE -ne 0) {
    Write-Warning "fetch に失敗しました。手元にある内容で起動します（最新でない可能性があります）。"
}

# 3-b. switch（失敗したら中断。ここで進むとブランチが静かに壊れる）
git -C $ClaudeDir switch $Branch
if ($LASTEXITCODE -ne 0) {
    [Console]::Error.WriteLine("ブランチ '$Branch' への切替に失敗しました。中断します。")
    exit 1
}

# 3-c. 現在ブランチが指定と一致することを確認してから reset --hard
$current = (git -C $ClaudeDir rev-parse --abbrev-ref HEAD)
if ($LASTEXITCODE -ne 0 -or $current.Trim() -ne $Branch) {
    [Console]::Error.WriteLine("現在のブランチ '$current' が指定 '$Branch' と一致しません。reset を中止します。")
    exit 1
}

git -C $ClaudeDir reset --hard "origin/$Branch"
if ($LASTEXITCODE -ne 0) {
    [Console]::Error.WriteLine("reset --hard に失敗しました。中断します。")
    exit 1
}

# 4. 起動（起動フラグは不要）
claude
```

> ### ⚠ 終了コードを検査しないと、ブランチが「静かに壊れる」
>
> **【実測】** `switch` の失敗を無視して `reset --hard` を続けると、**現在いるブランチの名前はそのままに、中身だけが別ブランチで上書きされる**。
>
> ```text
>     switch: fatal: invalid reference: does/not/exist
>     switch の終了コード: 128
>     reset: HEAD is now at 3e83305 other 版
>     reset の終了コード: 0
>   現在のブランチ: master
>   asset.txt: other の資産（main には存在してはいけない）
>   master の先頭: 3e83305 other 版
>   origin/master の先頭: 8cb2c58 main 初版
> ```
>
> **何が起きているか**: `switch` が exit 128 で失敗しても HEAD は元のブランチに残る。そこへ `reset --hard origin/<別ブランチ>` が走ると、**元のブランチそのものを別ブランチの内容へ移動させてしまう**。
>
> **なぜ気づけないか**: **ブランチ名は変わらない。** そのため [§5-7](#cautions) で推奨する「statusline に `.claude/` の現在ブランチを表示する」という取り違え防止策が**偽陰性になる**——statusline は正しい名前を表示し続け、中身だけが別物になる。
>
> 上記 3-b（`switch` 失敗で中断）と 3-c（reset 前のブランチ名一致確認）は、**この 1 点を塞ぐためにある**。

**`fetch` と `switch` / `reset` で扱いを変える理由**: `fetch` の失敗はネットワーク不通が主因で、**手元の内容で作業を続けられる**（古いだけ）。一方 `switch` / `reset` の失敗は**「意図したブランチで作業していない」状態**を生むので、続行してはならない。

#### `reset --hard` の deny 設定

> **⚠ 「Claude には触らせないが、ランチャーには許す」という非対称を明記する。**
>
> **共有 `.claude` リポジトリの `settings.json`（`main` ブランチに置けば全ブランチへ届く）に、次の deny を入れる。**
>
> ```json
> {
>   "permissions": {
>     "deny": [
>       "Bash(git reset --hard*)",
>       "Bash(git -C * reset --hard*)"
>     ]
>   }
> }
> ```
>
> PowerShell 経由も塞ぐなら次を足す。
>
> ```json
> {
>   "permissions": {
>     "deny": [
>       "PowerShell(git reset --hard*)",
>       "PowerShell(git -C * reset --hard*)"
>     ]
>   }
> }
> ```
>
> これは **Claude Code のセッション内で Claude 自身が実行すること**を禁じる設定であって、**ランチャーがシェルスクリプトとして実行することは対象外**である（permissions は Claude のツール呼び出しにしか効かない）。
>
> **この deny は trust に依存せず必ず効く**（[§3-4](#sec-3-4)）。`allow` と違って入れ子リポジトリの不確定性（V7）の影響を受けないので、**統制として当てにしてよい**。
>
> この非対称は意図的なものであり、**混乱を招くのでチームに明示する**。「reset --hard は禁止」とだけ周知すると、ランチャーの実装がルール違反に見えてしまう。正しい周知は「**Claude に reset --hard をさせない。同期はランチャーが行う**」。
>
> **⚠ deny はコマンド文字列に対して効く。** ランチャーそのものを Claude に実行させると、`reset --hard` はスクリプトの内側で走るので **deny を通り抜ける**。[§5-7](#cautions) で「ランチャーを Claude に実行させない」を運用ルールとして置くのはこのためである。

#### 既存ランチャーとの関係

本チームには既にランチャー `start_claude_code.{ps1,sh}` が存在する。スクリプトの実体は、リポジトリのルートの `start_claude_code.{ps1,sh}` と、その部品を置く `.claude/launcher/` にあり、設計書は `base-dev-kit-for-cc`（C-BDK）の `docs/launcher/` にある。上の最小例は**それを置き換える提案ではなく、案C-1 で生じる差分を示すもの**である。

| 既存ランチャーの要素 | 案C-1 での扱い |
|---|---|
| 起動オプションの 4 分類判定木（`--add-dir` / `--settings` / `--mcp-config` 等の組み立て） | **不要になる。** 案C-1 は起動フラグを渡さない（[§5-1](#sec-5-1)） |
| `.claude/` の同期（clone / fetch / switch / reset） | **新規に必要。** 上の最小例の 1〜3 |
| env・秘匿値の取り回し | **従来方針を維持する。** **分類A（秘匿値）は OS 環境変数**に置き、共有リポの `settings.json` には入れない（[§3-4](#sec-3-4) の警告ブロック） |
| `.ps1` の BOM+CRLF・`.sh` の LF という改行／エンコーディング方針 | **そのまま適用する** |

**⚠ 同名ファイルの衝突に注意する。** 既存の `start_claude_code.ps1` と新しい同期処理を**どう統合するか（置き換え／併存／マージ）は作業指示者の判断事項**とし、本書では決めない（[§7-0](#sec-7-0)）。**無自覚に上書きすると、既存ランチャーが持っていた秘匿値の受け皿が失われ、秘匿値が共有 `settings.json` へ流れ込む退行を招く。**

**ランチャーの部品が共有クローンの内側に入る。** 既存ランチャーの部品（`.claude/launcher/` のスクリプトとテンプレート）は `.claude/` の下にある。案C-1 では `.claude/` が共有リポのクローンになるので、部品は共有リポで配ることになり、ルートのランチャーは「同期した直後に、同期された部品を読む」順序で動く。個人ごとの実体ファイル（`.claude/custom.env`・`.claude/option-settings.*`）は、共有リポ側の `.gitignore` に入れておけば `reset --hard` で消えない（`settings.local.json` と同じ扱い＝[§5-5](#mirror)）。部品をこのまま `.claude/launcher/` に置くか、`.claude/` の外へ出すかは、既存ランチャーの扱い（[§7-0](#sec-7-0)）と一緒に決める。

**`.sh` 版の要否も判断する。** 既存ランチャーは `.ps1` / `.sh` の両対応である。案C-1 でも WSL・macOS・Linux のメンバーがいるなら `.sh` 版が要る（処理内容は同一で、`$LASTEXITCODE` の代わりに `$?` を見る）。

<a id="cautions"></a>

### §5-7 運用上の注意

**起動と切替**

- **起動は必ず作業リポジトリのルートから行う。** サブディレクトリから起動すると **`.claude/settings.json` が読まれない**（`settings.json` の探索だけは親へ遡らない＝[§3-1](#sec-3-1)）。`CLAUDE.md` と skills はロードされるのに `permissions` だけが効かない、という分かりにくい状態になる。ランチャーの先頭で `Set-Location $PSScriptRoot` する（[§5-6](#sec-5-6)）
- **ブランチ切替はセッション開始前に行う。** 起動後に切り替えても反映されない（**要再起動**）。ランチャーで自動化しつつ、チームにも周知する
- **statusline に `.claude/` の現在ブランチを表示する。** 作業リポジトリのブランチとは別物なので、取り違えると「なぜこの指示が効かないのか」が分からなくなる。**ただしこれは万能ではない** —— ランチャーが `switch` の失敗を検査していないと、**ブランチ名は正しいまま中身だけが別物になる**（[§5-6](#sec-5-6) の実測）

**資産の置き方**

- **最初からブランチを細分化しない。** MECE に割り切れない作業は**親ブランチに寄せる**のが基本。context 消費量が実際に問題になってから分ける（分割の効果は `CLAUDE.md` と `paths:` なし `rules/` にしか効かない＝[§4-1](#sec-4-1)）
- **hooks は原則 `main` に置く。** ブランチごとに hooks を変えると、切替直後・trust 前に走る（[§3-4](#sec-3-4)）ため事故が見えにくい
- **`.claude/` を作業リポジトリの `.gitignore` に入れる。**【実測】入れておけば作業リポの `git status` は完全にクリーンなままになる

**統制**

- **ランチャーを Claude に実行させない。** `permissions.deny` は**コマンド文字列**に対して効くので、`reset --hard` がランチャーの内側で走ると deny を通り抜ける（[§5-6](#sec-5-6)）。同期はメンバー自身がランチャーを起動して行う
- **hooks・スクリプトの変更は 2 名レビューを必須にする。** 共有 `.claude` リポジトリの hooks は **trust 前でも全メンバーの端末で実行される**（[§3-4](#sec-3-4)）。実行されるコードと同じ扱いにする
- **force-push を許可するのは作業種別ブランチだけにする。** `main` はリモートで保護し、変更は PR 経由にする。**`main` は rebase の土台であって rebase 対象にならない**ので（[§5-4](#sec-5-4)）、保護しても rebase 運用は壊れない
- **メンバーの CLI の版をそろえる。** `"attribution": false` を含む settings ファイルは、その値の形を知らない旧い CLI が**ファイルごと読み飛ばす**（v2.1.281 の changelog）[\[51\]](./結論・構成案【別紙】出典一覧.md#ref-51)。共有の `settings.json` が読み飛ばされると、`permissions.deny` も含めて全部が効かなくなる。ほかの値で同じことが起きるかは確かめていないが、共有の `settings.json` に新しいキーや値の形を入れるときは、メンバーの CLI の版の下限を決め、旧い版で読めることを確かめてからにする
- **メンテナーの交代手順を決めておく。** force-push 権限を持つのが 1〜2 名という前提が崩れると、rebase 運用そのものが破綻する

### §6-2 各案を採らない理由

**現状維持（submodule / 複製）**
共通資産の実体が複数になり、submodule のピンがリポジトリごとにずれる。**「どのリポジトリが最新の規約で動いているか」が誰にも分からなくなる**のが最大の問題。作業種別ごとの出し分けは端から不可能。

**案A（`--add-dir <Share>` で共有ディレクトリを参照する）** —— **何がロードされるのかの詳細は [付録 2](./結論・構成案【別紙】付録.md#appendix-b)**
致命的なのは **`permissions` が `--add-dir` では届かない**点。`<Share>` の `settings.json` からは `enabledPlugins` / `extraKnownMarketplaces` の 2 キーしか読まれない [\[19\]](./結論・構成案【別紙】出典一覧.md#ref-19) ため、`deny` を効かせるには `--settings <Share>/.claude/settings.json` を別途渡す必要がある。つまり**ランチャーを経由しない素の `claude` 起動では `deny` が一切効かない**。さらに `--add-dir` の例外ロード範囲は版ごとに広がっており（skills のみ → ＋subagents → ＋commands）、**「何がロードされるか」が CLI の版に従属する**。加えて、trust が及んでいないフォルダを `--add-dir` で足すと trust を尋ねられ（v2.1.326 以降）、追加ディレクトリの `extraKnownMarketplaces` は、そのディレクトリの trust を保存するまで読まれない [\[47\]](./結論・構成案【別紙】出典一覧.md#ref-47)。案C-1 はこの従属をまるごと消す。

**案A'（D-11: `<Common>` を `--add-dir` にする逆転案）** —— **不採用（2026-09-14 決定）**
案A の変種で、作業リポジトリを主・共通資産を追加ディレクトリにする向きを逆転させ、共通資産側を主にする案。案A の起動フラグ依存と `permissions` 二重化をそのまま引き継ぐため、案C-1 が成立するなら採る理由が無い。**ドラフトは [`drafts/D-11_パターン2逆転案_改訂ドラフト.md`](../../reports/01.配布・統制方針調査/drafts/D-11_パターン2逆転案_改訂ドラフト.md) に凍結保存**する。

**案B（機能資産を層2 plugin へ集約する）** —— **併用する。対立しない**
案C-1 と排他ではない。**リポジトリ固有の機能資産は plugin に寄せる**のが案C-1 の推奨でもある（[§5-2](#assignment)）。ただし **`CLAUDE.md` / `rules` / `permissions` は plugin で運べない**（[§2-2](#matrix) ②）ため、plugin だけでは設計が閉じない。

plugin を併用する際の注意が 3 点ある。

- **marketplace を宣言しただけでは、外部ソースの plugin は install されない。** project の `settings.json` が `enabledPlugins` で有効化していても、GitHub リポジトリや npm パッケージ由来の plugin は**メンバーが `claude plugin install` するまでロードされない**（それまで `/plugin` の Errors タブに `isn't installed here` と表示される）[\[32\]](./結論・構成案【別紙】出典一覧.md#ref-32)。install はクローンごとに要る（`--scope user` なら全プロジェクトに効く）。marketplace の中を相対パスで指す plugin は、install 無しでロードできる場合がある。**「clone すれば即動く」は成り立たない**ので、ランチャーか onboarding 手順に install を組み込む（`claude plugin install <name>@<marketplace> --scope project`。v2.1.292 以降は `--marketplace <ソース>` を付けると marketplace の追加と install を 1 コマンドで済ませられる [\[51\]](./結論・構成案【別紙】出典一覧.md#ref-51)）
- **ネットワーク前提を外したいなら `archive` / `command` ソースか `@skills-dir` 型を検討する。** `archive` は HTTPS 配布の zip を `sha256` で pin でき、`command` の link mode は**キャッシュへコピーせずその場で使う**（link mode は Windows では使えない）[\[33\]](./結論・構成案【別紙】出典一覧.md#ref-33)。また **個人かプロジェクトの skill フォルダに `.claude-plugin/plugin.json` を置くだけで `<name>@skills-dir` という plugin になり**、marketplace も install も不要のまま agents / hooks / MCP をバンドルできる（**project の `.claude/skills/` では workspace trust の承認が先に要る**）[\[6\]](./結論・構成案【別紙】出典一覧.md#ref-6)
- **`@skills-dir` 型の plugin は、層3 の設定によってエラー無しで読み飛ばされる。** managed settings が `strictPluginOnlyCustomization` でどれか 1 種類でも制限しているか、marketplace を制限していると、ロードされない [\[52\]](./結論・構成案【別紙】出典一覧.md#ref-52)。層3 を敷いた配布先へ配るなら、marketplace 経由の plugin にする

**案C-2（`.claude/` を submodule にする）**
`.claude/` を git submodule として作業リポジトリに登録する案。ブランチ切替はできるが、**作業リポジトリ側に submodule のピンがコミットされる**ため、「`.claude/` の更新が作業リポジトリのコミット履歴を汚す」「ブランチを切り替えるたびに作業リポ側で差分が出る」という問題が戻ってくる。**gitignore された素の clone にすれば両方消える**（【実測】作業リポの `git status` は空のまま）。

**案D（層3 managed settings で強制する）** —— **組織に IT 統制基盤があるなら併用**
案C-1 と排他ではない。**上書きを防げるのは層3 だけ**なので、強制が要る組織は重ねる（[§4-2](#sec-4-2)）。ただし層3 はチームではなく組織の持ち物であり、チーム単独では選べない。

**`rules/` の symlink 共有**
外部 import の承認（対話セッションの開始時のダイアログ。1 プロジェクトにつき 1 回）が要り、**承認後も `paths:` 付き rule はロードされない**[\[16\]](./結論・構成案【別紙】出典一覧.md#ref-16)。共有手段としては穴が 2 つある（[§3-3](#sec-3-3)）。

> **その他、検討したうえで配布設計の柱から外した経路**（claude.ai 同期 skill・Organization settings > Plugins・`--plugin-dir` / `--plugin-url`・`~/.claude/` への配布・`pluginConfigs` の commit・submodule 化）は **[付録 3](./結論・構成案【別紙】付録.md#appendix-c)** にまとめてある。

<a id="sec-7-1"></a>

### §7-1 共有 `.claude` リポジトリを立てる

1. 新規リポジトリを作る（例: `<org>/shared-claude`）。**中身は `.claude/` の中身そのもの**（`CLAUDE.md` / `rules/` / `skills/` / `settings.json` … をリポジトリ直下に置く。`.claude/` という階層は作らない）
2. **`.gitignore` に `settings.local.json` を入れる**（[§5-5](#mirror) の警告）
3. 現行の共通資産を `main` ブランチへ移す。**この時点ではブランチを分けない**
4. リモートで**メンテナーの force-push を許可**する設定にする（branch protection で禁止されていないことを確認）

<a id="sec-7-2"></a>

### §7-2 ブランチを切る（必要になってから）

1. 「このブランチでしか要らない」と**実際に判断できた資産**だけを対象にする
2. `git switch -c <group>/base main` → 資産を移動 → commit
3. `git switch -c <group>/<作業種別> <group>/base` → 同上
4. **[§5-3](#sec-5-3) の命名規約を守る**（親名をそのままブランチ名にしない）
5. **push する前に、検証用リポジトリで対象ブランチを clone して確認する。** 空のリポジトリを作り、その `.claude/` として対象ブランチを clone し、**対話セッションを起動して `/context` で何がロードされているかを目視する**。skill が期待どおりロードされているか・`CLAUDE.md` の内容が意図どおりかを見る

> **⚠ 02 編手順書の「方法A / 方法B」は、そのままでは案C-1 に当てはまらない。** 同手順書の **方法A は `<Share>` そのものの中で起動する**スモーク確認、**方法B は別の作業リポから `--add-dir` で `<Share>` を結合する**検証である（[§2](../../reports/02.配布物の開発・テスト/02.Marketplace外資産編/Marketplace外資産_開発・テスト_手順書.md) / [§3](../../reports/02.配布物の開発・テスト/02.Marketplace外資産編/Marketplace外資産_開発・テスト_手順書.md)）。案C-1 は**共有リポジトリの内容が作業リポジトリの `.claude/` として実体で存在する**形なので、**トポロジがどちらとも違う**。
>
> 流用できるのは**検証の中身のほう**である —— [§4 ロード・適用の検証コマンド早見](../../reports/02.配布物の開発・テスト/02.Marketplace外資産編/Marketplace外資産_開発・テスト_手順書.md)、[§5 クリーン隔離テスト](../../reports/02.配布物の開発・テスト/02.Marketplace外資産編/Marketplace外資産_開発・テスト_手順書.md)、[§6 公開前の必須コマンドと落とし穴チェックリスト](../../reports/02.配布物の開発・テスト/02.Marketplace外資産編/Marketplace外資産_開発・テスト_手順書.md) はそのまま使える。**トポロジの作り方だけを上記 5. に読み替える。** 手順書側の追随は [§8-3](#sec-8-3) D-13 で扱う。

> **`main` を更新したときの検証範囲**: `main` の変更は**全ブランチへ rebase で波及する**（[§5-4](#sec-5-4)）。したがって `main` を触ったら、**代表として各系列の葉ブランチを 1 つずつ検証する**（`java/ut`・`python/coding` など）。全ブランチを毎回見る必要はないが、**`main` だけ見て済ませてはいけない** —— 系列ブランチ側の資産と衝突する変更は、`main` 単体では見えない。

<a id="sec-7-3"></a>

### §7-3 作業リポジトリ側を切り替える

各作業リポジトリで:

1. 既存の `.claude/` を退避する
   - **通常のディレクトリの場合**: `git mv .claude .claude.bak`
   - **submodule の場合**（現行の C-BCP がこれ）: **`git mv` だけでは submodule 登録が外れない。** 次の順で外す

     ```bash
     git submodule deinit -f .claude
     git rm -f .claude              # .gitmodules と index から除去
     rm -rf .git/modules/.claude    # 内部メタデータの削除
     git commit -m "chore: .claude の submodule 登録を解除"
     ```

2. `.gitignore` に `.claude/` を追加して commit
3. **リポジトリ固有だった資産を仕分ける**:
   - 指示文 → ルート `CLAUDE.md` へ移す
   - skill / agent / hooks → plugin 化するか、共有リポの適切なブランチへ移す
   - MCP → root `.mcp.json`（既にそこにあるはず）
4. `git clone --branch main <shared-claude> .claude`
5. ランチャー `start_claude_code.ps1` を配置して commit（[§5-6](#sec-5-6)。**既存ランチャーがある場合は [§7-0](#sec-7-0) (a) の判断に従う**）
6. **ルート `CLAUDE.md` に `.claude/` の由来を 1 行書いておく**（推奨）。例: 「`.claude/` は共有リポジトリ `<org>/<shared-claude>` のクローンで、本リポジトリでは gitignore されている。直接編集しない。更新は `start_claude_code.ps1` が行う」。**これが無いと、後から参加したメンバーが `.claude/` を普通のディレクトリだと思って編集し、次の同期で失う**
7. 動作確認後、`.claude.bak` を削除

<a id="sec-7-4"></a>

### §7-4 チームへの周知（最低限これだけ）

- **起動はランチャー経由**。素の `claude` でも動くが、`.claude/` が古いまま使われる。**初回はそもそも `.claude/` が存在しない**（まだ clone されていない）ので、素の `claude` では共有資産が一切ロードされない
- **起動は作業リポジトリのルートから**。サブディレクトリから起動すると `permissions` が効かない（[§3-1](#sec-3-1)）
- **ブランチを切り替えたら Claude Code を再起動する**
- **`.claude/` は編集しない**。直したいことがあればメンテナーへ依頼する（ローカル変更があるとランチャーが止まる）
- **個人設定は `.claude/settings.local.json` に書く**。**このファイルが `reset --hard` で消えないことは実測済みで、断定してよい**（[§5-5](#mirror)）
- **`reset --hard` は Claude にはさせない。同期はランチャーがやる**（[§5-6](#sec-5-6) の非対称）。**共有 `settings.json` に deny を入れておく**（同節にスニペット）
- **秘匿値は OS 環境変数に置く。** 共有 `.claude/settings.json` の `env` には書かない（[§3-4](#sec-3-4)）
- **初回起動時に trust ダイアログが 2 回出る可能性がある**（作業リポジトリと、入れ子リポジトリである `.claude/`）。**両方承認する**。文言は V7 の確認結果で確定する（[§8-2](#sec-8-2)）

> **⚠ この周知のうち、確度が違うものが混じっている。**
>

## §8 確認できない点・推測領域

ガバナンス設計上、根拠が公式ドキュメントに無く推測に留まる点、および未検証の点を明示する。

<a id="sec-8-1"></a>

### §8-1 公式に記載が無い（推測領域）

- **条件付きロードの発火の条件**は、rule とサブディレクトリの `CLAUDE.md` については公式の記述 [\[15\]](./結論・構成案【別紙】出典一覧.md#ref-15)[\[12\]](./結論・構成案【別紙】出典一覧.md#ref-12)[\[44\]](./結論・構成案【別紙】出典一覧.md#ref-44) と本書の実測（[§3-2](#conditional)）が合っている。**サブディレクトリの skills について、公式は "reads or edits" としか書いておらず** [\[7\]](./結論・構成案【別紙】出典一覧.md#ref-7)、Bash コマンドで発火しないことは本書の実測だけが根拠である。**発火の条件は CLI の版で変わってきたので、版が上がったら測り直すこと。** 変わっても案C-1 は壊れない（条件付きロードに依存していないため）。「保証が要る出し分けには使えない」という判断の理由のうち、[§3-3](#sec-3-3) の 1 と 2 は版に依存し、3 は依存しない
- `.claude/` を**入れ子の git リポジトリ**にする構成を、公式ドキュメントは**配布手段としては扱っていない**。ただし**入れ子リポジトリの存在自体には明示的な言及があり**、workspace trust の単位は「入れ子になった git リポジトリ（submodule など）を除いた git リポジトリのルート」と定義され、入れ子リポジトリには**対話セッションで別途 trust ダイアログが出る**とされている [\[23\]](./結論・構成案【別紙】出典一覧.md#ref-23)。つまり**「言及が無い」のではなく「trust の扱いが明示されている」**。ロードされること自体は[§3-1 の実測](#sec-3-1)で確認済みだが、**`permissions.allow` が実際に適用されるかは未確認**（V7＝[§8-2](#sec-8-2)）。**CLI の版が上がったら再測すること**
- `rules/` を **plugin 単体**でそのまま運ぶ仕組みは公式に記載が無い（plugin の正規コンポーネントに rules は無い）
- 3 チャネルを結合する scaffold / onboarding スクリプトの公式手順は無い（運用設計＝推測領域）
- file-based `managed-settings.json`（MDM / plist / registry 配置）のプラン非依存は、ファイル機構の性質からの**推定**で原文に明示は無い。**server-managed（admin console 経由）が Team/Enterprise 必須**である点は原文明記
- **公式ドキュメント以外の事例調査は行っていない。** 本書の「単一の既製ベストプラクティスは存在しない」（[§0](#summary) 問2）は、**公式ドキュメントが記載する配布機構を全経路棚卸しした範囲での結論**である。コミュニティの運用事例・OSS の実装パターン・他社事例は調査対象に含めていない

#### V7 の再現手順（所要 3 分・**対話セッションが必要**）

**目的**: 作業リポジトリを trust したとき、入れ子クローンである `.claude/` の `settings.json` の `permissions.allow` が適用されるかを判定する。**`claude -p` では trust ダイアログが出ない** [\[23\]](./結論・構成案【別紙】出典一覧.md#ref-23) ため、この検証は非対話（`claude -p`）では行えない。

1. 空のディレクトリを作り `git init` する（＝作業リポジトリ）
2. その中に `.claude/` として共有リポジトリ相当を用意する（別途 `git init` したリポジトリでよい）。作業リポの `.gitignore` に `.claude/` を入れる
3. `.claude/settings.json` に、**それ以外は何も許可しない**形で allow を 1 つだけ置く

   ```json
   { "permissions": { "allow": ["Bash(echo TRUSTPROBE:*)"] } }
   ```

4. **作業リポジトリのルートから対話セッションを起動**し、trust ダイアログを承認する。**`.claude/` について 2 枚目のダイアログが出るかどうかも記録する**（公式の記述どおりなら出る＝[§3-4](#sec-3-4)）
5. `echo TRUSTPROBE-OK` を実行させる
   - **許可プロンプトが出ずに実行された → `allow` は適用されている（V7 ＝ 可）**
   - **許可プロンプトが出た → `allow` は届いていない（V7 ＝ 否）**。stderr に `this workspace has not been trusted` が出ていないかも確認する

**V7 ＝ 否 だった場合の代替手段**（いずれも案C-1 自体は維持できる）:

| 代替 | 内容 | 代償 |
|---|---|---|
| **(a)** `.claude/` を個別に trust する | 各メンバーが `.claude/` についても trust を承認する（**公式の記述どおりならこれが既定の挙動**） | 初回セットアップのダイアログが 1 枚増える |
| **(b)** onboarding スクリプトで trust を書き込む | `~/.claude.json` の `projects["<パス>"].hasTrustDialogAccepted` を `true` にする（公式が案内している手段）[\[23\]](./結論・構成案【別紙】出典一覧.md#ref-23) | 承認の意味が形骸化するので、**スクリプトの内容自体をレビュー対象にする** |
| **(c)** `allow` を `settings.local.json` へ寄せる | **git が追跡していない `settings.local.json` の rule は、そのフォルダ自体を trust していなくても適用される**（親フォルダを trust した後か、`claude -p`・SDK の実行で。git が追跡している場合と `.claude` が symlink の場合は、リポジトリが供給した設定として扱われる） [\[23\]](./結論・構成案【別紙】出典一覧.md#ref-23) | **`allow` を一元配布できなくなる**（各自が設定する） |
| **(d)** `allow` を諦め、`deny` / `ask` だけを配る | `deny` / `ask` は trust 非依存で必ず効く | 許可の事前付与ができず、確認プロンプトが増える |

> **いずれの場合も `deny` / `ask` による統制は成立する。** V7 が否でも「**危険なコマンドを塞ぐ**」という目的は達成できる。影響を受けるのは「**あらかじめ許して確認プロンプトを減らす**」という利便性のほうである。
