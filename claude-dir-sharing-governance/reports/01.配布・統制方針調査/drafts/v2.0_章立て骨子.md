## 2. §3「どう届くか」の骨子（本書の中核）

**この章が v2.0 の存在理由。** 「置いたものが本当に載るのか」を機構ごとに明示する。

### 2-1. 無条件ロード（起動時に必ず載る）

| 資産 | 経路 | 実測 |
|---|---|---|
| 作業リポの `.claude/CLAUDE.md`・ルート `CLAUDE.md` | project スコープ | ✅ |
| 作業リポの `.claude/rules/*.md`（`paths:` **なし**） | project スコープ | ✅ |
| `.claude/settings.json`（**gitignore されていても**） | project スコープ | ✅ **2026-09-14 実測** |
| `.claude/skills/` `agents/` `commands/` | project スコープ | ✅ |
| `--add-dir <dir>` の `.claude/CLAUDE.md`（＋環境変数） | 追加ディレクトリ例外 | ✅ **2026-09-14 実測** |
| `--add-dir <dir>` の `.claude/rules/*.md`（`paths:` なし） | 同上 | ✅ **2026-09-14 実測** |

### 2-2. 条件付きロード（**発火契機が Read/Edit ツール限定**）

**⚠ 本書で最も重要な事実。** 公式は「Claude がそのパス配下のファイルを **reads or edits** したとき」としか書いておらず、**どのツールでの read かを限定していない**。実測では次のとおり。

| 先行操作 | `paths:` 付き rule | サブディレクトリの `CLAUDE.md` | サブディレクトリの `.claude/skills/` |
|---|:---:|:---:|:---:|
| **Read ツール** | ✅ | ✅ | ✅ |
| Bash ツールで `cat` | ❌ | ❌ | ❌ |
| Grep ツールで検索 | ❌ | ❌ | ❌ |
| `/reload-plugins` | — | — | ❌ |
| 起動時 `--add-dir <サブディレクトリ>` | — | — | ✅ |

**含意**: 条件付きロードを「必要なときだけ載せる」設計の基盤にしてはならない。**Bash 中心の探索をする運用では実質的に載らない**。

### 2-3. 設計原則（この章の結論）

> **届けたい資産は、条件ではなく「実体の置き場所」で分ける。**

## 3. §5「推奨構成（案C-1）」の骨子

### 3-1. リポジトリ構成

```txt
<共有 .claude リポジトリ>          ← メンテナー 1〜2 名が管理
├── main                         ← チーム全体で常に要る資産
├── java                         ← java リポジトリ群で共通（main から分岐）
│   ├── java/design
│   ├── java/coding
│   └── java/ut
└── python … （同様）

<作業リポジトリ>
├── .claude/                     ← 上記リポジトリのクローン（ブランチ切替で内容が変わる）
│                                   作業リポ側では .gitignore で除外
├── CLAUDE.md                    ← このリポジトリ固有の指示（.claude/ の外）
└── start_claude_code.ps1        ← ランチャー
```

### 3-2. 資産の振り分け

| 資産 | 置き場所 |
|---|---|
| チーム共通・作業種別共通 | 共有リポの **`main`** |
| 作業種別ごと | 共有リポの**対応ブランチ** |
| 作業リポジトリ固有の**指示** | 作業リポの**ルート `CLAUDE.md`** |
| 作業リポジトリ固有の**機能資産**（skill/agent/hooks） | **層2 plugin** |
| 個人設定 | `.claude/settings.local.json`（gitignore 済み） |

### 3-3. 親ブランチへの追従は `rebase`

- **理由**: 多段の親子関係で「全ブランチが先祖の更新を取り込めているか」を**ブランチグラフで視覚的に把握できる**。merge だとグラフがスパゲッティ化し反映漏れが検知しづらい
- **前提**: メンテナーは 1〜2 名の選任担当。force-push の衝突リスクが実質的に無い
- **多段は `rebase.updateRefs`**（git 2.38+／利用中の 2.46.0 で確認済み）で一括更新する
  - ⚠ 更新対象は「rebase 対象のコミットを指す**ローカル**ブランチ」のみ。**メンテナーは全ブランチをローカルに持った状態で実施する**
- ⚠ リモート側でこれらのブランチに **force-push 保護がかかっていないこと**を確認する

### 3-4. 消費側クローンは「読み取り専用ミラー」

```bash
git fetch --all --prune
git switch <ブランチ>
git reset --hard "origin/<ブランチ>"
```

- **`git pull --ff-only` は使えない**（2026-09-14 実測）。rebase でハッシュが変わると分岐扱いになり、`fatal: Not possible to fast-forward` で**毎回失敗する**。壊れはせず止まるだけだが、定常運用が回らない
- `reset --hard` は **gitignore 対象のファイルに触らない**ので、個人の `settings.local.json` は保護される
- **安全策**: `reset --hard` の前に `git status --porcelain` を確認し、ローカル変更があれば警告する（無人実行時は中断）
- **detached HEAD 方式は採らない** —— `reset --hard` を避けられるがブランチ名が `HEAD` になり、statusline で作業種別が見えなくなる

### 3-5. ランチャーの責務

1. 共有クローンの存在確認（無ければ clone）
2. `fetch` → `switch <ブランチ>` → `reset --hard`（ローカル変更があれば警告）
3. Claude Code を起動

**`--add-dir` / `--settings` / `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` は不要になる。**

> ⚠ 本リポジトリの共有 `settings.json` は `git reset --hard` を deny している。ランチャーはシェルスクリプト内で実行するため抵触しないが、**「Claude には触らせないが、ランチャーには許す」という非対称は文書に明記する**。

### 3-6. 運用上の注意

- **ブランチ切替はセッション開始前**。起動後に切り替えても反映されない（要再起動）。ランチャーで自動化しつつ、チームにも周知する
- **最初からブランチを細分化しない**。MECE に割り切れない作業は**親ブランチに寄せる**のが基本
- **statusline に現在のブランチを表示**して取り違えを可視化する

## 5. 本文執筆時の方針

- **必要な情報は本書内に保持する。** 公式に正本ができた表（skills の配置場所・層3 の統制面）も**参照で済ませず自前で持つ**。理由は ①情報が分散すると読みづらい ②公式の更新頻度が高く、一部だけ参照すると本文と静かに不整合を起こす
- そのかわり**各記述に BASE-D への出典アンカー（行番号付き）を必ず添える**。次回の再照合コストを下げるため
- **出典は BASE-D を主基準に振り直す**。BASE-A/B/C は既存出典の保全のために残す
- v1.2 は**時点記録として保持**し、削除しない（相互リンク保全）
