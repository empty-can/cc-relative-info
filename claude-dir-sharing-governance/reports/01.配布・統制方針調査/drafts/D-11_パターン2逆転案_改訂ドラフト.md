## 1. 提案の要旨

**現行の運用モデル**（実態）:

利用者は配布雛型 **C-BCP** を clone する。C-BCP の `.claude` は **C-BDC の submodule** なので、**チーム共通の `.claude` が物理的に各作業リポジトリに入る**。ランチャーもその中（`.claude/launcher/`）に含まれる。

**逆転案**:

作業リポジトリに置くのは**ランチャー一式のみ**とし、チーム共通の `.claude` は**共通リポジトリ `<Common>` を 1 つだけ `--add-dir` して参照**する。

```txt
【現行】                              【逆転案】
作業リポ/                             作業リポ/
├── .claude/          ← 共通の複製    ├── start_claude_code.ps1   ← ランチャーのみ
│   ├── CLAUDE.md                    ├── .claude/
│   ├── rules/                       │   ├── launcher/            ← ランチャー補助
│   ├── skills/                      │   ├── CLAUDE.md            ← このリポ固有のみ
│   ├── agents/                      │   └── rules/               ← このリポ固有のみ
│   ├── settings.json                └── （共通資産は置かない）
│   └── launcher/
└── （固有資産は共通の複製に混在）     <Common>/                    ← 各自 1 回 clone
                                      └── .claude/  ← 共通資産の唯一の実体
```

**ねらい**（作業指示者の提示内容）:

1. 複数リポジトリを `--add-dir` したくなるユースケースが発生しない。共通リポは「チームの作業というカットから見ても共通的なもの」だけになり、個別具体的な作業に必要な資産はその作業用リポジトリの `.claude` に既にあるはずだから。
2. 特定・限定的な作業でしか使わない資産（および対応する `CLAUDE.md` の記述）をチーム共通 `.claude` から外出しでき、**別の作業しかしないメンバーの Claude Code が無駄に消費していたコンテキストを減らせる**。

## 3. 技術的成立条件（一次ソースで検証済み）

> **`--add-dir` に渡すパスの仕様（変更なし・2026-08-29 再確認）**: `--add-dir` には **`.claude/` を内包する親フォルダ**を渡す。Claude Code は `<渡したパス>/.claude/skills/` 等を読むため、フォルダ名自体を `.claude` にすると `<Share>/.claude/.claude/` を探すことになり中身が読まれない（v1.2 §解決案 案C の「探索仕様（フォルダ名の落とし穴）」のとおり）。**2026-08-29 の公式更新でも `--add-dir` 例外ロード表・パス解決仕様に変更はない**（`f3e6841`→`f5de441` の差分で当該表は完全一致を確認）。

`--add-dir` だけでは足りない。ランチャーが以下 3 点を付与して初めて成立する。

| ランチャーが付与するもの | 運べる資産 |
|---|---|
| `--add-dir <Common>` | `skills/` ／ `commands/` ／ `agents/` ／ `enabledPlugins`・`extraKnownMarketplaces` |
| `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` | `CLAUDE.md` ／ `rules/` ／ `CLAUDE.local.md` |
| **`--settings <Common>/.claude/settings.json`** | **`permissions` ／ `hooks` ／ `env`**（`--add-dir` では絶対に載らない部分） |

3 番目が成立の鍵。以下を公式ドキュメントで確認した。

- `--settings` は settings precedence の**レベル2**（managed の下、project / local / user の上）
- **リスト系キーはスコープ間でマージされる**（公式が `permissions.allow` を例示）。したがって**共通 permissions と作業リポ固有 permissions は共存し、上書き事故は起きない**
- 同一イベントに合致した hooks は**全ソース分が実行される**
- `--settings` は `disableSideloadFlags` の対象外なので、**層3 併用下でも生き残る**（落ちるのは `--mcp-config` のみ・v1.2 §解決案 パターン2 の既知事項）

**運べないもの（残るギャップ）**:

| 資産 | 状況 |
|---|---|
| `output-styles/` | **どの経路でも運べない**。物理配置か `~/.claude/` のみ |
| MCP（`.mcp.json`） | `--mcp-config` は層3 下で起動拒否されうる。層2（plugin 同梱）か層3（`allowedMcpServers`）へ寄せる |
| `workflows/` `agent-memory/` | 層1 専用（マトリクス④）。`--add-dir` の例外ロード対象外 |

## 4. ⚠ 未解決の重大な制約 — background / agent-view セッション

**逆転案の成立を左右する最大の論点。採否判断の前に結論を出す必要がある。**

ランチャーが与えるものは、いずれも**そのプロセスから起動した foreground セッションにしか届かない**。

- `--add-dir` / `--settings` は**起動フラグ**。ランチャーを経由しない起動には付かない
- `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` はランチャープロセスの env。子プロセスにしか継承されない

一方、**background セッションはディレクトリ設定から構成を読む**。これは C-BDK ランチャー実装計画 §3 の警告としてだけでなく、**公式ドキュメントに明記された確定事実**である（2026-08-29 取込版で確認）。

> *"A background session reads its settings from the directory it runs in, the same as if you had started `claude` there."*

シェルから継承されるのは**プロバイダ関連の env に限られる**（`CLAUDE_CODE_USE_BEDROCK` / `CLAUDE_CODE_USE_VERTEX` / `ANTHROPIC_DEFAULT_*_MODEL` / `CLAUDE_CODE_EXTRA_BODY` / gateway の `ANTHROPIC_BASE_URL`）。**`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` はこのホワイトリストに含まれない。**

**同型の事例が 2026-08-29 の公式更新で追加された（Remote Control）**: `claude --settings <path> remote-control ...` のように `remote-control` 動詞より前に置いた global フラグ（`--settings` / `--setting-sources` / `--permission-mode` 等）は、**Remote Control が起動するセッションへ引き継がれない**。しかも新仕様では**黙って落とさず、Remote Control が起動自体を拒否する**（`<flag>` before `remote-control` is not carried over to the sessions Remote Control starts）。「ランチャーが与えたフラグは、別機構が起動するセッションには届かない」という構造が繰り返し現れており、**プラットフォームは「黙って劣化」より「起動拒否」へ寄せる方向**にある点も押さえておく価値がある。

**帰結**: 逆転案では、background / agent-view で走るセッションは**チーム共通の CLAUDE.md・rules・skills・permissions・hooks を一切持たずに動く**。現行のコピー配布ではディレクトリに実体があるため、この問題は起きない。

**⚠ 影響範囲は「セッションの起動経路」に限られる。同一セッション内の subagent は影響を受けない（2026-08-29 精査で確定）。**

**background subagent と background セッションは別物**である。前者は親セッションの**プロセス内**で動くため（permission prompt が親セッションに出る／`/subtask` の結果が同じ会話へ返る）、親が持つ `--add-dir` / `--settings` / env をそのまま共有する。**`Ctrl+B` による背景化も subagent をセッション内に留めたまま**であり、別セッションへは移らない。後者は**独立したフルの会話**（`/bg`・`claude --bg`・agent view からの dispatch・`/fork`）で、別プロセスとして起動する。

**⚠ 判定軸は「foreground / background」ではなく「起動時にフラグが付与されるか」である。** foreground / background の別は関係がなく、`-p` かどうかも関係がない。整理すると 3 群に分かれる。

**群A: 起動フラグを直接付与できる経路（ランチャーが担当できる ＝ 解決可能）**

| 経路 | 備考 |
|---|---|
| `claude`（対話・ランチャー経由） | 基本形 |
| **`claude -p`**（CI・スクリプト） | `-p` でも `--add-dir` / `--settings` は有効。**ランチャーを `-p` 対応させれば群A に統合できる**。ただし `-p` の既定 permission mode は全プランで Manual、**bare mode では `--add-dir` から skills しか載らない**（`commands/` `agents/` は skip） |
| `claude --bg` | 同上 |
| **`claude agents`**（agent view） | agent view は `--settings` / `--add-dir` / `--plugin-dir` / `--mcp-config` を**自身と dispatch 先セッションの両方へ引き継ぐ**。※ `--add-dir` と `--mcp-config` は `agents` の**後ろ**に置く（前に置くと `claude agents --json` が `unknown option` で失敗） |
| `claude --remote-control`（`--rc`）／ VS Code の `/remote-control` | 自分の対話セッションに RC を有効化するだけなので起動フラグはそのまま効く |

**群B: 親セッションから継承する経路（そもそも問題にならない）**

| 経路 | 根拠 |
|---|---|
| **同セッション内の subagent**（foreground / background / `Ctrl+B` 背景化 / `/subtask`） | 親のプロセス内で動く。permission prompt が親セッションに出る／結果が同じ会話へ返る |
| **dynamic workflows が起動する subagent** | セッションのアクティブ作業として扱われ、セッションを背景化すると一緒に移動する。**オーケストレータが直接起動した subagent と同じ** |
| **in-process teammate**（`teammateMode` の既定） | teammate の permission prompt も lead セッションに出る |

**群B-2: 背景化しても起動フラグが引き継がれる経路（公式明記・2026-08-29 確認）**

**`/bg`・`←` による背景化でも起動フラグは失われない。** 公式は *"Configuration flags from the original launch carry through to the backgrounded session, so its MCP servers, settings, and fallback model remain in effect"* と明記し、対象フラグを列挙している:

`--mcp-config` / `--strict-mcp-config` ／ **`--settings`** ／ **`--add-dir`** ／ `--plugin-dir` ／ `--fallback-model` ／ `--allow-dangerously-skip-permissions`

さらに **セッション中に `/add-dir` で追加したディレクトリも引き継がれる**。したがって当初 V1 として実測を要件に挙げた点は**公式記述で解決済み**であり、`/bg`・`←` は群A/B と同じ扱いでよい。

> **⚠ ただし環境変数は別**: 上記は「configuration **flags**」の話であり、`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` は**環境変数**なので、ランチャーの shell から export した値が背景化後のプロセスへ届く保証はない（background セッションがシェルから継承するのはプロバイダ関連 env のホワイトリストのみ）。
>
> **対策（設計に織り込むこと）**: この変数を**ランチャーの shell export ではなく `<Common>/.claude/settings.json` の `env` ブロックに書く**。`--settings` は背景化で引き継がれるため、変数も一緒に travel する。公式も settings ファイルの `env` について「higher-precedence settings files（project / local / `--settings` payload）の `env` エントリが勝つ」「保存すると実行中セッションにも再適用される」と記述している。→ 実測項目 V6。

**群C: フラグが届かない経路**

| 経路 | 状況 |
|---|---|
| **素の `claude`**（ランチャー不使用） | **なし**。**本枠組みの検討対象外とする（2026-08-29 作業指示者決定）** ―― 統制はランチャー起動時のみ設定される OTel サーバへのメトリクス送信と、コスト追跡基盤（LiteLLM）の記録との突合で別途行う。**メトリクスが来ないのにコストが発生している利用者＝ランチャー未経由**として利用者単位で検出できる |
| **split-pane の teammate**（`teammateMode` が `tmux` / `iterm2` / `auto`） | **未確認**。別ペインで別プロセスとして起動するためフラグが渡るかは公式に記載がない。agent teams は実験的機能で既定オフ（`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` が要る）・`-p` では生成されないため、**当面は検討対象外**（→ V5） |

**結論: §4 は D-11 の障壁ではなくなった。** 当初「background / agent view / `-p` がすべて共通資産ゼロで動く」「D-11 の成否を分ける」と記したのは**過大評価であり、ここで全面的に訂正する**。実際に対処が要るのは **`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` を settings の `env` ブロックへ移す**という設計上の一手だけで、**これは 2026-08-29 に CLI v2.1.251 で実測し成立を確認済み**（§7 V6）。**§4 に未解決事項は残っていない。**

**緩和の方向（要検討）**:

1. **セキュリティ最小核だけは作業リポにも commit する**（`permissions.deny` 等）。deny はマージされるので重複しても害がない。ただしこれは「コピーをゼロにする」のではなく「**コピー範囲をセキュリティ最小核まで縮める**」案になる ―― 作業指示者の当初イメージ（作業リポにはランチャーだけ）への修正点。
2. background を使わない運用に限定する（現実的でない）
3. 層3（managed）で共通ガバナンスを配る（組織の統制基盤が前提。チーム単位では選べない）

### 5-1. v1.2 §解決案 層1系「層1 の配布パターン（運用形態）」

#### 現行（該当箇所の要旨）

3 パターンを並列に提示し、どれを主に据えるかの推奨は置いていない。

#### 改訂案

冒頭のリード文を差し替え、パターン1 と 2 の関係を明示する。

> **層1 の配布パターン（運用形態）**:
>
> 層1（commit／clone ベース）の資産を実際にチームへ届ける運用は、3 パターンに整理できる。**層2 で配れる機能資産は層2（Plugin/Marketplace）へ寄せ、本パターンは「層2 で配れない資産」を対象とする**（振り分けは §推奨）。起動オプションの全容は 付録B を参照。
>
> **⚠ パターン1 と パターン2 は「どちらを主に据えるか」で運用が大きく変わる（2026-08-29 追記）**。両者の対象は本来 排他的 ―― パターン1 は**そのリポジトリ固有の資産**、パターン2 は**リポジトリ横断で共通の資産**である。しかし実装上は「共通資産を各作業リポジトリへ複製する」形（配布雛型に共通 `.claude` を同梱する等）も成立してしまうため、**どちらの実体をどこに置くかを設計時に明示的に決めること**。両者の比較は下表のとおり。
>
> | | パターン1 主体（共通資産を各リポへ複製） | パターン2 主体（共通資産は `<Common>` に 1 つ） |
> |---|---|---|
> | 共通資産の更新伝播 | **N リポジトリ分の同期が要る** | `<Common>` で `git pull` 1 回 |
> | 作業リポの `.claude/` | 共通＋固有が混在 | **固有資産のみ**（コンテキスト削減に直結） |
> | 起動方法への依存 | **なし**（実体があるので必ず載る） | **ランチャー経由の foreground 起動が前提**。background / agent view / `claude -p` には届かない（→ §4） |
> | 初期セットアップ | clone 1 回 | clone 2 回（作業リポ＋`<Common>`） |
> | 強制力 | なし（各自が編集可） | なし（起動方法も各自任せ） |
>
> **本書の推奨**: 共通資産は**パターン2 に一本化**し、パターン1 は固有資産に限定する。ただし **`permissions.deny` 等のセキュリティ最小核だけは作業リポジトリにも commit して二重化する**（配列はマージされるため重複による害がなく、ランチャーを経由しない起動経路への保険になる）。

#### パターン1 の定義（改訂）

> - **パターン1（作業リポジトリに commit）**: 作業する Git リポジトリそのものに `.claude/` 資産を commit してチーム共有。**そのリポジトリ固有の資産に限定する**（そのプロジェクト専用の `CLAUDE.md`/`rules`/`settings.json` 等）。**リポジトリ横断で共通の資産をここへ複製しないこと** ―― 複製すると更新伝播が N 倍になり、かつ「その作業をしないメンバーのコンテキストを消費する」問題が発生する。共通資産はパターン2 で参照させる。**例外はセキュリティ最小核**（`permissions.deny` 等）で、これは起動経路に依存させないために意図的に二重化する。

#### パターン2 の定義（改訂）

> - **パターン2（共通リポジトリ `<Common>` を clone ＋ 起動オプションで参照）**: Claude Code の**チーム共通資産だけ**を一元管理する共通リポジトリ `<Common>` を各自が clone し、**起動ランチャーで起動オプションを付与して読み込ませる**。作業リポジトリに依らない**横断的・チーム共通**の資産のうち、**層2 で配れないもの**が対象。`<Common>` を clone しただけでは Claude は読まないため、**「clone ＋ 起動オプション」の二点セット**で初めて有効になる:
>   - CLAUDE.md / rules → `--add-dir <Common>` ＋ 環境変数 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`
>   - skills / commands / subagents → `--add-dir <Common>`（例外ロード。完全一覧は 付録B 正本表）
>   - permissions / hooks / env → `--settings <Common>/.claude/settings.json`（command-line precedence で project 等とマージ）
>   - MCP（`.mcp.json`）→ `--mcp-config <Common>/.mcp.json`（層3 下では起動拒否されうる。§既知事項）
>   - **`--add-dir` は 1 つで足りる**: 分割軸ごとに担当機構が異なるため、複数の `<Common>` を並べる必要は生じない。リポジトリ軸＝作業リポの `.claude/`、全員共通軸＝`<Common>`、**役割軸＝層2 plugin（install 単位）**、ファイル種別軸＝`paths:` frontmatter が担当する。
>   - ⚠ **`--add-dir` は資産種別を選べない**。ディレクトリを足せばその `.claude/` 配下の例外ロード対象が丸ごと載り、`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` も all-or-nothing である。したがって分割の単位原則は **「1 ディレクトリ ＝ 一緒に載ってよい資産の束」**。
>   - ⚠ **届く範囲はランチャー経由の foreground セッションのみ**。background セッション・agent view のセッションは ambient シェル env ではなくディレクトリ設定から構成を読むため、**共通資産が載らない**。この経路を使うチームは §4 の緩和策を併用すること。

#### パターン3 の定義（改訂・追記のみ）

> - **パターン3（別リポジトリから手動で作業リポジトリ直下へ移動）**: （現行のまま）…
>   - **パターン2 を主体にすると、パターン3 の重要度が上がる**。共通資産の到達手段がランチャーに一本化されるため、**ランチャーの配布が失敗すると共通資産が丸ごと載らない**。パターン1 主体であれば実体が repo にあるので degrade で済むが、パターン2 主体では全損になる。ランチャーの配布・更新経路は単一障害点として設計すること。

### 5-4. v1.2 付録B「ランチャー集約の例」

#### 現行

```bash
claude \
  --add-dir <Share> \
  --settings <Share>/.claude/settings.json \
  --mcp-config <Share>/.mcp.json
```

#### 改訂案

> **ランチャー集約の例**（パターン2 主体構成の実体）:
>
> ```bash
> claude \
>   --add-dir "$COMMON_DIR" \
>   --settings "$COMMON_DIR/.claude/settings.json"
> # MCP は層2（plugin 同梱）か層3 へ寄せる。--mcp-config は層3 下で起動拒否されうる
> ```
>
> **`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` はランチャーから export しない。** `<Common>/.claude/settings.json` の `env` ブロックに置く:
>
> ```json
> { "env": { "CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD": "1" } }
> ```
>
> 理由: `/bg`・`←` で背景化したセッションへ**引き継がれるのは configuration flags であって環境変数ではない**。`--settings` は引き継がれるため、変数を settings 側に置けば背景化後も維持される。**この方式は 2026-08-29 に CLI v2.1.251 で実測済み**（シェルの export を除去した対照実験で、`--settings` 経由の `env` ブロックだけで `<Common>` の CLAUDE.md がロードされることを確認。→ §7 V6）。
>
> `COMMON_DIR` は**起動オプション設定ファイル**（`.claude/option-settings.*`・利用者がテンプレートからコピー作成し Git 追跡しない）に記述する。秘匿情報ではないため `custom.env`（分類A 秘匿の受け皿）ではなく `option-settings` が正しい置き場所。**未設定なら `--add-dir` を付与しない**設計とし、`<Common>` を持たない利用者でも起動できるようにする。
>
> **hooks は `<Common>` の `settings.json` に置かない。層2（plugin）で配る。**（2026-08-29・作業指示者の提案を採用し、当初案を全面差し替え）
>
> **問題の所在**: hooks の設定を `<Common>/.claude/settings.json` に置くと、**スクリプトの所在が「作業リポジトリ側」に解決されてしまう**。実資産で確認したところ、書き方の違う 2 経路がいずれも同じ結果になる:
>
> | 対象 | hooks の書き方 | 解決先 |
> |---|---|---|
> | 本リポ `cc-relative-info` の共有 `settings.json` | `bash .claude/hooks/pre-task-reminder.sh` 等 | **cwd 相対**＝作業リポジトリ |
> | C-BDC（配布される `.claude` 本体）＝ C-BDK も同一 | `command: "python"` ＋ `args: ["${CLAUDE_PROJECT_DIR}/.claude/hooks/bat_cp932_guard.py", …]` | **`${CLAUDE_PROJECT_DIR}` は "stable project root"** で `--add-dir` の増減により変わらない＝作業リポジトリ |
>
> **根本原因は「hooks を層1 の設定データとして運ぼうとしたこと」**。設定（`settings.json`）とスクリプト実体が別の場所に分かれるため、どちらの書き方でも `<Common>` を指せない。**`--settings` のファイル位置を指す変数は存在しない**（利用できるのは `CLAUDE_PROJECT_DIR` / `CLAUDE_PLUGIN_ROOT` / `CLAUDE_SKILL_DIR` / `CLAUDE_CONFIG_DIR` 等で、いずれも `<Common>` を指さない）。
>
> **解決: チーム共通 hooks は plugin として配り、`${CLAUDE_PLUGIN_ROOT}` で参照する。**
>
> - **plugin は設定とスクリプトを 1 単位に束ねる**ので、`${CLAUDE_PLUGIN_ROOT}/scripts/<name>` が常に解決される。公式は `${CLAUDE_PLUGIN_ROOT}` を **「hook コマンドと MCP server config で plugin のインストールディレクトリ内のファイルを参照するための変数」**と明記しており、`hooks/hooks.json` は `claude plugin validate` の検査対象でもある。**Windows / PowerShell の shell-form コマンド内でも v2.1.198 以降は置換される**
> - **プロジェクト固有の hooks は各作業リポジトリの `.claude/settings.json` に置き `${CLAUDE_PROJECT_DIR}` で参照する**。実体が同じリポジトリにあるので正しく解決される
> - **`enabledPlugins` と `extraKnownMarketplaces` は `--add-dir` の例外ロード対象**なので、`<Common>/.claude/settings.json` にこの 2 キーを書けば**プラグインの有効化情報まで `<Common>` が運べる**
>
> **結果、`--settings` に残る役割は `permissions` と `env` だけになり、hooks を含まないためパス展開が不要になる。ランチャー側のケアは要らない。**
>
> これは v1.2 の既存推奨（**機能・拡張資産＝skills / commands / **hooks** / MCP / output-styles は層2 へ集約**）とそのまま整合する。**「hooks を `<Common>` の settings.json が運ぶ」という当初の前提自体が誤りだった**と整理できる。
>
> **前提・代償**:
>
> 1. **層2 レールの立ち上げが前提**。C-MKT に `marketplace.json` が無い（D-2 実測）ため、**D-5（リリースチャネル）とセットで動かす**必要がある
> 2. **plugin は自動 install されない**。v2.1.195 以降、marketplace は無プロンプトで追加されるが**外部ソースの plugin は install を促されず「未インストール」報告のみ**。初回セットアップに `claude plugin install` の一手が残る（`CLAUDE_CODE_PLUGIN_SEED_DIR`＝案B''' で緩和可）
> 3. **trust 承認前は `extraKnownMarketplaces` が使われない**（ダイアログも出ない）
> 4. **強制力は依然として弱い**。利用者が plugin を無効化できる（強制は層3 のみ、という結論は不変）
> 5. **混同注意**: 「plugin 経由の subagent では frontmatter の `hooks` が無視される」は**別論点**。plugin レベルの hooks（`hooks/hooks.json`）はこの制約を受けない

## 8. 参考：分割軸と担当機構（D-8 案3' と共通）

| 分割軸 | 例 | 担当機構 | `--add-dir` の追加 |
|---|---|---|---|
| リポジトリ軸 | このリポ特有の運用ルール | 作業リポの `.claude/`（層1） | 不要 |
| 全員共通軸 | 命名規約・共通 permissions | `<Common>` を 1 つ `--add-dir` | **1 つで足りる** |
| **役割軸** | リリース担当だけが要る手順 | **層2 plugin**（install 単位） | **不要** |
| ファイル種別軸 | `*.py` を触るときだけ | `paths:` frontmatter（rules・skills 両方が持つ） | 不要 |

**「作業が MECE に割れない」ケースはリポジトリ軸の内側の話**であり、`paths:` とサブディレクトリ `CLAUDE.md`（読んだときだけロードされる）で解ける。役割軸を層2 plugin が吸収するため、複数 `--add-dir` は必要にならない。

## 9. 参考：機構別の context コスト（D-8 案3' の E3 と共通）

| 資産 | 常時載るもの | 外出しの効果 |
|---|---|---|
| **`CLAUDE.md`** | **全文**（毎リクエスト。prompt-cache されるがコンテキストは占有） | **大** |
| `rules/` | `paths:` 該当時のみ | 中（既に条件付きロード） |
| `skills/` | **name ＋ description のみ**（本文は選択時のみ） | 小。ただし**数が多いと description が自動で切り詰められ選択精度が落ちる**ため、「context 削減」ではなく**「選択精度の維持」**として価値がある |
| `agents/` `commands/` | 一覧行のみ | 小 |
