### C-1. §5-6 ランチャースクリプトにエラーハンドリングが無く、`switch` 失敗が「静かなブランチ破損」に直結する

**観点**: 完了条件明瞭性

#### C-1. 問題点

* **概要**: `start_claude_code.ps1` が `git clone` / `git switch` / `git reset --hard` の終了コードを一切検査していない。`switch` が失敗しても `reset --hard "origin/$Branch"` が続けて実行される。
* **問題点**:
  1. Step 3（`fetch` → `switch` → `reset --hard`）の 3 コマンドが無条件で連続実行され、`switch` の失敗を検出する分岐が無い
  2. Step 1（`git clone`）の失敗も検査されない
* **影響**:
  1. `switch` 失敗後に `reset --hard` が走ると、**現在チェックアウトされているブランチが、名前はそのままで別ブランチの内容に上書きされる**。v2.0 §5-7 が取り違え防止策として挙げている statusline は正しいブランチ名を表示し続けるため、**安全策が偽陰性になる**
  2. clone 失敗を検査しないため、不完全な `.claude/` のまま `claude` が起動しうる
* **詳細**:
  1. `switch` が失敗する典型例は、本書 §5-3 が実測で示した **D/F コンフリクト**そのものである
  2. PowerShell は外部コマンドの非ゼロ終了を終端エラーとして扱わない。`$ErrorActionPreference` の設定も `$LASTEXITCODE` の確認もスクリプト中に存在しない
  3. §5-5 の「`reset --hard` の前に `git status --porcelain` を確認する」はローカル変更による失敗だけをカバーし、D/F コンフリクト等による `switch` 失敗は未カバー
* **根拠**:
  1. v2.0 §5-6 のスクリプト全文に `$LASTEXITCODE` / `-ErrorAction Stop` / try-catch のいずれも存在しない
  2. v2.0 §5-3 の実測（`fatal: cannot lock ref 'refs/heads/java/design': 'refs/heads/java' exists`）が、まさに Step 3 の `switch` を失敗させうるシナリオ

##### C-1. レビューイからの回答・見解・補足（問題点）

* **指摘内容に対する同意の程度**: **全面的に同意する。**
* **判断材料の追加情報**:
  * **指摘の帰結を実測で再現した**（2026-09-14 / git 2.46.0）。`master` ブランチ上で `git switch does/not/exist` を実行（**exit 128**）し、終了コードを見ずに `git reset --hard origin/other` を続けたところ:

    ```text
        switch: fatal: invalid reference: does/not/exist
        switch の終了コード: 128
        reset: HEAD is now at bbffd4c other 版
        reset の終了コード: 0

      現在のブランチ: master
      asset.txt: other の資産（main には存在してはいけない）
      master の先頭: bbffd4c other 版
      origin/master の先頭: e159571 main 初版
    ```

    **ブランチ名は `master` のまま、中身が `other` で上書きされた。** ローカルの `master` が `origin/master` から乖離した状態になる
  * したがって本指摘は「起こりうる」ではなく「起こる」。**ラベルは CRITICAL が妥当**と判断する
  * 再現スクリプトは実測記録として本書へ反映する

#### C-2. 問題点
