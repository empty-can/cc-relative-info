### C1. §3 の実測は案C-1 を一意に選ばない —— §0「なぜこの形を選ぶのか（3 行で）」が結論を導いていない

**観点**: 論理整合性

#### C1. 問題点

* **概要**: §0 の 3 段論法は「条件付きロードは信頼できない → 実体の置き場所で分ける → ブランチ」で閉じているが、「その実体を**作業リポジトリの `.claude/`** に置く」理由が論証に入っていない。案C-1 を他案から分離している事実は §2-2 ② と §6-2 にあり、§3 ではない。
* **問題点**:
  1. §0 の 3 行は、切替機構として git ブランチを選ぶところまでしか言っておらず、**案A（`--add-dir <Share>`）を排除していない**。`<Share>` も git リポジトリにしてブランチを切り替えれば、同じ「実体の置き場所による出し分け」が成立する
  2. §6-1 の比較表は案A の「作業種別ごとの出し分け」を「困難（`paths:` が信頼できない＝§3-2）」としているが、**案A が `paths:` に依存しなければならない必然性は §2〜§4 のどこにも示されていない**。この行だけが §2〜§4 の事実から導けない
  3. 実際の決め手（§2-2 ②「チームだけでガバナンス資産を一元管理できる唯一の場所が P1」、§6-2「`<Share>` の `settings.json` からは 2 キーしか読まれない＝`permissions` が届かない」、§4-3 の層3 との衝突）が §0 に現れない

  1. §0 は「最初に読む場所」を提供する入口として設計されており、**ここだけ読む決裁者が妥当でない導出のまま結論を受け取る**
  2. 却下理由が事実から導けない行が 1 つ混じることで、比較表全体の信頼度が落ちる
  3. 「§3 が本書の中核」という位置づけも揺らぐ。§3 が支えているのは「条件付きロードに依存するな」までで、案C-1 の選択は §2・§6 が支えている
* **詳細**:
  1. §3-3 の結論「届けたい資産は、条件ではなく実体の置き場所で分ける」は正しいが、置き場所の候補は P1・P3・`--add-dir` 先の 3 つある。P1 を選ぶ論証は §2-2 ②（plugin では運べない）と §6-2（`--add-dir` でも運べない）の二段構えで初めて閉じる

* **根拠**:
  1. v2.0 §0「なぜこの形を選ぶのか（3 行で）」／§3-3 結論／§6-1 比較表の「作業種別ごとの出し分け」行／§6-2 案A の致命傷／§2-2 ② の注記

### C2. 入れ子 git リポジトリと workspace trust の関係が未検討で、実測はすべて `-p` のため原理的に検証できていない

**観点**: 仮説の妥当性

#### C2. 問題点

* **概要**: 公式は「trust は git リポジトリルートを鍵に保存され、**その中に入れ子になった git リポジトリは対象外**」と明記している。案C-1 の `.claude/` はまさにその入れ子リポジトリだが、本書はこの記述を取り込んでいない。さらに §3 の実測はすべて `claude -p` で行われており、`-p` は `permissions.allow` が適用されないモードである。
* **問題点**:
  1. BASE-D L81157: "Claude Code keys the trust on the git repository root, so the trust covers the whole repository **apart from any git repository nested inside it, such as a submodule**." —— 案C-1 の `.claude/` clone はこの例外に該当する形状である
  2. §3-4 は trust 表をそのまま引いているのに、直前の注記 L81180「The parent-folder column doesn't apply **inside a nested repository**」だけが落ちている。**案C-1 に最も効く 1 行**である
  3. 実測条件が `claude --model haiku -p`。公式表では `-p` は「folder never trusted」列で、`permissions.allow` は **"Not used"**（L81185）
  4. 実測した `settings.json` の `env` は trust 前でも実行される欄（L81184）である。「settings.json が読まれた」証拠にはなるが、**trust 依存部分が効く証拠にはならない**
* **影響**:
  1. 案C-1 の中核価値「チームの permissions を一元配布する」のうち、**`allow` の適用が対話セッションで確認されていない**。仮に入れ子リポ例外が効けば、共有リポの allow は trust ダイアログ承認まで使われず、メンバーは毎回許可プロンプトを踏む
  2. §6-1「素の `claude` 起動での `deny` が効く ✅」自体は成立する（deny/ask は trust 非依存＝L81153）。しかし表がこの非対称を書かないため、**読者は allow も同様に効くと読む**
  3. §8-1「`.claude/` を入れ子の git リポジトリにする構成について、公式ドキュメントに言及が無い」は**不正確**。少なくとも trust の節（L81157・L81180）には入れ子リポジトリの明示的な扱いがある
* **詳細**:
  1. 同じ節には `settings.local.json` について「tracked in git か `.claude` が symlink なら repository-supplied 扱いになり trust まで保留」（L81165）、「untracked なら trust 前でも適用」（L81170）という記述もある。案C-1 は共有リポで gitignore する設計なので untracked 側に落ちる見込みが高い。調べれば §8-2 V6 も同時に前進する
  2. 本書の執筆方針（必要な情報を本書内に保持する／各主張に出典アンカーを添える）に照らすと、trust 表だけ引いて入れ子リポジトリの注記を落とすのは方針違反にあたる
* **根拠**:
  1. BASE-D L81153（`allow`・`additionalDirectories` は trust 後に適用／`deny`・`ask` は非依存）
  2. BASE-D L81157（入れ子リポジトリは親の trust の対象外）
  3. BASE-D L81161（`-p` は trust ダイアログを出さず、親フォルダの trust も数えない）
  4. BASE-D L81180（親フォルダ列は入れ子リポジトリには適用されない）
  5. BASE-D L81165・L81170（`settings.local.json` の tracked / untracked による分岐）
  6. v2.0 §3-1・§3-2 の実測手法（すべて `-p`）／§3-4 の trust 表／§6-1 の deny 優位の主張／§8-1「公式に言及が無い」
