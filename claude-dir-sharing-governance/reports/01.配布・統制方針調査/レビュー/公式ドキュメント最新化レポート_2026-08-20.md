### 【方針判断】

#### D-4. 層1 body と plugin の「二重管理」を単一実体に畳めるか（案B'' の採否）

- **背景**: 配布計画 §4 判断 #1 は「同じ資産を層1 body としても plugin としても発行する（dual）」を採用している。
- **今回の所見**: v1.2 の **案B''（`@skills-dir` 型）** —— `<repo>/.claude/skills/<name>/.claude-plugin/plugin.json` を commit するだけで **marketplace も install もネットワークも不要**に plugin として自動ロードされる —— を使えば、**dual を単一実体に畳める可能性がある**。
- **制約（そのまま採用できない理由）**: project スコープは **trust 承認が必須**（親フォルダ trust や `claude -p` では読まれない）／**monitors はロードされない**／**リポジトリルートから起動しないと検出されない**。
- **判断**: 再検討に着手するか、現行 dual を維持するか。**「clone 直後に即動く」という売りと trust 要件の衝突**をどう見るかが分かれ目。

#### D-5. リリースチャネル（stable / latest）を導入するか

- レーンA に **§6-bis** として追記済み（公式の release channels ＝ 同一リポの異なる ref を指す marketplace を 2 本立て、managed settings でグループ割当）。
- **既知の罠**: 2 つの ref が**同じ version 文字列に解決されると更新がスキップされる**。本テーマは `v1.0.0` と `v1.0.0-RC2` が **payload バイト同一**だった実績があり、そのまま故障モードになる。
- **非対称**: **層2 だけがチャネル化でき、層1 body トラック（submodule 配布）には対応物が無い。**
- **判断**: 導入するか（＝Phase 5b の受入検証を実利用者で回す段を作るか）。現状は**記録のみで未着手**。

#### D-6. `claude-security` プラグインをリリース工程に組み込むか

**メインセッションは 7.5MB の `llms-full.txt` を一度も読んでいない。** 代わりに機械的な差分地図だけを作った:

3. **主要 46 ページの unified diff を生成** —— 各エージェントは「該当ページ」と「その差分」だけを読む

> この下ごしらえにより、**どのエージェントも巨大ファイルを grep せずに済んだ**。

### 3-4. エージェント構成（観点別ではなく文書群別に分割した理由）

**3 観点（陳腐化・不整合・改善機会）は同じ本文の同じ読み込みから判定できる**ため、観点別に分割すると同じ本文を 3 回読ませることになる。よって **文書群別に分割し、3 観点は各エージェント内に内包**させた。ただし「**新機能起点の横断改善提案**」だけは、文書ではなく**新機能側を起点に読む**必要があるため別建てにした。
