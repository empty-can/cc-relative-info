## 問い

1. `<Prjルート>\.claude` を Marketplace の仕組みで配布できるか。
2. 特定リポジトリ向けにチューニングされていない、ゼロから作ったリポジトリでも使える **最低限の資産だけのシンプルな `.claude/`** を、Marketplace のように Skill 等を配布する形でチーム共有するベストプラクティスは存在するか。

## エグゼクティブサマリ（結論の先出し）

> 急ぐ読者はこの節だけで結論を把握できる。詳細は [§推奨](#recommend)・[§マトリクス](#matrix)・[§解決案](#resolve) へ。

**問1（`<Prjルート>\.claude` を Marketplace の仕組みで配布できるか）→ No（部分的にのみ可）。** Marketplace で配れるのは `.claude/` の一部＝**機能・拡張資産**（skills/commands/hooks/MCP/output-styles/agents 等）と plugin 専用コンポーネントに限られ、**`.claude/` 全体を単一 Marketplace では配れない**（`CLAUDE.md`/`rules`/`permissions` は plugin で運べない＝[§マトリクス](#matrix) ②）。

**問2（最小・ポータブルな `.claude/` を「Marketplace のように」共有する単一ベストプラクティスは存在するか／無ければ設計せよ）→ 単一の既製ベストプラクティスは存在しない。** 単一チャネルで全資産を運ぶ手段が無いため（[§配布チャネル](#channels)）、資産種別ごとに最適チャネルへ振り分けて設計する：

- **① 機能・拡張資産 → 層2（Plugin / Marketplace）** に集約（一元更新・版管理）
- **② ガバナンス資産（CLAUDE.md / rules / permissions） → 層1（Git commit）**。メンバーに**強制**したい組織は層3（Managed settings）を重ねる（※純正 API ＋ Claude for Teams/Enterprise なら claude.ai オンライン設定で **MDM 不要**／**Amazon Bedrock 等の第三者プロバイダ利用時**は server-managed が使えないが、**v2.1.235 版(2026-08-19) では自ホスト型 Claude apps gateway がリモート配信の代替系統として公式化されており [\[82\]](#ref-82)**、endpoint-managed（MDM）一択ではなくなった。[§解決案](#resolve) 層3系）
- **③ 層2 を起動する設定（extraKnownMarketplaces / enabledPlugins） → 層1（project commit）**

**ポータブル最小 `.claude/` のスターター（層1 commit から始める出発点）**:

```txt
<repo>/
├── CLAUDE.md                     # チーム共通指示（層2 で運べない＝層1 commit）
└── .claude/
    ├── settings.json             # permissions（最小）＋ 層2 起動装置
    │                             #   （extraKnownMarketplaces + enabledPlugins）
    └── rules/*.md                # 常時ロードのトピック規約（必要なら）
# 機能資産（skills/commands/hooks/MCP）は層2 plugin から配り、repo には起動装置のみ残す
```

Git テンプレートリポジトリに置き "Use this template" で展開すれば、clone 直後（trust 承認後）に動く。**強制**が要る組織は層3 を重ねる。
**※ ゼロから即動く最小性を最優先するなら**、機能資産も `.claude/skills/` 等に同梱する従来型（層1 のみ）が最もポータブル（install/trust 不要。トレードオフは [§推奨](#recommend)）。

## 用語定義

本ドキュメントで一般語と異なる／特定の意味で用いる語を定義する。

| 用語 | 本ドキュメントでの意味 |
|---|---|
| **資産（asset）** | `.claude/` 配下に置く各構成要素（`CLAUDE.md` / `rules` / `settings.json` / `skills` / `agents` / `hooks` / MCP 定義 等）の総称。「配布対象となるファイル・設定」を指す。 |
| **配布チャネル（distribution channel）** | 資産をチームメンバーの環境へ届ける経路。本書では **層1（Git commit）／層2（Plugin・Marketplace）／層3（Managed settings）** の 3 つ。 |
| **強制力** | **配布した資産・ポリシーを、メンバーが上書き・無効化・不採用にできない度合い**（「配った資産を確実に使わせる」配布面の強制力に加え、層3 は permission/挙動ポリシーの強制＝`disableBypassPermissionsMode` 等による危険操作の禁止も含む）。3 段階＝**なし ＜ 弱 ＜ 最高**：層1 = なし（各自が自由に変更可）／層2 = 弱（`enabledPlugins` で有効化を誘導できるが install/無効化はメンバー可能）／層3 = 最高（managed は原則上書き不可）。**※ v2.1.235 版(2026-08-19) で「上書き不可」に公式の例外表が新設された**——`disableClaudeAiConnectors` / `isolatePeerMachines` は任意スコープの `true` が優先、`remoteControlAtStartup` は下位スコープの `false` が managed の `true` より優先、`crossSessionInbound` は project/local の**より厳格な値**が優先される（いずれも「より安全側へ倒す方向のみ」下位が勝つ設計）[\[83\]](#ref-83)。 |
| **統制（governance / control）** | 組織が資産の内容・許可範囲を管理し、メンバー側での逸脱（勝手な権限緩和・無効化）を防ぐこと。主に層3 が担う。 |
| **一元更新** | 配布元を 1 か所更新すれば全メンバーへ反映できる性質（バージョン管理つき）。層2 の主利点だが、層3 の中央 push も同性質（版管理 UI の有無・強制の有無が層2 と異なる）。 |
| **ポータブル** | 特定リポジトリに依存せず、ゼロから作ったリポジトリでもそのまま動く最小構成であること。 |
| **スコープ** | 設定の適用範囲。global（`~/.claude`）／project（リポジトリ `.claude/`）／local（`settings.local.json`・個人用）／managed（組織配布）。 |
| **trust dialog（workspace trust）** | 信頼されていないフォルダを開いた際、project 由来の権限・skills 等を有効化する前に表示される承認ダイアログ。承認するまで commit 済み設定はフル有効化されない。 |
| **managed settings** | 組織管理者が OS レベル（MDM 等）または admin console 経由で配布する、ユーザーが上書きできない最上位設定（= 層3）。 |

## 資産を一元的に配布・統制する手段（配布チャネル）

前提情報 (A)〜(D) で挙げた資産を、チームへ**一元的に配布・統制する手段**を整理する。手段は **3 つの配布チャネル**に大別でき、各チャネルが運べる資産・更新性・強制力が異なる。**単一の手段で全資産を配ることはできず**、設計とは資産特性に応じてこの 3 チャネルを組み合わせることである。

運べる資産の詳細は次の [§マトリクス](#matrix)で網羅するため、ここでは概要に留める。

| チャネル | 運べる資産（概要） | 更新性 | 配布の強制力 | 仕組みづくりのコスト |
|---|---|---|---|---|
| **層1: Git テンプレート / commit** | **最も広い**（commit 可能な全資産） | 手動（各自 pull） | **なし**（各自が上書き可） | **低**：Git リポジトリに `.claude/` を commit するだけ（テンプレ化は任意） |
| **層2: Plugin / Marketplace** | 機能・拡張資産＋plugin 専用（LSP/bin 等） | **一元更新（バージョン管理）** | 弱（enabledPlugins で誘導。強制は層3併用） | **中**：plugin 化＋marketplace リポジトリ＋settings 設定（軽量化は §解決案 B'〜B'''） |
| **層3: Managed settings** | ガバナンス・制御資産＋skills/subagents/output-styles | 中央 push | **最高（上書き不可。ただし v2.1.235 版で公式に少数の例外が新設 → [用語定義](#terms)）** | **3系統で大きく異なる**：server-managed＝**極低**（Teams/Enterprise の claude.ai 設定のみ・MDM 不要）／gateway-managed＝**中**（自ホスト gateway の運用）／endpoint-managed＝**高**（MDM）〜中（file 手動配置）（下記補足） |

> **層3（managed）の仕組みづくりのイメージ**: 公式は層3 を当初 **2系統**で整理していた（「server-managed と endpoint-managed のどちらを選ぶか」出典 [\[74\]](#ref-74)）が、**v2.1.235 版(2026-08-19) では第三者プロバイダ向けの (3) gateway-managed が加わり 3 系統**になった [\[82\]](#ref-82)。**(1) server-managed**＝**Claude for Teams / Enterprise** 契約があれば **Claude.ai admin console** からオンラインで中央 push（**MDM 不要・基盤コスト極低**。出典 [\[49\]](#ref-49)）。MDM を持たない組織・非管理デバイス向け。**(2) endpoint-managed**＝各マシンの **OS 管理者領域**へ配る方式で、(a) **MDM**（Jamf / Kandji / Intune / GPO 等）で `managed-settings.json` を OS パスへ配布、(b) **plist（macOS）/ レジストリ（Windows `HKLM`）** へポリシー配布。**管理者権限・MDM 基盤が前提**だが OS レベルで改ざん保護でき強制力が最も堅牢（公式に MDM スターターテンプレートあり。出典 [\[34\]](#ref-34) [\[35\]](#ref-35)）。**(3) gateway-managed**＝**v2.1.235 版(2026-08-19) で追加**。Amazon Bedrock / Google Cloud's Agent Platform / Microsoft Foundry 向けに、**自ホスト型 Claude apps gateway が「remote managed settings の同等配信」を担う**（gateway にサインインしたクライアントは `api.anthropic.com` ではなく gateway から managed settings を取得。IdP グループ単位のポリシー割当も可）[\[82\]](#ref-82)。**したがって「第三者プロバイダ利用時は (2) endpoint-managed 一択」は現行では誤り**——ただし gateway へ接続させる設定（`forceLoginMethod` / `forceLoginGatewayUrl`）自体は gateway から push できず endpoint-managed で配る必要があるため、**gateway は endpoint-managed を不要にするのではなく、初期ブートストラップだけ endpoint-managed に残す形になる**（詳細は §解決案 案D）。

### 重要な点

- managed settings（層3）は統制（制限）の手段であると同時に、`CLAUDE.md`・permission rules・MCP・subagents・skills を**中央配布できる配布チャネル**でもある（出典 [\[27\]](#ref-27) [\[28\]](#ref-28) [\[39\]](#ref-39)）。
- `.claude/` のガバナンス資産（`CLAUDE.md` / `rules` / `permissions`）を、**メンバーが上書きできない形で（＝強制）**配布できる唯一の経路である。

### 注意事項

**「`.claude` が無いと claude が起動できない」は誤り。** "The rest of the directory is optional"（出典 [\[1\]](#ref-1)）。`.claude/` は起動の必須要件ではない。
Marketplace で `.claude/` 全体を配れないのは「起動必須だから」ではなく、**Marketplace の配布対象が plugin 単位に限定されているため**である。

## 核心：資産種別 × 配布チャネル マトリクス

設計判断の中核。前提情報の資産を**配布のふるまいが共通するグループ**に分け、各グループがどのチャネルで配布できるかを示す。資産が増えても視認性を保つため、単一の大表ではなくグループ別の小表に分割した。

> **凡例**: ✅ 配布可（全構成要素）／ ❌ 不可（機構が無く配布できない）／ △ **部分的・条件付き**（構成要素や設定の一部しか配布／適用されない）／ ? **公式記載なし・未確認** ／ — 非該当（そのチャネルの概念自体が資産に適用されない。例: `--add-dir` と MCP）。
> **チャネル列**: 層1（Git commit）・層2（Plugin）・層3（Managed）・`--add-dir`（補助参照）。
> **パス列**: 各資産の主な配置（commit できる資産は `.claude/` 等の層1 の場所、plugin 専用は plugin root）。資産の「チャネル」は**配置場所と対応**し（skill を `.claude/skills/` に置けば層1／plugin に同梱すれば層2／managed dir に置けば層3）、層2・層3 で場所が異なる資産はセルに併記する。
> **scope の差（重要）**: パス列の `.claude/` は **project スコープ**（`<project>/.claude/` ＝ 層1 commit 対象）を指す。同じ資産を **`~/.claude/`（ユーザーホーム ＝ global）** に置いた場合は**各自の個人設定**となり、team 配布チャネルにはならない（`~/.claude/` へ team が配る経路は無い）。よって `.claude` を含むパスの資産は「**project `.claude/` ＝ 層1 ／ `~/.claude/` ＝ 個人（非配布）**」という差がある（前提情報 (A) 参照）。

**① 機能・拡張資産 — 層1・層2 を主とし層3 でも配布可（一部に条件付き △/? あり）**

| 資産 | パス | 層1 commit | 層2 plugin | 層3 managed | `--add-dir` |
|---|---|:---:|:---:|:---:|:---:|

| `agents/`（subagents） | `.claude/agents/*.md` | ✅ | △ `hooks`/`mcpServers`/`permissionMode` は無視（**これらを使う subagent は実質①の条件分岐＝層1/層3 が配布先**。[§推奨](#recommend) 参照）[\[39\]](#ref-39) | ✅ managed dir（最高優先）[\[39\]](#ref-39) | ✅ 自動ロード（**v2.1.178+ で追加・v2.1.165 までは不可**。`--add-dir`/`/add-dir` のみ・`additionalDirectories` は❌）[\[25\]](#ref-25)[\[75\]](#ref-75) |

| `workflows/*.js` | `.claude/workflows/*.js` ／ plugin `workflows/` | ✅ [\[44\]](#ref-44) | ✅ **v2.1.235 版(2026-08-19) で plugin の正規コンポーネントに昇格**（standard layout・File locations reference・manifest の `workflows` フィールド。v2.1.165 版では未定義＝当時は層1 専用だった）[\[78\]](#ref-78) | — | ❌ |

> **※ ①「`skills/` ✅ 層2」の補足（構成要素別の制約）**: 「✅ 層2」は **skill フォルダが plugin として配布される**ことを示すが、**同梱物が cache 先（`~/.claude/plugins/cache`）でそのまま機能する保証ではない**。`references/`・`templates/`・`scripts/` の参照は `${CLAUDE_SKILL_DIR}` 解決が必須、cache への書き込み（ナレッジ蓄積等）は不可（→ `${CLAUDE_PLUGIN_DATA}`）、同梱 README は UI 非閲覧（→ `homepage` 提示）、plugin root の `CLAUDE.md` は非ロード。構成要素別の制約は [調査結果 §7](../02.配布物の開発・テスト/01.Plugin・Marketplace編/Plugin・Marketplace配布物の開発・テスト_調査結果.md) ／ [手順書 §8](../02.配布物の開発・テスト/01.Plugin・Marketplace編/Plugin開発・テスト_手順書.md#impl-rules) を参照。

- auto memory（`~/.claude/projects/<project>/memory/`）
- `keybindings.json`（個人キーバインド）

<a id="resolve"></a>

## 解決案（チャネル別 + トレードオフ）

[§前提情報](#prereq) が資産の**配置場所**を、[§マトリクス](#matrix) が**資産 × チャネルの配布可否**を示したのに対し、本節は**チャネル軸**で各チャネルの実装案と、[§配布チャネル](#channels) で示した**コスト・強制力・更新性のトレードオフ**を扱う。資産ごとの配布可否・配置場所は前掲 2 節に譲り、本節では**チャネル固有の実装と注意点**に絞る（資産一覧は再掲しない）。

本節は各チャネルで「何を・どう配れるか」を並べる**実装カタログ**であり、チャネルの優劣を論じるものではない。**どの資産をどのチャネルへ寄せるか（組み合わせ方針）は次の [§推奨](#recommend) で扱う**——本節＝チャネル別の実装手段、§推奨＝資産の振り分け方針、という役割分担である。

提示順は **層1 → 層2 → 補助（`--add-dir`）→ 層3** とし、[§配布チャネル](#channels) の **コスト 低→高／強制力 なし→最高** の並びに対応する（順序はコスト軸の説明都合であり、層1 を基盤・主役とする趣旨ではない）。各小節の冒頭にそのチャネルのコスト／強制力／更新性を再掲する。`--add-dir` は主配布チャネルではないため補助系として層2 と層3 の間に置く。層2 は 4 案を横並び比較できるよう 1 表にまとめる。

### 層1系（Git テンプレート / commit）

> **コスト 低｜強制力 なし（各自が上書き可）｜更新性 手動（各自 pull）**

| 案 | 概要 | 主な長所 | 主な短所・制約 | 使いどころ |
|---|---|---|---|---|
| **案A** | Git リポジトリ（テンプレート／既存）に `.claude/` を commit。"Use this template" 等で展開 | ゼロから作るリポジトリでもそのまま動く。**IT 統制基盤なしに（層3 を持たない組織でも）層2 で運べないガバナンス資産（CLAUDE.md/rules/permissions）と層2 起動装置を配れる唯一の経路**。commit 可能な資産は技術的には最も広く運べる | 更新伝播が手動（各自 pull）。**配布の強制力なし**。trust 承認後に有効化。project で無視される security キーあり。配列設定は結合マージ | **層2 で運べない資産（ガバナンス／層1専用）＋層2 起動装置**の配布。機能資産も技術的には載るが、更新性のため層2 へ寄せるのが推奨（→[§推奨](#recommend)） |

**補足（案A）**:

**［利点・活用］**

- **commit 対象（層1 が"運べる"資産の全体）**: `CLAUDE.md`/`rules/*.md`/`settings.json`/`skills/`/`agents/`/`commands/`/`output-styles/`/`workflows/*.js`/`.mcp.json`/`.worktreeinclude`/`agent-memory/`（[前提情報 (B)](#prereq-b)（`.claude/` 配下）＋(C)（root の `.mcp.json`/`.worktreeinclude`）・出典 [\[2\]](#ref-2)）。[§マトリクス](#matrix) で層1 が ✅ の資産すべてに対応する。**これは層1 で配布"できる"資産の全体であって"載せるべき"資産ではない**——機能資産は層2 へ寄せ、層1 には層2 で運べないものを残すのが推奨（振り分けは [§推奨](#recommend)）。
- **hooks の配布**: hook 設定（`settings.json`）と repo 内のスクリプト本体（`$CLAUDE_PROJECT_DIR` 相対。例 `scripts/`・`.claude/hooks/`）の**両方を commit** する（出典 [\[61\]](#ref-61)）。
- **rules の軽量共有**: `.claude/rules/` はシンボリックリンク可（`ln -s ~/shared-rules .claude/rules/shared`。出典 [\[24\]](#ref-24)）。
- **💡 `--settings` 起動による強化（応用）**: ランチャースクリプト（層1 で commit）から `claude --settings <path>` で起動すると、`<path>` の settings は **command-line precedence（managed 直下・local/project/user より上）** で適用される（出典 [\[62\]](#ref-62)）。層3 が無くても通常 settings（`permissions`/`hooks`/`env` 等）を高優先で効かせられる。**ただし公式は `--settings` を automation/CI・background(agent view)・Agent SDK 向けの per-invocation / セッション限りの override として説明しており**（出典 [\[66\]](#ref-66)）、対話運用での恒久的な設定共有手段とは位置づけていない（正規ルートは project commit／層3）。本テクはその転用で、**強制力は弱**（ランチャー経由起動を強制できず、値ファイルも書換可）。`defaultMode: auto` 等の security 系キーは project/local で無視される仕様だが、**`--settings` 経由の値がどのスコープ判定を受けるか**（command-line として特別扱いされ有効化されるのか、依然 project 相当で無視されるのか）が原文に不記載で、効果は不確定（推測領域）。

**［注意事項 ⚠］**

- **project settings で無視される security キー**（commit しても効かない）: `defaultMode: auto`（v2.1.142+）／`skipDangerousModePermissionPrompt`／`autoMode`・`useAutoModeDuringPlan`（出典 [\[21\]](#ref-21)）。「リポジトリが自分に auto mode を付与する」攻撃を防ぐため、project/local settings からは読まれない。
- **trust dialog 条件**: commit した project settings の permission は、**workspace trust 承認後**に有効化（出典 [\[22\]](#ref-22)）。clone 即フル機能ではない。
- **⚠ 「trust 前は何も動かない」ではない（v2.1.235 版(2026-08-19) で公式に表として明文化）**: 何が trust 前に動くかは資産の種類で分かれる [\[96\]](#ref-96)。**配布物を設計する側の信頼境界そのもの**なので、層1 で `.claude/` を配るチームは把握しておくこと。

  | リポジトリが供給するもの | 親フォルダしか信頼していない場合 | `claude -p` / SDK（未信頼） |
  |---|---|---|
  | settings の **hooks**・**`env` ブロック**・`apiKeyHelper` 等のヘルパーコマンド、project skill の **hooks / `allowed-tools`** | **実行される** | **実行される**（skill の `allowed-tools` は trust に一切ゲートされない） |
  | `permissions.allow` / `additionalDirectories` | 承認まで使われない（ダイアログに列挙される） | 使われない（stderr に警告） |
  | project subagent の frontmatter hooks・`@skills-dir` plugin・`extraKnownMarketplaces` | 使われない（ダイアログも出ない） | 使われない |
  | `.mcp.json` のサーバー | 接続前に毎回確認 | **確認なしで接続される** |

  **したがって「配布する `.claude/settings.json` に hooks や `env` を入れる」ことは、受け取った人が trust する前から実行される処理を配るということ**である。逆に **`allowed-tools` を持つ skill は trust に関係なく効く**ので、配布物のセルフレビューでは permission よりも hooks / `env` / `allowed-tools` を優先して見ること。
- **配列設定のマージ**: `permissions.allow` 等の配列はスコープ間で**結合＋重複除去**（置換ではない。出典 [\[23\]](#ref-23)）。user 設定と結合され、予期せぬ許可が生じうる。

**［制約］**

- **settings の外部化に「ファイル内 import」は無い**: `settings.json` から別パスの settings を取り込む `extends`/`import` 相当のキーは存在しない。外部化手段は階層マージ（managed>local>project>user）／`--settings`／`managed-settings.d/`（層3 のみ）。`CLAUDE.md` には `@path` import 構文があるが **memory 専用**で settings には適用されない（出典 [\[67\]](#ref-67)）。

**層1 の配布パターン（運用形態）**:

層1（commit／clone ベース）の資産を実際にチームへ届ける運用は、3 パターンに整理できる。**層2 で配れる機能資産は層2（Plugin/Marketplace）へ寄せ、本パターンは「層2 で配れない資産」を対象とする**（振り分けは [§推奨](#recommend)）。起動オプションの全容は [付録B](#appendix-b) を参照。

- **パターン1（作業リポジトリに commit）**: 作業する Git リポジトリそのものに `.claude/` 資産を commit してチーム共有。**各リポジトリの特性に合わせた固有資産**（そのプロジェクト専用の `CLAUDE.md`/`rules`/`settings.json` 等）が対象。
- **パターン2（共通リポジトリ `<Share>` を clone ＋ 起動オプションで参照）**: Claude Code 資産だけを一元管理する共通リポジトリ `<Share>` を各自が clone し、**起動ランチャーで起動オプションを付与して読み込ませる**。作業リポジトリに依らない**横断的・チーム共通**の資産のうち、**層2 で配れないもの**が対象。`<Share>` を clone しただけでは Claude は読まないため、**「clone ＋ 起動オプション」の二点セット**で初めて有効になる:
  - CLAUDE.md / rules → `--add-dir <Share>` ＋ 環境変数 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`（[§マトリクス](#matrix) ②・出典 [\[26\]](#ref-26)）
  - permissions → `--settings <Share>/.claude/settings.json`（command-line precedence で project 等とマージ・出典 [\[62\]](#ref-62)）
  - MCP（`.mcp.json`）→ `--mcp-config <Share>/.mcp.json`（MCP は層2 でも配れるため層1 で配るかはチーム判断）
  - ⚠ **層3 を敷いた組織では `--mcp-config` が起動時に拒否されうる（v2.1.235 版(2026-08-19)）**: managed 専用キー `disableSideloadFlags`（v2.1.193+）は `--plugin-dir` / `--plugin-url` / `--agents` / **`--mcp-config`** の 4 フラグを起動時に拒否する [\[88\]](#ref-88)。**`--add-dir` と `--settings` は対象外**なので、パターン2 のうち **CLAUDE.md/rules（`--add-dir`）と permissions（`--settings`）は生き残り、MCP（`--mcp-config`）だけが落ちる**という非対称な壊れ方をする。層3 併用を想定するなら MCP は層2（plugin 同梱）か層3（`allowedMcpServers`）へ寄せておくこと。
- **パターン3（別リポジトリから手動で作業リポジトリ直下へ移動）**: パターン2 の `<Share>` とは別リポジトリで管理し、各自が clone 先から**手動でファイルを作業リポジトリ直下へ移動**して使う。作業リポジトリに依らない資産だが、**層2 で配れず、かつ起動オプションでも渡せず、作業 Git リポジトリ直下への物理配置が必須**なものが対象。現状は **起動ランチャースクリプト**（パターン2 の起動オプションを付与する起動装置そのもの。作業フォルダ直下で実行する必要があり、自己参照的にこれだけは手動配布が避けられない）が該当する。
  - **公式 `corporate-launcher`（v2.1.235 版(2026-08-19) で新設）はこの問題を解かない**（2026-08-20 確認）。`CLAUDE_CODE_PROCESS_WRAPPER` / `processWrapper` は **Claude Code が自分のバイナリから起動するプロセス**（background service・agent view のセッション・更新後の再起動・Remote Control worker 等）を指定ランチャー経由に強制する仕組みであり、**ユーザーが端末で自分で起動したセッションは対象外**（"A session you start yourself in a terminal, which runs however you invoked it"）。加えて **Windows では変数自体が無視される**（`exec` 契約に依存するため。デバッグログに警告が出るだけで全プロセスが素のまま起動する）。本テーマの配布先には Windows マシンが含まれるため、**パターン3 の手動配布は現時点でも回避できない**。ただし `processWrapper` が **project/local settings から設定できない**（commit されたファイルが全プロセスの前段にバイナリを挿せないようにする設計）という事実は、層1 で配れる設定の境界を示す例として押さえておく価値がある [\[89\]](#ref-89)。
  - なお [(C)](#prereq-c) の `.worktreeinclude` も「リポジトリ直下必須・フラグで渡せない」点でパターン3 の形式に当たるが、**worktree 運用（明示 `--worktree`／background agents・agent view の自動 worktree／`isolation: worktree` 指定の subagent）をするチームの場合のみ必要**。foreground の subagent orchestration では worktree は生成されないため、**worktree を使わない方針なら配布対象外**（worktree 自体の概要は本書スコープ外）。

### 層2系（Plugin / Marketplace）

> **コスト 中｜強制力 弱（`enabledPlugins` で誘導。強制は層3 併用）｜更新性 一元更新（バージョン管理）**

| 案 | 概要 | 主な長所 | 主な短所・制約 | 使いどころ |
|---|---|---|---|---|
| **案B** | 共有資産を plugin 化し private Marketplace で配布。`settings.json` に `extraKnownMarketplaces`+`enabledPlugins` を commit | バージョン管理・一元更新。名前空間で衝突回避。`--scope project` でチーム共有 [\[10\]](#ref-10) | `CLAUDE.md`/`rules`/`permissions` は運べない（[§マトリクス](#matrix) ②）。コマンドが `/plugin:name` 化 [\[11\]](#ref-11)。**v2.1.195+ は外部ソース plugin の install プロンプトすら出ず「未インストール」と報告されるだけ**（要手動 `claude plugin install`）[\[84\]](#ref-84) | plugin が**多数・高頻度更新・複数リポ横断** |
| **案B'（インライン宣言型）** | `extraKnownMarketplaces` に `source:'settings'` で plugin を直接インライン宣言 [\[15\]](#ref-15) | 層1↔層2 を 1 ファイルに統合。**専用 Marketplace リポジトリ不要** | plugins は外部ソース（GitHub/npm 等）参照必須。enable は `enabledPlugins` 別途 | plugin が**少数・低更新** |
| **案B''（@skills-dir 型）** | `.claude/skills/<name>/` に `.claude-plugin/plugin.json` を置き `<name>@skills-dir` として自動ロード [\[16\]](#ref-16) | **marketplace/install 不要**。次セッションから自動ロード。`claude plugin init` で scaffold | project スコープは **monitors 無効**・MCP は per-server 承認・**trust 必須**・サブディレクトリ起動時は非検出。`plugin init` は個人スコープのみ scaffold [\[16\]](#ref-16) | marketplace を立てずに**最小の plugin 配布** |
| **案B'''（seed 焼き込み型）** | `CLAUDE_CODE_PLUGIN_SEED_DIR` でビルド時に plugins を焼き込み、起動時に runtime クローンなしで利用 [\[17\]](#ref-17) | runtime クローン依存・ネットワーク前提を解消。fresh machine の install 落とし穴を回避。read-only・seed 優先 | ビルド/CI への組み込みが前提 | **コンテナ/CI 環境**への焼き込み |

**補足（層2 共通）**（案B'〜B''' 固有の注意は上の比較表を参照）:

**［利点・活用］**

- **plugin が梱包できる資産の全容**は[前提情報 (D)](#prereq-d)・[§マトリクス](#matrix) ③ を参照（skills〜MCP の機能資産 ＋ LSP/monitors/bin/channels の plugin 専用コンポーネント。出典 [\[4\]](#ref-4)）。
- **plugin の配置メカニズム**: 有効化された plugin はキャッシュへ独立コピーされ、外部ディレクトリは参照しない（symlink は例外。出典 [\[8\]](#ref-8)）。**v2.1.235 版(2026-08-19) の追加例外**: `command` ソースの **link mode** はコピーせずその場（in place）で使う [\[86\]](#ref-86)。
- **配布ソース種別の拡張（v2.1.235 版(2026-08-19)）**: 従来の github / git / git-subdir / npm / directory に加え、**`archive`**（HTTPS で zip を配布・`sha256` で pin 可・256MiB 上限。v2.1.224+）と **`command`**（ローカルコマンドが生成するディレクトリを plugin 化。セッションごとに再実行・copy/link モード。v2.1.229+）が追加された [\[86\]](#ref-86)。**`archive` は「git も npm も使えない社内アーティファクトサーバー経由の配布」を可能にする**ため、Marketplace リポジトリを立てられない組織の選択肢になる。**`command` は任意コマンドを実行する経路**なので、統制側は `disableCommandPluginSources` で組織全体を禁止できる（→[付録A](#appendix-a)）。
- **バンドル plugin（チーム標準セットの一括配布・v2.1.235 版(2026-08-19)）**: `plugin.json` に `dependencies` だけを書いた「マニフェストのみの plugin」でロール別の標準ツールセットを 1 install にまとめられる [\[87\]](#ref-87)。**「汎用資産は 1 本の大きな plugin に集約するか、粒度を保って複数に分けるか」というトレードオフを、粒度を保ったまま導入体験だけ束ねる形で解消できる**。
- **hooks は層2 で自己完結**: plugin に `hooks/hooks.json`（設定）とスクリプト本体を同梱し `${CLAUDE_PLUGIN_ROOT}` で参照すれば、設定もスクリプトも plugin 内で完結して配れる（層1 のような repo 側スクリプト配置に依存しない。出典 [\[4\]](#ref-4) [\[61\]](#ref-61)）。
- **新オプション**: `defaultEnabled: false`（インストールするが初期無効＝段階的ロールアウト）／`strict: false`（marketplace エントリが plugin.json より権威を持ち plugin 内容を完全制御）／release channel（同一 repo の異なる ref を 2 marketplace 化し managed settings でグループ別割当＝stable/latest）（出典 [\[18\]](#ref-18)）。
- **private repo 認証**: 自動更新には `GITHUB_TOKEN`/`GH_TOKEN`・`GITLAB_TOKEN`/`GL_TOKEN`・`BITBUCKET_TOKEN`（出典 [\[19\]](#ref-19)）。手動 install は credential helper で可（トークン不要）。
- **monorepo 配布**: `git-subdir` ソース / `--sparse` で必要ディレクトリのみ取得。npm private registry ソースも可（出典 [\[20\]](#ref-20)）。
- **`autoUpdate` が「一元更新」の実体**: marketplace 内の plugin 更新は各 `extraKnownMarketplaces` エントリの `autoUpdate`（起動時 refresh）が担う。**公式 Anthropic marketplace は default `true`／それ以外は default `false`** なので、自動更新したい組織 marketplace は明示 `"autoUpdate": true` を付けるか managed で強制する。ソース定義自体は marketplace の増減時のみ変更で低頻度（出典 [\[65\]](#ref-65)）。

**［注意事項 ⚠］**

- **△ subagent の一部設定は無効化**: plugin 経由の subagent は `hooks`/`mcpServers`/`permissionMode` が無視される（[§マトリクス](#matrix) ① の △）。これらを効かせたい subagent は層1 commit か層3 managed で配る（出典 [\[39\]](#ref-39)）。
- **enabledPlugins は「自動有効化」ではない**（**v2.1.195 で挙動が変わり、当初より不便になった**）: v2.1.165 版では commit した `extraKnownMarketplaces`+`enabledPlugins` に対し trust 時に**インストールを促すプロンプト**が出る仕様だった（出典 [\[13\]](#ref-13)）。**v2.1.235 版(2026-08-19) では ⑴ marketplace は trust 後にプロンプトなしで追加され、⑵ 外部ソース（GitHub リポジトリ・npm パッケージ等）の plugin は install を促されることすらなく「未インストール」と報告され `claude plugin install` コマンドが表示されるだけ**になった [\[84\]](#ref-84)。さらに **fresh machine では cache されておらず `claude plugin install` が必要**（出典 [\[14\]](#ref-14)）。**「clone だけで全 plugin 即利用可」でないどころか、プロンプトによる誘導も期待できない**——導入手順書やランチャーで `claude plugin install` を明示的に踏ませる設計にすること。なお `plugin-relevance`（v2.1.235 版で新設）は marketplace 運営者がセッション文脈に応じて plugin をサジェストする機構で、この導線不足を部分的に補える（`pluginSuggestionMarketplaces` で opt-in）[\[85\]](#ref-85)。
- **起動装置（`enabledPlugins`/`extraKnownMarketplaces`）のスコープと頻度**: 両者は `settings.json` の設定値。`enabledPlugins` は `"plugin@marketplace": true/false` の boolean マップで、一度有効化すれば plugin を増減しない限り変更不要（削除時は stale entry の掃除が要る）。スコープは **user(`~/.claude/settings.json`)＝個人の全プロジェクト共通／project(`.claude/settings.json`)＝チーム配布／local／managed**、precedence は managed>local>project>user（出典 [\[63\]](#ref-63)）。**user スコープはチーム配布にならない**——`~/.claude/` は repo 外で他者に渡らず web セッションにも乗らないため、全員へ効かせるには project に commit する（出典 [\[64\]](#ref-64)）。

**［制約］**

- **`rules` の代替（条件付きのみ層2 可）**: `rules` は plugin で直接運べないが、**条件付き rule（`paths:` で特定ファイル種別に限定）は skill として実装すれば層2 で配れる**——skill も `paths:` frontmatter を持ち（path-specific rules と同 format）、`user-invocable: false` で `/` 補完にも出さない（出典 [\[68\]](#ref-68)）。**ただし「常時ロードしたい rule」は skill 化では代替できない**: skill は「呼び出し時／関連と判断した時／`paths` 該当時」のみロードで常時ロードが無く、公式も「常時は rules/CLAUDE.md、必要時は skills」と用途を分けている（出典 [\[69\]](#ref-69)）。`CLAUDE.md` の `@import` で SKILL.md を常時展開する迂回も、import は内容をテキスト展開するだけで skill 機構（frontmatter・progressive disclosure 等）が死に、glob 非対応（単一パス・再帰4ホップ）・plugin のキャッシュパスも不安定なため非現実的（出典 [\[70\]](#ref-70)）。常時 rule は層1（commit/`--add-dir`）か層3（managed）に残す。

**補足（案B''')**: 複数 seed は Unix `:` / Windows `;` で多層化。ビルド時直接 install は `CLAUDE_CODE_PLUGIN_CACHE_DIR`（出典 [\[17\]](#ref-17)）。

### 補助系（`--add-dir`）

> **主配布チャネルではない補助参照｜強制力 なし｜実体（追加ディレクトリ）の配布は層1 等が前提**

`--add-dir` は 3 つの主配布チャネル（層1/2/3）には数えない**補助参照機構**。層番号は付さない。**配布チャネルに数えない判定基準**＝ (1) 資産の実体を運ばず（参照のみ）、(2) 起動フラグ/環境変数の手動付与に依存し恒久設定として宣言・commit できない——この 2 点で層1（実体を repo で運び commit 宣言できる）と峻別される。実体配布は層1 等に依存する。

| 案 | 概要 | 主な長所 | 主な短所・制約 | 使いどころ |
|---|---|---|---|---|
| **案C** | `claude --add-dir ../shared-config` で共有リポジトリの skills を参照。`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` で `CLAUDE.md`/`rules` も読む [\[26\]](#ref-26) | 複数リポジトリで共通の skills 等を 1 箇所に括り出して参照（DRY）。参照なので 1 箇所更新が反映される | **追加ディレクトリ自体は各自が clone 等で別途取得する必要がある**（`--add-dir` は配布手段ではなく参照のみ。実体の配布は層1 等が前提）。**subagents（`.claude/agents/`）は自動ロードされる**（**v2.1.178+ で追加・v2.1.165 までは不可**[\[75\]](#ref-75)）。**commands（`.claude/commands/`）も v2.1.235 版(2026-08-19) で自動ロード対象に加わった**（live reload なし・同名は作業リポ側が優先）[\[77\]](#ref-77)。hooks/output-styles/permissions は引き続き不可。`permissions.additionalDirectories` 設定では **skills すら読まれない**（自動ロードは `--add-dir` フラグ／`/add-dir` 専用例外）[\[25\]](#ref-25)。**例外ロードの完全一覧・版依存事実は [付録B『`--add-dir` 例外ロード一覧（正本）』](#adddir-exceptions) を正本とする**。起動フラグ運用が煩雑 | **補助的**。共有の主役にはならない |

**補足（案C）**:

**［利点・活用］**

- **チーム共通 CLAUDE.md/rules の配布**: `--add-dir <Share>` ＋ `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` を設定すると、`<Share>/CLAUDE.md`・`<Share>/.claude/CLAUDE.md`・`<Share>/.claude/rules/*.md`・`<Share>/CLAUDE.local.md` がロードされる（`<Share>/CLAUDE.md` と `<Share>/.claude/CLAUDE.md` は**両方**読まれ等価。環境変数を付けないと既定では読まれない。出典 [\[71\]](#ref-71)）。層2 で運べない**常時ガバナンス（CLAUDE.md/rules）を共通フォルダ 1 箇所で参照させる**用途に使える（実体は各自 clone・強制力なしは案C 共通）。

**［注意事項 ⚠］**

- **探索仕様（フォルダ名の落とし穴）**: `--add-dir <Share>` は `<Share>` を作業ルートに加え、設定を **`<Share>/.claude/` 配下**から読む（skills は `<Share>/.claude/skills/`。出典 [\[25\]](#ref-25)）。したがって共有設定リポジトリを clone する際に**フォルダ名自体を `.claude` にすると `<Share>/.claude/.claude/` を探すことになり中身が読まれない**。`--add-dir` に渡すのは「`.claude/` を内包する親フォルダ」にする（例: `~/shared/team-config` を渡し `~/shared/team-config/.claude/skills/` を読ませる）。
- **競合**: `<Share>/.claude/` とプロジェクトの `.claude/` は別パスのため FS 競合は起きない（Claude は両者を区別）。ただし資産は結合され（skills 両ロード、`enabledPlugins`/`extraKnownMarketplaces` はマージ）、同名資産があれば名前レベルの衝突はありうる（フォルダ名とは無関係）。

### 層3系（Managed settings）— 配布 ＋ 強制

> **コスト server-managed＝極低（Teams/Enterprise・claude.ai 設定のみ・MDM 不要）／endpoint-managed＝中〜高（MDM・file 配置）｜強制力 最高（上書き不可）｜更新性 中央 push**

| 案 | 概要 | 主な長所 | 主な短所・制約 | 使いどころ |
|---|---|---|---|---|
| **案D** | managed settings で permission/MCP/`CLAUDE.md`/subagents/skills/version を管理者制御ティアで配布。**上書き不可** [\[37\]](#ref-37) | **唯一の強制手段**。`CLAUDE.md`/permissions の中央配布も担う | endpoint-managed は IT 統制（MDM/plist/registry）が前提／server-managed は **Claude for Teams / Enterprise** 契約のみで可〔MDM 不要〕[\[49\]](#ref-49)。**Bedrock 等の第三者プロバイダ利用時は server-managed 不可**（[\[74\]](#ref-74)）。マシン/組織単位 | 「推奨」でなく「**強制**」したい・plugin 以外の customization を禁止したい組織 |

**補足（案D）詳細**:

**［選択：server-managed と endpoint-managed］**

公式は利用組織の状況に応じた **2系統の選択軸**を示していた（「server-managed と endpoint-managed のどちらを選ぶか」出典 [\[74\]](#ref-74)）。**「層3＝MDM 必須・構築コスト極高」は誤り**で、Teams/Enterprise 契約があれば MDM 無しでもオンライン設定だけで層3 を組める。
**v2.1.235 版(2026-08-19) では、これに第三者プロバイダ向けの第3系統（gateway-managed）が加わった** [\[82\]](#ref-82)。

| 系統 | 配布元 | 向く組織 | 基盤コスト | 改ざん耐性 | 前提 |
|---|---|---|---|---|---|
| **server-managed** | Anthropic サーバー（認証時に配信）／Claude.ai admin console で設定 | **MDM 無し**・非管理デバイス中心 | **極低**（オンライン設定のみ） | 弱（クライアント制御。admin/sudo 権限者は回避可） | **Claude for Teams / Enterprise**（**設定操作には Owner / Primary Owner ロールが必要** [\[90\]](#ref-90)）＋ **純正 API 直結**（[\[49\]](#ref-49)[\[74\]](#ref-74)） |
| **gateway-managed**（v2.1.235 版で追加） | **自ホストの Claude apps gateway**（サインイン済みクライアントが gateway から取得） | **第三者プロバイダ利用**（Bedrock / Google Cloud's Agent Platform / Microsoft Foundry） | 中（gateway の自ホスト運用） | 弱〜中（クライアント制御。gateway 側で IdP グループ別ポリシー割当が可能） | gateway の構築・運用 ＋ **接続設定（`forceLoginMethod` / `forceLoginGatewayUrl`）を endpoint-managed で配る**必要あり [\[82\]](#ref-82) |
| **endpoint-managed** | 各デバイス（MDM プロファイル／plist／registry／`managed-settings.json`） | **MDM/端末管理あり** | 中〜高（MDM 基盤 or file 手動配置） | 強（OS レベルで保護） | OS 管理者権限（**プロバイダ非依存**・[\[34\]](#ref-34)） |

> MDM が無くても **file-based `managed-settings.json`** を OS 所定パスへ手動配置すれば endpoint-managed を最小構成で実現できる（ただし書込権限を持つユーザーによる改変リスクは残る）。強い強制力には MDM ＋ endpoint-managed。
> **⚠ 起動時の失敗挙動が系統で異なる**: gateway クライアントは gateway に到達できないと**キャッシュ済み設定へフォールバックせずエラー終了**する（server-managed はキャッシュへフォールバック）。定期リフレッシュ（1時間ごと）は双方 fail-open [\[82\]](#ref-82)。
> **プロバイダ別の機能可否**は公式の [`feature-availability`](https://code.claude.com/docs/en/feature-availability) ページ（v2.1.235 版で新設）が一覧化するようになった。subagents / hooks / commands / skills / CLAUDE.md / plugins / MCP / checkpoints / sandboxing / workflows は全プロバイダで利用可、**server-managed settings は Team/Enterprise 限定**という判定が公式表として引ける [\[91\]](#ref-91)。層3 の可否判定は本書の表ではなく**この公式ページを一次参照にするのが陳腐化に強い**。

**［注意事項 ⚠］**

- **商用プラン要件**: **server-managed settings（Claude.ai admin console 経由）は Claude for Teams または Enterprise の機能**（Teams は v2.1.38+、Enterprise は v2.1.30+。device management 不要。出典 [\[49\]](#ref-49)）。一方 **file-based `managed-settings.json`（MDM/plist/registry 配置）は OS レベルの管理者機構**で、admin 権限があれば配置可能（＝商用プランが無くても MDM 経由の層3 統制は可能。なお file-based のプラン非依存はファイル機構の性質からの推定で原文に明示はない）。
- **server-managed のバイパス（Amazon Bedrock 等の第三者プロバイダ利用時）**: server-managed は `api.anthropic.com` への直結が必須で、**Amazon Bedrock / Google Cloud's Agent Platform（旧 Google Vertex AI・v2.1.235 版で改称）/ Microsoft Foundry / Claude Platform on AWS / カスタム endpoint（`ANTHROPIC_BASE_URL`・LLM gateway）は公式に非対応**として名指しで列挙されている（出典 [\[74\]](#ref-74)。プロバイダ名の現行表記は [\[90\]](#ref-90)）。`CLAUDE_CODE_USE_BEDROCK`/`_VERTEX`/`_FOUNDRY` 等を設定した時点で server-managed は**バイパスされる**（出典 [\[48\]](#ref-48)）。
  - **⚠ 訂正（2026-08-20）**: v1.0〜v1.2 は続けて「**したがって Bedrock 利用組織の層3 は endpoint-managed（MDM／file-based）一択**」と結論していたが、**v2.1.235 版(2026-08-19) 時点ではこれは誤り**。これら 3 プロバイダ向けに **自ホスト型 Claude apps gateway が「remote managed-settings の同等配信」を担う**と公式に明記された [\[82\]](#ref-82)。ただし **gateway へ接続させる設定自体（`forceLoginMethod` / `forceLoginGatewayUrl`）は gateway から push できず endpoint-managed で配る必要がある**ため、正確には「**endpoint-managed 一択**」→「**ブートストラップだけ endpoint-managed、以降のポリシー配信は gateway**」への変化である。
  - **AWS 側のオンライン代替は存在しない（この記述は現在も有効）**: AWS が claude.ai 相当の「オンラインで Claude Code の managed settings を中央配布・統制する機能」を提供しているかを **AWS 公式ドキュメント（AWS Documentation MCP 経由・2026-06 調査）** で確認したが、**該当機能の記載は無い**。Bedrock コンソール／フリート管理・AWS Organizations / SCP / IAM・IAM Identity Center いずれもクライアント設定（層3）を中央配布する機能を持たない。AWS Organizations の「Bedrock policies」や Bedrock Guardrails は **モデルアクセス境界・推論 I/O の統制**であって、`.claude/` 設定の配布・上書き防止とは別レイヤであり、層3 の代替にはならない。**上記 gateway は Anthropic 製の自ホスト製品であり AWS の機能ではない**ため、この結論とは矛盾しない。MDM も gateway も持たないチームには file-based `managed-settings.json` の手動配置が現実解（改変リスクは残る）。

**［利点・活用（配布・統制でできること）］**

- **配布メカニズムの 4 層と優先順位**（出典 [\[34\]](#ref-34)。**v2.1.235 版(2026-08-19) で 1. の定義拡張と 3 つの例外が追加**[\[83\]](#ref-83)）:
  1. **リモート設定**＝Claude.ai の server-managed settings **または Claude apps gateway**（最高、全OS）※ gateway が加わったのが v2.1.235 版での変更
  2. plist / registry（macOS `com.anthropic.claudecode` plist ／ Windows `HKLM\SOFTWARE\Policies\ClaudeCode`、高）
  3. File-based（`managed-settings.json` ＋ `managed-settings.d/*.json`、中）
  4. Windows user registry（`HKCU\...`、最低）
  - **managed tier 間はマージしない（先勝ち）**。上位 tier が非空なら下位は完全無視。file-based tier 内のみ base + `managed-settings.d/` がマージ。
  - **⚠ 先勝ちの例外（v2.1.235 版で追加）**[\[83\]](#ref-83):
    - **`policyHelper` を使うと、その出力が上記 4 層すべてを置き換える**（従来は file-based のみを置換していた）。他の配信経路を敷いている組織は無効化される点に注意。
    - **cross-source キー**は「選ばれた 1 ソース」に関わらず**管理者制御の全ソースから拾われる**（HKCU は除外）。対象＝`sandbox.network.allowManagedDomainsOnly` / `sandbox.filesystem.allowManagedReadPathsOnly` とその allowlist、`allowAllClaudeAiMcps`、`sandbox.bwrapPath` / `sandbox.socatPath` / `sandbox.ripgrep`、`forceRemoteSettingsRefresh`、および **`env`**。
    - **`env` は変数単位でマージ**（各変数は定義している最上位ソースから採り、下位が未定義分を埋める。v2.1.223+。旧挙動へ戻すには `CLAUDE_CODE_DISABLE_ADMIN_ENV_UNION`）。
  - **配列マージの例外**: `permissions.allow` 等の配列はスコープ間で結合されるが、**`fallbackModel`（順序に意味があるため最上位ファイルの値を丸ごと採用）と `availableModels`（最上位 managed ソースが定義していればそれをそのまま適用し user/project/local を無視）は結合対象外** [\[83\]](#ref-83)。
- **OS別 file-based パス**: macOS `/Library/Application Support/ClaudeCode/`／Linux・WSL `/etc/claude-code/`／**Windows `C:\Program Files\ClaudeCode\managed-settings.json`**（旧 `C:\ProgramData\...` は **v2.1.75 以降廃止**。出典 [\[36\]](#ref-36)）。
- **`managed-settings.d/`**: 複数チームの独立ポリシー断片をアルファベット順マージ（数値プレフィックスで順序制御。スカラー後勝ち・配列結合＋重複除去・オブジェクト deep merge）。MDM starter templates（Jamf/Kandji/Intune/GPO）が公式 repo に（出典 [\[35\]](#ref-35)）。
- **層3で配布できる資産（配布チャネルとしての側面）**:
  - **組織共通 CLAUDE.md**: OS-path に `CLAUDE.md` 配置 or `managed-settings.json` の `claudeMd` キー埋め込み（全セッション強制ロード・除外不可。出典 [\[27\]](#ref-27)）。
  - **permission rules**: managed に置き `allowManagedPermissionRulesOnly` で user/project の permission 定義を排除（出典 [\[28\]](#ref-28)）。
  - **MCP**: `allowedMcpServers` ＋ `allowManagedMcpServersOnly`（出典 [\[28\]](#ref-28)）。`managed-mcp.json` は server-managed では配布不可・キーで代替（出典 [\[46\]](#ref-46)）。
  - **managed subagents / skills**: managed settings dir の `.claude/agents/`・skills（Enterprise スコープ）が最高優先（出典 [\[39\]](#ref-39) [\[38\]](#ref-38)）。**v2.1.235 版(2026-08-19) では具体パスが明記された**——Linux なら `/etc/claude-code/.claude/skills/<skill-name>/`（＝ managed settings ディレクトリ配下の `.claude/skills/`）。**これは skill 配布の第3経路**（個人 `~/.claude/skills/` ／ プロジェクト `.claude/skills/`＝層1 ／ plugin＝層2 に続くもの）であり、**層3 が「設定だけを配るチャネル」ではなく「ファイル実体を配るチャネル」でもある**ことを示す [\[92\]](#ref-92)。
  - **output-styles**: managed settings dir の `.claude/output-styles/` から読まれる [\[76\]](#ref-76)（v1.0〜v1.2 は「公式記載なし」としていたが、**旧スナップショットにも同じ記述があり執筆時の見落とし**。2026-08-20 訂正）。
  - **enabledPlugins**: 全スコープの install をブロック ＋ marketplace から非表示する組織ポリシー（出典 [\[40\]](#ref-40)）。
  - **hooks（△ 部分配布）**: `allowManagedHooksOnly` で hook を managed 由来のみに制限できるが、**配布できるのは設定のみ・スクリプト本体は別途配置が必要**で層3 単独では完結しない（[§マトリクス](#matrix) ① の △。出典 [\[28\]](#ref-28) [\[61\]](#ref-61)）。
    - **💡 層2＋層3 の合わせ技（v2.1.235 版(2026-08-19) で有効性を確認）**: hook は層2（plugin）なら `hooks/hooks.json` ＋ スクリプト本体を同梱して**自己完結**で配れる。そこで **managed settings の `enabledPlugins` で当該 plugin を force-enable し、`allowManagedHooksOnly` で他の hook を排除する**と、「実体は層2 が運び、強制は層3 が担う」形で**層3 単独の △ を実質 ✅ に近づけられる**。ただし `allowManagedHooksOnly` を `true` にすると **`command` ソースの plugin も既定で無効化される**（`disableCommandPluginSources` を明示 `false` にしない限り）ため、`command` ソースを併用する組織は要注意 [\[88\]](#ref-88)。
- **層3の統制（強制）キー一覧**（20+ キー、いずれも Managed settings only）: 視認性のため一覧は文末の [付録A：層3 統制キー一覧](#appendix-a) に分離した。代表例＝`strictPluginOnlyCustomization`（skills/agents/hooks/MCP を plugin+managed 由来のみに制限）／`allowManagedPermissionRulesOnly`（permission を managed のみに）／`requiredMinimumVersion`（範囲外バージョンで起動拒否）／`strictKnownMarketplaces`（marketplace 許可リスト）。
- **検証**: `/status` の `Setting sources` で `(remote)`/`(plist)`/`(HKLM)`/`(HKCU)`/`(file)` を確認（出典 [\[47\]](#ref-47)）。設定が反映されない場合は `/debug`（debug-your-config）で設定ソースのロード状況を診断（出典 [\[72\]](#ref-72)）。

**［制約・スコープ外］**

- **一覧から除外した managed 専用キー**（漏れではなくスコープ外として明示）: `sshHostAllowlist`（Claude **Desktop アプリ専用**で CLI/IDE は読まない）、`bwrapPath` / `socatPath`（Linux/WSL2 のサンドボックス binary パス）。いずれも managed 専用だが `.claude/` 資産の配布統制とは目的が異なる（出典 [\[59\]](#ref-59)）。

<a id="recommend"></a>

## 推奨：機能資産は層2 へ集約し、層1・層3・`--add-dir` で役割分担

**配布の原則**: 層1/層2 の両方で配れる機能資産（skills/commands/hooks/MCP/output-styles 等）は、**強制力ゼロ・更新手動の層1ではなく、一元更新できる層2（plugin）へ一律寄せる**。層1 は「層2 で運べない資産」と「層2 を起動するための設定」に絞り、二重管理をなくす。

```txt
■ 原則: 層1/層2 両対応の機能資産は層2 へ一律集約。層1 は「層2 で運べない資産」と「層2 の起動装置」に絞る。

┌─ 層2 ── 機能・拡張資産を集約（案B〜B'''／更新性 ◎・強制力 弱）
│   skills/ commands/ hooks/ MCP/ output-styles/ ＋ △以外の agents/
│   ＋ plugin 専用（マトリクス③）: LSP/ monitors/ bin/ channels/
│   ⚠ install/trust・fresh machine で要 install・ネットワーク前提（即動ポータビリティ ↓）
│
├─ 層1 ── 層2 で運べない資産 ＋ 層2 起動装置（案A／強制力 なし）
│   ガバナンス（マトリクス②）: CLAUDE.md / rules/ / permissions
│   起動装置: settings.json の extraKnownMarketplaces + enabledPlugins（無いと層2 が有効化されない）
│   層1専用（マトリクス④）: workflows/ / agent-memory/
│   △回避: hooks/mcpServers/permissionMode を使う subagent（plugin だと無視されるため層1 へ）
│
├─ 補助 ── --add-dir（案C／参照のみ・強制力 なし）
│   層2 で運べない CLAUDE.md / rules を共有ディレクトリから参照（skills の --add-dir live reload と同性格）
│
└─ 層3 ── ガバナンス資産を「強制」（案D／IT 統制がある組織・強制力 最高）
    CLAUDE.md(claudeMd) / permissions / MCP / subagents / skills / version / strict 系
    → 上書きを防げるのは層3 だけ。中央 push。Windows=C:\Program Files\ClaudeCode\・複数チーム=managed-settings.d/
```

**役割分担の早見（どの資産をどこへ寄せるか）**: 配布可否そのものは [§マトリクス](#matrix)、各チャネルの実装と注意点は [§解決案](#resolve) に詳述済み。本表は方針（"寄せる先"）の早見に絞り、根拠は両節への参照に留める。

| 資産グループ | 寄せる先 | 根拠（詳細はマトリクス／解決案） |
|---|---|---|
| 機能・拡張（skills/commands/hooks/MCP/output-styles） | **層2** | 一元更新・版管理が効く（マトリクス①） |
| subagents | 原則 **層2**／ `hooks`・`mcpServers`・`permissionMode` を使うものは **層1**（or 層3） | plugin 経由は当該設定が無視（①△） |
| ガバナンス（CLAUDE.md/rules/permissions） | **層1**（強制が要れば層3） | 層2 では運べない（②）。例外＝条件付き rule のみ skill 化で層2 可 |
| 層2 起動装置（extraKnownMarketplaces/enabledPlugins） | **層1**（project commit） | 層2 有効化の前提。user スコープはチーム配布にならない |
| 層1専用（workflows/agent-memory） | **層1** | 層2 に運ぶ仕組みがない（④） |
| plugin 専用（LSP/monitors/bin/channels） | **層2** | plugin 経由でのみ配れる（③） |

**強制できるのは層3 だけ**: 層1・`--add-dir` は強制力なし、層2 も弱（`enabledPlugins` で誘導するのみで install/無効化は各自可）。メンバーの上書きを防いで**強制**したい、または plugin 以外の customization を禁止（`strictPluginOnlyCustomization`）したい組織は層3（managed）を重ねる。層3 は制限機構であると同時に、ガバナンス資産（CLAUDE.md/permissions/MCP/subagents/skills）の**中央配布チャネル**でもある（詳細は [§解決案](#resolve) 層3系・案D）。

**`--add-dir` で補える近縁資産（射程が広がっている・2026-08-20 更新）**: 層2 で運べない CLAUDE.md/rules は、`--add-dir` ＋ `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` で共有ディレクトリから参照する DRY 共有ができる（skills の `--add-dir` live reload と同じ "参照型共有" の性格）。ただし実体は各自 clone が前提・強制力なしで、補助の位置づけに留まる（詳細は [§解決案](#resolve) 補助系・案C）。

> **⚠ ただし「補助」という一語では実態より控えめになりつつある**。例外ロードの対象は **skills のみ（〜v2.1.165）→ ＋subagents（v2.1.178+）→ ＋commands（v2.1.235 版で確認）** と**増える方向に動いており** [\[75\]](#ref-75)[\[77\]](#ref-77)、`--add-dir` の射程は既に**①機能・拡張資産の大半**（skills / subagents / commands）に届いている。位置づけは「CLAUDE.md/rules を参照する補助」から「**強制力を持たない、層2 の部分的な代替経路**」へ読み替えるのが実態に近い。**主配布チャネルに数えない判定基準（実体を運ばない・恒久設定として commit 宣言できない）は変わらない**ので分類は据え置くが、**次の版で更に広がる前提で読むこと**。逆に「`<Share>` に置いたものが作業リポジトリのセッションへ入り込まない」という**共有境界の設計を `--add-dir` に依存させるのは危うい**（詳細は [付録B 正本表](#adddir-exceptions) の版境界注記）。

**トレードオフ（ポータビリティ）**: 機能資産を層2 へ寄せると install/trust/ネットワーク前提が加わり、「clone（commit）だけで即動く」最小ポータビリティ（問い2）は下がる。ゼロ立ち上げの即動性を最優先するなら、機能資産を層1 に同梱する従来型も依然有効。ネットワーク前提・fresh machine の `claude plugin install` を解消したい場合は [§解決案](#resolve) 案B'''（seed 焼き込み型・`CLAUDE_CODE_PLUGIN_SEED_DIR`）を併用する。

> **2026-08-20 追記（トレードオフの緩和策の再掲）**: このトレードオフを**両立させうる唯一の形が [§解決案](#resolve) 層2系の案B''（`@skills-dir` 型）** である ―― `<repo>/.claude/skills/<name>/.claude-plugin/plugin.json` を commit しておけば **marketplace も install もネットワークも不要**のまま、plugin としての自己完結性（`${CLAUDE_PLUGIN_ROOT}` によるスクリプト同梱・agents/hooks/output-styles/MCP のバンドル）が得られる。**「層1 に body を commit しつつ同じ資産を plugin としても発行する」という二重管理を、単一の実体に畳める可能性がある**。ただし案B'' の制約（**project スコープは trust 承認が必須**で親フォルダ trust や `claude -p` では読まれない／**monitors はロードされない**／**リポジトリルートから起動しないと検出されない**）は「clone 直後に即動く」という売りと部分的に衝突するため、**採否は配布先の起動運用（ランチャーがリポジトリルートで実行されるか・trust をいつ承認させるか）とセットで判断すること**。
>
> **2026-08-20 追記（実測による確定）**: 上記の「畳める可能性」を CLI **v2.1.237** の実機で検証し、**畳めることを確認した**（証跡・手法は [Plugin編 調査結果 §9](../02.配布物の開発・テスト/01.Plugin・Marketplace編/Plugin・Marketplace配布物の開発・テスト_調査結果.md#single-entity)、実務手順は [Plugin/Skill 手順書 §4](../02.配布物の開発・テスト/01.Plugin・Marketplace編/Plugin開発・テスト_手順書.md#publish-forms)）。要点は 3 つ ―― (a) **`plugin.json` の付与は既存利用者に非破壊**。追加後も素の skill としての呼び名 `/<name>` は project 経路でも `--add-dir` 経路でも変わらない（`--add-dir` では plugin にはならず素の skill のままロードされる）。**案A パターン2 の `--add-dir` レールは壊れない**。 (b) **`git-subdir` source を使うと、`<repo>/.claude/skills/<name>/` という 1 つのディレクトリを marketplace から直接参照でき、コピーも publish も不要**になる。**実体 1 つ・参照 2 通り**に畳めるということであり、配布専用リポジトリは `marketplace.json` 1 ファイルで成立する。 (c) **ただし「単一の消費形態」にはならない**。層1（リポジトリを持つ）と層2（同名 plugin を install）を**同じ利用者が両方持つと、素の project skill と plugin skill が二重に context へ載る**（plugin どうしの衝突は CLI が抑止するが、素の skill は残る）。**配布側は層1 と層2 のどちらで使うかを利用者に一つ選ばせる**設計にすること。

**結論の要約**（[§エグゼクティブサマリ](#summary) の詳細版）:

- **問1 への回答**: Marketplace で配れるのは `.claude/` の一部＝機能・拡張資産＋plugin 専用コンポーネントに限られ、**`.claude/` 全体を単一 Marketplace では配れない**（CLAUDE.md/rules/permissions は plugin 不可＝[§マトリクス](#matrix) ②）。
- **問2 への回答**: 「最小 `.claude/` を Marketplace のように共有する」**単一の既製ベストプラクティスは存在しない**（単一チャネルで全資産を運べないため）。代替として、資産を「**層2 で運べないもの（層1／強制が要れば層3）**」と「**両方で配れる機能資産（層2 へ集約）**」に振り分けて設計した。`--add-dir` は層2 で運べない CLAUDE.md/rules の DRY 共有を補助する。skills/subagents は公式も「Commit / Plugin / Managed の 3 経路」で整理している（出典 [\[50\]](#ref-50)）。

| `--mcp-config <file-or-json>` | MCP サーバー定義（複数可）。`--strict-mcp-config` で当該のみに限定 | ファイル or JSON | パターン2: `<Share>` の MCP |
| `--plugin-dir <dir/.zip>` | **plugin 一式**（skills/commands/agents/hooks/MCP/output-styles/LSP/monitors/bin/channels）。「そのセッションのみ」 | ディレクトリ or .zip | 層2 を marketplace なしで配る代替（本方針では原則不使用 ※） |
| `--plugin-url <url>` | plugin `.zip`（URL から） | URL | 同上 ※ |
| `--agents <json>` | subagent 定義（動的・インライン JSON） | JSON 文字列 | 一時的な subagent 定義 |
| `--append-system-prompt-file <file>` | system prompt への追記テキスト | ファイル | 共通の system prompt 追記 |

> **共通の注意**: これらは原則 **「そのセッションのみ」適用**で、毎起動でランチャーが付与する必要がある（恒久設定ではない）。**強制力は弱い**（ランチャー経由起動・`<Share>` 書き換えを各自任せ＝[§推奨](#recommend) の「強制は層3 だけ」と整合）。`--settings`/`--mcp-config` とも **managed policy（層3）には従う**（managed の deny を緩められない）。
>
> **⚠ 層3 を重ねたときの相互作用 —— 「無視される」ではなく「起動時に落ちる」（v2.1.235 版(2026-08-19)）**
>
> 層1+2 で組んだランチャーに後から層3 を重ねると、**セッションが起動しなくなる経路が 2 本ある**。層3 導入前に必ず確認すること。
>
> | 層3 側の設定 | 起動時に拒否されるフラグ | 症状 |
> |---|---|---|
> | `disableSideloadFlags: true`（managed 専用・v2.1.193+）[\[88\]](#ref-88) | `--plugin-dir` / `--plugin-url` / `--agents` / `--mcp-config` | 起動時に拒否。全サーバーが in-process `type: "sdk"` の `--mcp-config` のみ例外的に許容 |
> | `managed-mcp.json` を配備 [\[97\]](#ref-97) | `--mcp-config`（および `--strict-mcp-config`） | `You cannot dynamically configure MCP servers when an enterprise MCP config is present` で **exit** |
>
> **`--add-dir` と `--settings` はいずれの対象でもない**ため、パターン2 の主経路（`<Share>` の CLAUDE.md/rules/skills/agents/commands/permissions）は層3 下でも成立する。**壊れるのは MCP 同梱部分だけ**という非対称を押さえること。層3 併用が前提の組織では、**MCP はランチャーの `--mcp-config` ではなく層3（`managed-mcp.json` / `allowedMcpServers`）か層2（plugin 同梱）へ寄せる**。
>
> ※ なお `disableSideloadFlags` を**自組織で有効化することは本書では推奨しない**——層2 の開発・テストは `--plugin-dir` に依存する（[手順書 §3-2](../02.配布物の開発・テスト/01.Plugin・Marketplace編/Plugin開発・テスト_手順書.md#c2)）ため、有効化すると開発工程が止まる。「配布先の組織が敷いているかもしれない外部条件」として扱う。
>
> **`--safe-mode` / `CLAUDE_CODE_SAFE_MODE`（v2.1.235 版で新設）**: 配布した資産を渡すフラグではないが、**CLAUDE.md / skills / plugins / hooks / MCP / commands / agents / output-styles / workflows を一括で無効化して起動する**切り分け用フラグ。「配った資産のどれかが悪さをしている」ときの一次切り分けに使える（**managed settings のポリシーは適用され続ける**点に注意）[\[95\]](#ref-95)。
>
> **※ `--plugin-dir`/`--plugin-url` について**: plugin 化すれば agents/commands/hooks/output-styles も `<Share>` から marketplace なしに配れる（[§解決案](#resolve) 層2系・案B'' の CLI フラグ版に相当）。ただし plugin の制約（`settings.json` は `agent`/`subagentStatusLine` のみ・plugin root の CLAUDE.md 非ロード・subagent の hooks/mcpServers/permissionMode 無視）を引き継ぐため、**CLAUDE.md/rules/permissions は `--plugin-dir` でも運べない**。本書の「層2 で配れるものは層2」方針では、これらは marketplace 経由（案B〜B'''）を主とし、`--plugin-dir` は一時利用・特殊ケース向けに留める。

**ランチャー集約の例**（パターン2 の実体）:

```bash
claude \
  --add-dir <Share> \
  --settings <Share>/.claude/settings.json \
  --mcp-config <Share>/.mcp.json
# ＋ 環境変数 CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 を export（CLAUDE.md/rules 読込）
```

このランチャースクリプト自体は作業リポジトリ直下で実行する必要があるため、**パターン3**（別リポジトリから手動配置）で配る。

### `--add-dir` 例外ロード一覧（正本）

> `--add-dir`／`/add-dir` で追加ディレクトリの `.claude/` から自動ロードされる構成要素の**正本**。各成果物の同種の早見表（[01編 §4 調査結果](../02.配布物の開発・テスト/01.Plugin・Marketplace編/Plugin・Marketplace配布物の開発・テスト_調査結果.md)・[02編 §2 調査結果](../02.配布物の開発・テスト/02.Marketplace外資産編/Marketplace外資産の開発・テスト_調査結果.md)・[02手順書 §3](../02.配布物の開発・テスト/02.Marketplace外資産編/Marketplace外資産_開発・テスト_手順書.md)）は運用早見であり、**版依存の事実が食い違った場合は本表を優先**する（根拠 `docs/permissions`「Additional directories grant file access, not configuration」表）。

| 資産 | 自動ロード | 条件・版依存 |
|---|:---:|---|
| `skills/`（`.claude/skills/`） | ✅ | live reload。`--add-dir`／`/add-dir` 限定 [\[25\]](#ref-25) |
| `agents/`（subagents・`.claude/agents/`） | ✅ | **v2.1.178+。v2.1.165 までは非ロード** [\[75\]](#ref-75) |
| `enabledPlugins` / `extraKnownMarketplaces` | ✅ | `settings.json` **および `settings.local.json`** の**この2キーのみ** [\[41\]](#ref-41) |
| `commands/`（`.claude/commands/`） | ✅ | **v2.1.235 版(2026-08-19) で追加**。**live reload なし**（再起動が要る）。追加ディレクトリとプロジェクトで同名コマンドがある場合は**プロジェクト側が優先** [\[77\]](#ref-77) |
| `CLAUDE.md` / `.claude/rules/` / `CLAUDE.local.md` | △ | `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` 時のみ（all-or-nothing）[\[26\]](#ref-26)。`CLAUDE.local.md` はさらに `local` setting source が有効であること（既定で有効）が要る [\[77\]](#ref-77) |
| `settings.json` のその他キー（permissions/hooks/env）・`output-styles/` | ❌ | 結合不可。物理配置か直接起動で |

> **版境界の記録**: 本表の「自動ロードされる構成要素」は**増える方向に動いている** —— skills のみ（〜v2.1.165）→ ＋subagents（v2.1.178+）→ ＋commands（v2.1.235 版で確認）。**`--add-dir` を「共有境界」の設計前提に使っている箇所は、CLI 更新のたびに想定より広く読まれる可能性がある**（＝`<Share>` に置いたものが意図せず作業リポジトリのセッションへ入り込む）。共有境界を厳密に保ちたい場合は `--add-dir` ではなく物理配置・層2・層3 を選ぶこと。

> `permissions.additionalDirectories` **設定値**経由ではこれら例外は**一切**読まれない（ファイルアクセス付与のみ）。自動ロードは `--add-dir` フラグ／`/add-dir` コマンド限定 [\[25\]](#ref-25)。
