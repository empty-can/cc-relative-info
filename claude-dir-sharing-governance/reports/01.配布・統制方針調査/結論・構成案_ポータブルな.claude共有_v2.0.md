## §0 エグゼクティブサマリ

### 結論

**`.claude/` をひとつの Git リポジトリにし、そのリポジトリを作業リポジトリの `.claude/` ディレクトリとして clone する。作業種別はブランチで切り替える。**（＝**案C-1**。詳細は [§5](#recommend)）

```txt
<共有 .claude リポジトリ>              ← メンテナー 1〜2 名が管理
├── main                              ← チーム全体で常に要る資産
├── java/base                        ← java 系リポジトリ群で共通
├── java/design ・ java/coding ・ java/ut
└── python/base ・ python/…

<作業リポジトリ>
├── .claude/        ← 上記リポジトリのクローン。作業リポ側では .gitignore 対象
├── CLAUDE.md       ← このリポジトリ固有の指示（.claude/ の外）
└── start_claude_code.ps1   ← ランチャー（fetch → switch → reset --hard → 起動）
```

この形なら **`--add-dir` も `--settings` も環境変数も要らない**。資産は作業リポジトリの `.claude/` にそのまま**実体として存在する**ので、Claude Code から見れば「ごく普通の project スコープ」であり、条件付きロードにも起動フラグにも依存しない。

### 3 つの問いへの回答

| 問い | 回答 |
|---|---|
| **問1**: `<Prjルート>\.claude` を Marketplace の仕組みで配布できるか | **No（部分的にのみ可）**。Marketplace で配れるのは機能・拡張資産と plugin 専用コンポーネントに限られ、`CLAUDE.md` / `rules` / `permissions` は plugin では運べない（[§2](#where)） |
| **問2**: 最小・ポータブルな `.claude/` を「Marketplace のように」共有する単一ベストプラクティスは存在するか。無ければ設計せよ | **単一の既製ベストプラクティスは存在しない**。単一チャネルで全資産を運ぶ手段がないため。**設計した答えが案C-1**（[§5](#recommend)）。**この「存在しない」は、公式ドキュメントが記載する配布機構を全経路棚卸しした範囲での結論**である（検討して外した経路は [付録C](#appendix-c)。**公式以外のコミュニティ事例・他社事例は調査していない**＝[§8-1](#sec-8-1)） |
| **問3**（v2.0 で追加）: 作業種別ごとに必要な資産だけを載せる出し分けは、条件付きロードで実現できるか | **保証が要る出し分けには使えない**。条件付きロードの発火契機は **Read ツールでの読み取りに限られる**（【実測】[§3-2](#conditional)）。**Bash の `cat` でも Grep でも発火しない。**「載らなくても作業が止まらない補足」には使えるが、**確実に届ける必要がある資産は「実体の置き場所」＝ブランチで分ける** |

### なぜこの形を選ぶのか

1. **条件付きロード（`paths:` 付き rule・サブディレクトリの `CLAUDE.md`／`skills`）は「必要なときに載る」保証がない** —— Bash の `cat` や Grep で読んでも発火しない【実測】
2. だから**出し分けは「条件」ではなく「実体の置き場所」で行う**。**置き場所の切替を既存の道具で賄える**のが **git のブランチ**である（新しい機構をチームに持ち込まずに済む）
3. **実体を「作業リポジトリの `.claude/`」に置くのは、`--add-dir` では `permissions` が届かないから** —— 追加ディレクトリの `settings.json` から読まれるのは `enabledPlugins` / `extraKnownMarketplaces` の 2 キーだけで、`deny` を効かせるには `--settings` による二重化が要る（[§6-2](#sec-6-2)）
4. **`.claude/` を作業リポジトリから gitignore して入れ子 clone しても、資産は普通どおりロードされる**【実測】—— この一点が案C-1 の土台

### §0-1 なぜ書き直すのか（v1.2 を増改築しない理由）

v1.2 は次の 2 つを前提に全体が組まれていた。

1. **配布経路は 層1（commit）／層2（plugin）／層3（managed）／`--add-dir`（補助）の 4 分類で尽きる**
2. **条件付きロード（`rules` の `paths:`・サブディレクトリの `.claude/`）は「必要なときだけ載る」機構として使える**

2026-09-14 時点で**どちらも成立しない**。

- **1 について**: 層の外側に経路が増えた。claude.ai アカウント同期 skill、Organization settings 経由の plugin 配布、`managedMcpServers`（v2.1.259+）[\[26\]](#ref-26) など、「層1〜3」の枠に収まらない経路が並立している。4 分類を出発点に据えると、これらが常に例外扱いになる。**ただし破棄するのは「4 分類で尽きる」という網羅性の主張だけ**であり、**層1／層2／層3 という語そのものは本書でも引き続き使う**（強制力の段階を指す用語としては有効なため）
- **2 について**: **条件付きロードの発火契機が Read ツールに限定される**ことが実測で判明した（[§3-2](#conditional)）。Bash 経由の読み出しや Grep では載らない。v1.2 の §推奨・context コスト表はこの前提の上に立っており、**注記の追加では読者の誤解を防げない**

加えて、v1.2 は 4 つの基準スナップショット（BASE-A/B/C/D）に出典が分散し、再照合のたびに 4 ファイルを突き合わせる必要があった。v2.0 は **BASE-D 単一基準**に統一する。

> **v1.2 を削除しない理由**: v1.2 の `[1]`〜`[104]` は commit ハッシュで固定された基準に対する出典であり、**今も壊れていない**。他成果物からのリンク（`#adddir-exceptions`・`#adddir-controls`・`#appendix-a` 等）も生きている。v1.2 は「2026-06〜2026-09 に何がどこまで分かっていたか」の時点記録として保持する。**設計判断の根拠には v2.0 を使うこと。**

## §1 前提情報：Claude Code が読む資産と、その置き場所

配布設計の前に、そもそも何がどこに置かれるのかを押さえる。**ここでは配置場所の把握だけを目的**とし、どう配るかは [§2](#where) 以降で扱う。

> 急ぐ読者は [§3](#load) か [§5](#recommend) へ。本節は資産の所在を確認したい時の参照用。

<a id="prereq-a"></a>

### §1-1 `~/.claude/` 配下（個人・全プロジェクト共通）

home の `~/.claude/`。個人の全プロジェクトに適用される（Windows は `%USERPROFILE%\.claude`。`CLAUDE_CONFIG_DIR` で変更可）。**チームが配る経路は無い**[\[1\]](#ref-1)。

| フォルダ | 資産 | 説明 |
|---|---|---|
| `.` | `CLAUDE.md` | 全プロジェクト共通の個人指示 |
| `rules/` | `*.md` | 全プロジェクト共通のトピック別指示。**project rules より先に読まれる（＝project が優先）**[\[14\]](#ref-14) |
| `.` | `settings.json` | 個人の既定 settings（permissions / hooks / env / モデル） |
| `skills/<name>/` | `SKILL.md` ＋補助ファイル | 個人スコープの skill [\[5\]](#ref-5) |
| `commands/` | `*.md` | 個人スコープのコマンド（フラット単一ファイル） |
| `output-styles/` ・ `agents/` ・ `workflows/*.js` | `*.md` / `*.js` | 個人スコープの output-style / subagent / ワークフロー |
| `agent-memory/<name>/` | 永続メモリ | subagent の永続メモリ |
| `themes/` ・ `keybindings.json` | `*.json` | 個人のテーマ・キーバインド（global 専用） |
| `projects/<project>/memory/` | auto memory | Claude のセッション横断自己メモ（global 専用） |
| `plugins/` | install キャッシュ | install 済み plugin・clone 済み marketplace のキャッシュ [\[3\]](#ref-3) |
| `skills/synced/` | claude.ai 同期 skill | **`synced` は予約名**。enterprise / 個人 / project いずれの skills 配置でも、この名前の自作 skill は**黙ってスキップされる**[\[5\]](#ref-5) |

### §1-2 各プロジェクト直下の `.claude/` 配下（project スコープ）

**案C-1 が使う場所はここ。** リポジトリの `.claude/` 配下。

| フォルダ | 資産 | 説明 |
|---|---|---|
| `.` | `CLAUDE.md` | プロジェクト指示。root の `./CLAUDE.md` でも可（[§1-3](#prereq-c)）[\[11\]](#ref-11) |
| `rules/` | `*.md` | トピック単位の指示。**`.md` は再帰的に発見される**ので `frontend/` `backend/` 等のサブディレクトリに整理できる。`paths:` でファイル種別にゲート可能（**ただし [§3-2](#conditional) の制約に注意**）[\[14\]](#ref-14) |
| `.` | `settings.json` | permissions / hooks / env / モデル既定値。**スコープと優先順位の全体像は settings ページの一覧を参照**[\[24\]](#ref-24) |
| `.` | `settings.local.json` | 個人用オーバーライド。**git リポジトリルート基準で読み書きされる**（v2.1.211+）が、**Windows など Claude Code がリポジトリルートを使わないケースは例外**[\[22\]](#ref-22)。**gitignore は自動ではない**——Claude Code が*自分で書き込んだ*ときにのみ global git excludes へ追記する |

## §2 資産をどこに置くか（配置先と、そこで運べるもの）

**「どのチャネルで配るか」ではなく「どこに実体を置くか」で整理する。** 配布チャネルという抽象を先に立てると、層の外側に生えた経路（claude.ai 同期・Organization settings）が常に例外になるため、v2.0 は**置き場所を主語にする**。

### §2-1 置き場所は 6 つ

| # | 置き場所 | 実体の所在 | 誰が更新するか | 強制力 |
|---|---|---|---|:---:|
| **P1** | **作業リポジトリの `.claude/`（＝案C-1 の共有リポジトリのクローン）** | 共有 `.claude` リポジトリ | メンテナー（1〜2 名） | なし |
| **P2** | 作業リポジトリの root `CLAUDE.md` / `.mcp.json` | 作業リポジトリ | そのリポジトリの担当者 | なし |
| **P3** | plugin（marketplace 経由 or `@skills-dir` 型） | plugin リポジトリ | plugin の管理者 | 弱（`enabledPlugins` で誘導） |
| **P4** | managed settings ディレクトリ（層3） | 組織の配布基盤 | 組織の IT 管理者 | **最高（上書き不可）** |
| **P5** | `~/.claude/` | 各自の端末 | 各自 | 各自の自由 |
| **P6** | claude.ai アカウント（同期 skill・Organization settings） | claude.ai | 組織の Owner | プラン依存 |

> **v1.2 の「層」との対応**（[§0-1](#why-rewrite) のとおり、層という語そのものは引き続き使う）
>
> | v1.2 の層 | v2.0 の置き場所 | 備考 |
> |---|---|---|

### §3-2 条件付きロード —— **発火契機は Read ツールに限られる**

**本書で最も重要な事実。**

公式は 3 箇所で「条件付きで載る」機構を説明しているが、**どのツールでの read かを限定していない**。

| 機構 | 公式の表現（原文） | 出典 |
|---|---|---|
| `paths:` 付き rule | "Path-scoped rules trigger when Claude **reads files** matching the pattern, not on every tool use." | [\[15\]](#ref-15) |
| サブディレクトリの `CLAUDE.md` | "Instead of loading them at launch, they are included when Claude **reads files** in those subdirectories." | [\[12\]](#ref-12) |
| サブディレクトリの `.claude/skills/` | "They load the first time Claude **reads or edits a file** in that subdirectory and stay available for the rest of the session." | [\[7\]](#ref-7) |

実測すると、この "reads" は **Read ツールでの読み取りだけ**を指す。**Bash の `cat` でも Grep でも発火しない。**

> **【実測 2026-09-14 / CLI 2.1.266】発火契機の判定**
>
> **手法**: 1 つのサブディレクトリ `sub/` に、`paths: ["**/*.probefile"]` の rule がマッチする対象ファイル・`sub/CLAUDE.md`・`sub/.claude/skills/subskill/` の 3 つを同時に置き、**先行操作の種類だけを変えて 5 セッション（対照群を含む）**起動した（`claude --model haiku -p`）。各セッションは**先行操作に使うツールと `Skill` ツールだけを許可**し、合言葉を読みに行けないようにした。rule と `CLAUDE.md` は合言葉の完全一致で、skill は **`Skill` ツールの起動成否**で判定した。

| 先行操作 | `paths:` 付き rule | サブディレクトリの `CLAUDE.md` | サブディレクトリの `.claude/skills/` |
|---|:---:|:---:|:---:|
| **なし（対照群）** | ❌ | ❌ | ❌ |
| **Read ツールで読む** | ✅ **発火** | ✅ **発火** | ✅ **発火** |
| **Bash ツールで `cat` する** | ❌ | ❌ | ❌ |
| **Grep ツールで検索する** | ❌ | ❌ | ❌ |
| **Edit ツールで編集する（Read を許可しない）** | —（Edit 自体が Read 先行を要求するため実施不能） | —（同上） | —（同上） |

**別途、nested skill についてのみ測った条件**（2026-09-14・同 CLI）:

| 先行操作 | サブディレクトリの `.claude/skills/` |
|---|:---:|
| `/reload-plugins` を実行する | ❌（**plugin とその同梱資産しか管轄しない**） |
| 起動時に `--add-dir <サブディレクトリ>` を付ける | ✅ |

> **Edit ツール単独では発火しえない。**【実測】Read を許可せず Edit だけを許可したセッションで `sub/target.probefile` の編集を試みたところ、**Edit 自体が `File has not been read yet. Read it first before writing to it.` で失敗した**（対象が作業ディレクトリ配下でも同じ）。**Edit には必ず Read が先行する**ので、公式表現 "reads **or edits**" [\[7\]](#ref-7) の "edits" は Read 契機に包含される。**したがって「Read が発生しなければ載らない」で必要十分であり、発火契機の検証は Read についてだけ行えばよい。**
>
> **逆に、Read を経ない編集では発火しない。** Bash の `sed -i` / `python -c` / リダイレクトによる書き換えは Read ツールを通らないため、**ファイルを編集していても条件付きロードは起きない**（上表の Bash 行と同じ理屈）。一括置換やコード生成を Bash で回す運用では、`paths:` 付き rule は最後まで一度も載らない。
>
> **セッション中の `/add-dir <サブディレクトリ>`（v2.1.257+）は公式記載** [\[21\]](#ref-21)。ただし**ヘッドレス（`claude -p`）では使えない**ため（`/add-dir isn't available in this environment.`）、**対話セッション限定の手段**である【実測】。

> **判定を誤りやすい点（実測で踏んだ罠）**
>
> - **`--debug` のログには nested ロードが記録されない。** ログの有無でロードの有無を判定できない
> - **モデルの自己申告は信用できない。** 検証中、対象モデルが「skill はロードされています」と答え、ロードされた理由まで作文した（実際は skill 一覧に増えていなかった）。**機能的な確認（Skill ツールを実際に起動して成否を見る）に切り替えて初めて正しい判定ができた**
> - `/add-dir` は**ヘッドレス（`-p`）では使えない**。対話セッションでのみ有効

### §3-3 この章の結論

> ### **届けたい資産は、条件ではなく「実体の置き場所」で分ける。**

条件付きロードは「context を節約するための最適化」としては使える。だが**「必要なときに必ず載る」ことを前提にした設計の基盤にしてはならない。** Bash 中心の探索をする運用（コードベース調査・ログ解析・スクリプト実行が主体の作業）では、**`paths:` 付き rule は一度も載らないまま 1 セッションが終わりうる**。

**設計上の帰結:**

| やりたいこと | ❌ 使ってはいけない | ✅ 使う |
|---|---|---|
| 作業種別ごとに資産を出し分ける | `paths:` 付き rule、サブディレクトリ `.claude/` | **共有 `.claude` リポジトリのブランチ切替**（[§5](#recommend)） |
| ファイル種別ごとに補足指示を足す | —— | `paths:` 付き rule で**可**（**Read ツールで読んだときしか載らない**ので、載らなくても作業が止まらない内容に限る） |
| 常に効かせたいチーム規約 | `paths:` 付き rule | `paths:` **なし**の `rules/*.md` か `CLAUDE.md` |

> **この制約は、使う方向によって重さが違う。**
>
> - **削減方向（載る量を減らしたい）には安全** —— 条件付きロードが不発でも結果は「載らない」だけで、context が予想外に増えることはない。**最悪でも意図した削減が効きすぎるだけ**である
> - **保証方向（必ず載せたい）には使えない** —— 不発の結果が「指示が届いていないのに、届いている前提で作業が進む」になる。**失敗が静かで、事後に検知する手段も無い**
>
> したがって `paths:` 付き rule を禁止するのではなく、**「載らなくても作業が止まらない内容」に限る**という線引きにする。

> **⚠ `rules/` の symlink 共有も同じ理由で採らない**: `.claude/rules/` は symlink に対応しているが、**作業ディレクトリ外を指す symlink は「外部 import」扱い**になり、プロジェクトで外部 import を承認するまでロードされず、**承認後も `paths:` を持つ rule は載らない**[\[16\]](#ref-16)。共有の手段としては承認フローと非ロードの二重の穴がある。

### §3-4 ロードされる前に「実行される」もの（trust の前後）

配布設計では**「いつ trust するか」が挙動を変える**。公式は trust 前後で何が動くかを表で明示している [\[23\]](#ref-23)。**列は「そのフォルダ自体を trust していない 2 つの状況」**である。

| リポジトリが供給するもの | 親フォルダしか trust していない場合 | `claude -p` / SDK 実行（ダイアログが出ない） |
|---|---|---|
| `settings.json` の **hooks**・**`env` ブロック**・`apiKeyHelper` 等のヘルパーコマンド、および project skill の `hooks` / `allowed-tools` | **実行される**（"Used"） | **実行される**（skill の `allowed-tools` はどのセッション種別でも trust に阻まれない） |
| **`permissions.allow` ・ `additionalDirectories`** | **使われない。** trust ダイアログが改めて表示され、内容が列挙される | **使われない。** stderr に `this workspace has not been trusted` 警告 |
| project subagent の frontmatter hooks、project の `@skills-dir` plugin、**`extraKnownMarketplaces`** | **使われない。しかもダイアログも出ない** | **使われない** |
| subagent frontmatter のインライン `mcpServers` | **使われない。ダイアログも出ない** | **使われない** |
| `.mcp.json` のサーバー | 接続前に**毎回確認される**（リポジトリ自身の承認は数に入らない） | **確認せず接続される**（"Connected without asking, approved or not"） |
| `.mcp.json` サーバーの `headersHelper` | trust を承認するまで**実行されない**（静的 `headers` だけで接続） | **実行されない**（stderr に `headersHelper not run`） |

> **⚠ trust は「git リポジトリルート」を鍵にし、入れ子リポジトリはそこから除かれる。** 公式は trust の単位を **「そのリポジトリの中に入れ子になった git リポジトリ（submodule など）を除いた、git リポジトリのルート」**と定義している [\[23\]](#ref-23)（L81157）。**案C-1 の `.claude/` はまさにその「入れ子になった git リポジトリ」の形状**であり、作業リポジトリを trust しても**その trust には含まれない**。
>
> **ただし公式は、この場合の扱いも書いている。**「上表の**『親フォルダしか trust していない』列は入れ子リポジトリの内側には適用されない**。対話セッションでは Claude Code が**その入れ子リポジトリについて trust ダイアログを表示**し、そこでの `claude -p` / SDK 実行は `claude -p` 列に従う」[\[23\]](#ref-23)（L81180）。
>
> **したがって公式仕様上の想定はこうなる。**
>
> | 起動の仕方 | 共有 `.claude/settings.json` の `permissions.allow` |
> |---|---|
> | **対話セッション** | **`.claude/` について trust ダイアログが出る。承認すれば適用される**（＝メンバーは trust ダイアログを 2 回見る） |
> | **`claude -p` / SDK** | **適用されない**（ダイアログが出ないため。stderr に警告が出る） |
>
> **`deny` / `ask` はこの影響を一切受けない** —— trust 非依存で常に適用される [\[23\]](#ref-23)（L81153）。**「危険なコマンドを塞ぐ」という統制側の主張は、trust の不確定性から独立している。**
>
> **実測は未了である。** `claude -p` は trust ダイアログを出さない [\[23\]](#ref-23)（L81161）ため、**ヘッドレスでは検証できない**。対話セッションでの確認手順を未検証項目 **V7**（[§8-2](#sec-8-2)）に置いた。**ダイアログが実際に出るか・1 回の承認で足りるかは、展開前に確認すること**（周知文言と CI 運用が変わる）。
>
> **逃げ道**: どうしてもダイアログを経ずに trust させたい場合、`~/.claude.json` の `projects["<パス>"].hasTrustDialogAccepted` を `true` にする手段が公式に案内されている [\[23\]](#ref-23)。**onboarding スクリプトに組み込める**。

> **⚠ `extraKnownMarketplaces` は trust 前に使われず、しかもダイアログも出ない**（上表 3 行目）。**案B（plugin 併用）を案C-1 と組み合わせるとき、共有 `.claude/settings.json` に置いた marketplace 宣言は trust 承認まで効かない。** plugin の導入は onboarding 手順に明示的に組み込む（[§5-2](#assignment)）。

> **案C-1 での意味（hooks）**: 共有 `.claude` リポジトリの `settings.json` に hooks を置くと、**ブランチを切り替えた直後・trust 前でも走る**。ブランチごとに hooks を変える設計は、切り替え事故が「知らないスクリプトが動く」に直結する。**hooks は原則 `main` ブランチに置き、作業種別ブランチでは増やさない**（[§5-7](#cautions)）。

> ### ⚠ 案C-1 では `settings.json` の性質が変わる —— 導入前にチームへ周知する
>
> 従来 `.claude/settings.json` は「そのリポジトリを触る人が、自分のために置いた設定」だった。**案C-1 ではそれが「共有リポジトリから全メンバーへ配られる設定」になる。** ファイル名も書式も同じまま、**影響範囲だけが 1 人から全員へ広がる。**
>
> 帰結として最も重いのが **`env` ブロック**である。
>
> - `env` の値は**上表のとおり trust 前でも `claude -p` でも適用・実行される**
> - 共有リポジトリに commit された `env` は**全メンバーの端末へ配られ、git 履歴に恒久的に残る**
>
> したがって **共有 `.claude/settings.json` の `env` に秘匿値を書いてはならない。**
>
> | 分類 | 例 | 置き場所 |
> |---|---|---|
> | **分類A: 秘匿値** | API キー・認証トークン・パスワード・組織外秘の内部 URL | **OS 環境変数**（各自の端末で設定。共有リポには入れない） |
> | 分類B: 非秘匿の共通値 | モデル既定値・タイムアウト・機能フラグ・公開ドキュメントの URL | 共有リポの `settings.json` の `env` に置いてよい |
> | 分類C: 個人ごとに異なる非秘匿値 | ローカルのツールパス等 | `.claude/settings.local.json`（gitignore 済み） |
>
> **この分類は既存ランチャーの方針（分類A は OS 環境変数）をそのまま継承する**（[§5-6](#sec-5-6)）。

## §4 どう絞るか（統制機構）

配ることと**絞ること**は別問題である。ここでは「載る量を減らす」機構と「メンバーに上書きさせない」機構を分けて整理する。**チームが自前で握れるものと、組織の IT 基盤がないと握れないものの線引き**が本節の要点。

<a id="sec-4-1"></a>

### §4-1 載る量を絞る機構

| 機構 | 効き方 | 誰が握れるか | 制約 |
|---|---|---|---|
| **置き場所そのもの（＝案C-1 のブランチ）** | 置いていないものは読まれない。**最も確実** | **チーム** | 設計とレビューの規律に依存 |
| `claudeMdExcludes` | `CLAUDE.md` / `rules` を**パス・glob 単位**で除外。**user / project / local / managed の全スコープで設定可・commit 可・配列はスコープ間でマージ**[\[18\]](#ref-18) | **チーム（project へ commit）** | 静的（タスク単位の出し分け不可）。**managed policy の `CLAUDE.md` は除外できない**[\[17\]](#ref-17) |
| `paths:` 付き rule | マッチしたファイルを **Read ツールで読んだときだけ**載る | チーム | **[§3-2](#conditional) の制約**。載らない前提で書く |
| `--setting-sources` から `project` を外す | フラグ追加ディレクトリの skills / commands / subagents は `project` setting source 経由なので全部落ちる [\[20\]](#ref-20) | 起動側（ランチャー） | **作業リポジトリ自身の project 設定も同時に落ちる**（全か無か） |
| bare mode（`--bare`） | hooks / skills / commands / subagents / plugins / MCP / auto memory / `CLAUDE.md` の**自動発見を一括でスキップ**。**`--add-dir` ディレクトリだけは部分例外**で、その `.claude/skills/` は載り `commands` / `agents` は載らない [\[36\]](#ref-36)[\[20\]](#ref-20) | 起動側（headless） | **対話運用向けではない**（CI・スクリプトで再現性を得るためのモード） |
| `--safe-mode` / `CLAUDE_CODE_SAFE_MODE=1` | `CLAUDE.md` / skills / plugins / hooks / MCP / commands / agents / output-styles / workflows を**一括で無効化**して起動 [\[34\]](#ref-34)[\[10\]](#ref-10) | 起動側 | **切り分け用。常用しない**（managed のポリシーは適用され続ける） |
| `strictPluginOnlyCustomization` | skills / agents / hooks / MCP を **plugin ＋ managed 由来のみ**に制限（`true` で 4 種全部、配列で個別指定） | **層3（managed）のみ**[\[28\]](#ref-28) | **Scope が Managed 固定。チームレベルでは使えない** |

> **チームが主体的に握れるのは上 3 つだけ。** 下 4 つは起動側または組織側の機構であり、チームの設計手段には数えない。

> **📊 機構別の context コスト** —— 「どこに置くか」はロード経路だけでなく**常時消費する context 量**でも決まる。
>
> | 資産種別 | 常時消費する量 | 削減の効き |
> |---|---|---|
> | `CLAUDE.md` | **全文を常時**ロード | **最も効く**。`claudeMdExcludes` で絞る。公式も **1 ファイル 200 行以下**を推奨し、4 MiB 超はスキップされる [\[11\]](#ref-11) |
> | `rules/*.md`（`paths:` なし） | **全文を常時** | **効く**。ブランチ分割（案C-1）で絞る |
> | `rules/*.md`（`paths:` あり） | マッチ時のみ全文 | 条件付き（[§3-2](#conditional)） |
> | `skills/` | **`name` ＋ `description` のみ**（本体は起動時に読む） | **薄い**。ただし**数が多いと description が切り詰められ選択精度が落ちる**とされる〔**未実測**——切り詰めが始まる件数も切り詰め方も本書では測っていない（[§8-2](#sec-8-2) V4）〕ため、精度維持の観点では分割に意味がありうる |
> | `commands/` ・ `agents/` | 呼ばれたときのみ | —— |
>
> **含意**: 「context 削減」を目的に skills を外出ししても効果は薄い。**削減が効くのは `CLAUDE.md` と `rules/`**。
>
> **⚠ `@path` import は削減にならない**: `CLAUDE.md` を `@path` で分割しても、**import されたファイルは起動時にそのまま context に載る**[\[11\]](#ref-11)。整理には役立つが節約にはならない。

<a id="sec-4-2"></a>

### §4-2 上書きさせない機構（＝強制）

**強制できるのは層3（managed settings）だけ。** 層1（commit）と `--add-dir` は強制力ゼロ、層2（plugin）も弱い（`enabledPlugins` で誘導するのみで、install も無効化も各自の自由）。

> **⚠ ただし「層1 は強制力ゼロ」は `deny` には当てはまらない。** 層1 で配った `permissions.deny` / `ask` は、**メンバーが `settings.local.json` で明示的に上書きしない限り確実に効く**（しかも **trust 非依存**＝[§3-4](#sec-3-4)）。層3 が要るのは「**メンバーによる上書きを不可能にしたい**」ときであって、「deny を効かせたい」だけなら層1 で足りる。
>
> 逆に、**許可を事前に付与する方向（`permissions.allow`）は trust 依存**である（[§3-4](#sec-3-4)）。**塞ぐ統制は確実・あらかじめ許す利便は不確実**、という非対称を前提に設計する。

層3 には 3 系統あり、**必要な基盤コストが大きく異なる**。

| 系統 | 仕組み | 前提 | 基盤コスト |
|---|---|---|---|
| **(1) server-managed** | claude.ai admin console から中央 push | **Claude for Teams / Enterprise 契約**[\[31\]](#ref-31)。設定操作には **Owner または Primary Owner ロール**が必要。**Bedrock / Google Cloud's Agent Platform / Microsoft Foundry / Claude Platform on AWS では非対応**[\[29\]](#ref-29)。**組織全体へ一律に配る機構であり、チーム／グループ単位の出し分けは現時点でできない**（グループ単位のポリシー割当ができるのは (3) gateway-managed のみ）[\[30\]](#ref-30) | **極低**（MDM 不要） |
| **(2) endpoint-managed** | MDM（Jamf / Kandji / Intune / GPO 等）で `managed-settings.json` を OS パスへ配布、または plist / レジストリへポリシー配布 [\[41\]](#ref-41) | 管理者権限・MDM 基盤 | **高**（MDM 運用）〜中（手動配置） |
| **(3) gateway-managed** | 自ホスト型 Claude apps gateway が remote managed settings の同等配信を担う。gateway にサインインしたクライアントは `api.anthropic.com` ではなく gateway から取得。IdP グループ単位のポリシー割当も可 [\[30\]](#ref-30) | 自ホスト gateway の運用。第三者プロバイダ（Bedrock / Agent Platform / Foundry）向け | **中** |

> **統制キーの全件一覧は [付録A](#appendix-a)**。どのキーが managed 専用か、複数の managed ソースがあるときどれが勝つかをまとめてある。

> **(3) は (2) を不要にはしない。** gateway へ接続させる設定（`forceLoginMethod` / `forceLoginGatewayUrl`）自体は gateway から push できないため、**初期ブートストラップだけ endpoint-managed に残る**。

> **層3 が届いているかの確認**: `claude doctor` の **`Organization policy` 行**に、ポリシーをどこから読み込んだか（読み込めなかった理由）が出る（**v2.1.261+**）。セッション中は `/status` でも同じ行が見られる [\[26\]](#ref-26)。

<a id="sec-4-3"></a>

### §4-3 層3 を重ねたときの相互作用 —— 「無視される」ではなく「起動時に落ちる」

層1+2 で組んだランチャーに後から層3 が重なると、**セッションが起動しなくなる経路が 2 本ある**。

| 層3 側の設定 | 起動時に拒否されるフラグ | 症状 |
|---|---|---|
| `disableSideloadFlags: true`（v2.1.193+）[\[26\]](#ref-26) | `--plugin-dir` / `--plugin-url` / `--agents` / `--mcp-config` | 起動時に拒否。cloud セッションでは in-process `type: "sdk"` 以外の MCP サーバーを落として起動する |
| `managed-mcp.json` を配備 [\[35\]](#ref-35) | `--mcp-config` / `--strict-mcp-config` | `You cannot dynamically configure MCP servers when an enterprise MCP config is present` で **exit** |

> **案C-1 はこの罠を踏まない。** 案C-1 のランチャーは**起動フラグを一切使わない**（`--add-dir` も `--settings` も `--mcp-config` も不要）。層3 を敷いている配布先でもそのまま成立する。これは `--add-dir` 方式に対する案C-1 の明確な優位点である（[§6](#alternatives)）。

## §5 推奨構成（案C-1）

<a id="sec-5-1"></a>

### §5-1 全体像

**`.claude/` をひとつの Git リポジトリにし、それを作業リポジトリの `.claude/` として clone する。作業種別はブランチで切り替える。**

```txt
■ 共有 .claude リポジトリ（メンテナー 1〜2 名が管理）

  main                    チーム全体で常に要る資産
   ├── java/base         java 系リポジトリ群で共通
   │    ├── java/design
   │    ├── java/coding
   │    └── java/ut
   └── python/base
        └── python/…

  すべてのブランチは main を先祖に持つ。main が更新されたら rebase で取り込む。

■ 作業リポジトリ（各メンバーの手元）

  <work-repo>/
  ├── .claude/                  ← 共有リポジトリのクローン。作業リポの .gitignore 対象
  │   ├── CLAUDE.md             （切り替えたブランチの内容になる）
  │   ├── rules/*.md
  │   ├── skills/ agents/ commands/
  │   ├── settings.json
  │   └── settings.local.json   ← 個人設定。共有リポ側で gitignore（後述）
  ├── CLAUDE.md                 ← このリポジトリ固有の指示
  ├── .mcp.json                 ← このリポジトリ固有の MCP（要るなら）
  └── start_claude_code.ps1     ← ランチャー
```

**`--add-dir` / `--settings` / `--mcp-config` / `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD` はいずれも不要になる。**

<a id="sec-5-2"></a>
<a id="assignment"></a>

### §5-2 資産の振り分け

| 資産 | 置き場所 | 理由 |
|---|---|---|
| チーム共通・作業種別を問わず要るもの | 共有リポの **`main`** | 全ブランチの先祖なので必ず届く |
| 作業種別ごとに要るもの | 共有リポの**対応ブランチ** | 載せたくないブランチには実体が無い |
| **作業リポジトリ固有の指示** | 作業リポの**ルート `CLAUDE.md`** | `.claude/` は共有リポなので、リポジトリ固有を混ぜるとブランチが破裂する |
| **作業リポジトリ固有の機能資産**（skill / agent / hooks） | **plugin**（P3） | 同上。plugin なら作業リポの `settings.json` から `enabledPlugins` で有効化できる。**ただし外部ソースの plugin は `enabledPlugins` だけでは入らず、メンバーの `claude plugin install` が要る**（[§6-2](#sec-6-2)）。また層3 で `allowManagedHooksOnly` が敷かれた環境では、**plugin 同梱の hooks は managed が `enabledPlugins` で明示的に force-enable したもの以外すべて落ちる**[\[28\]](#ref-28) |
| 作業リポジトリ固有の MCP | 作業リポの root `.mcp.json` | `.mcp.json` は root 直下にしか置けない |
| **環境変数（非秘匿）** | 共有リポ `settings.json` の `env` | モデル既定値・タイムアウト等。**全メンバーへ配られ git 履歴に残る**ことを前提に選ぶ |
| **秘匿値**（API キー・トークン・パスワード・組織外秘 URL） | **OS 環境変数**（各自の端末） | **共有リポには絶対に置かない。** `env` は trust 前・`claude -p` でも適用される（[§3-4](#sec-3-4)）。既存ランチャーの分類A と同じ方針 |
| 個人設定 | `.claude/settings.local.json` | **共有リポ側の `.gitignore` に必ず入れる**（後述） |

> **「作業リポジトリ固有」を `.claude/` に置かない**のがこの設計の肝。置いた瞬間、ブランチが「作業種別 × リポジトリ」の直積に膨らむ。

<a id="sec-5-3"></a>

### §5-3 ブランチ命名 —— 親ブランチ名をそのまま使ってはいけない

> **【実測 2026-09-14 / git 2.46.0】git の ref 仕様により、`java` ブランチと `java/design` ブランチは共存できない。**
>
> ```text
> $ git branch java master
> $ git branch java/design master
> fatal: cannot lock ref 'refs/heads/java/design': 'refs/heads/java' exists;
>        cannot create 'refs/heads/java/design'
> ```
>
> ref は `refs/heads/<名前>` というパスで保持されるため、`refs/heads/java` がファイルとして存在すると `refs/heads/java/` をディレクトリにできない（**D/F コンフリクト**）。これは git の根本的な制約である。**packed-refs（ref を個別ファイルではなく単一ファイル内のテキスト行として持つ形式）でも回避できない**〔**公式仕様上の推定・未実測**——packed-refs 状態での再現は測っていない。D/F 判定は ref 名の名前空間に対する検査であり、格納形式に依存しないと理解している〕。

**規約**: **すべてのブランチ名を「葉トークン」で終える。名前空間セグメントをそのままブランチ名にしない。**

| ❌ 不可 | ✅ 可 | 備考 |
|---|---|---|
| `java` ＋ `java/design` | **`java/base` ＋ `java/design`** | 推奨。`java/` 配下にまとまり、多くの Git クライアントでフォルダとして畳まれる |
| `java` ＋ `java/design` | `java` ＋ `java-design` | 平坦。階層が視覚的に分かりにくい |
| `java/design` ＋ `java/design/ut` | `java/design/base` ＋ `java/design/ut` | 3 段目も同じ規約が必要 |

> `base` は「この名前空間の共通ぶん」を表す予約語として決め打ちする（`common` 等でもよいが**チームで 1 つに固定する**）。`base` は `coding` / `design` / `ut` といった作業種別名よりアルファベット順で先に来るので、ブランチ一覧でも自然に先頭へ並ぶ。
>
> **本リポジトリ（`cc-relative-info`）の `feature/<X>` 規約と同じ構造**である——`feature` というブランチは作らず、常に `feature/` 配下に葉を作る。

<a id="sec-5-4"></a>

### §5-4 親ブランチへの追従は `rebase`

**方針: 子ブランチは親の更新を `rebase` で取り込む（`merge` は使わない）。**

**理由**（作業指示者判断・2026-09-14 確定）:

1. 多段の親子関係で「**全ブランチが先祖の更新を取り込めているか**」を**ブランチグラフで視覚的に把握できる**。取り込み済みなら一直線に並ぶので、反映漏れが一目で分かる。`merge` だとブランチ数に比例してグラフがスパゲッティ化し、漏れの検知が難しくなる
2. メンテナーは **1〜2 名の選任担当**。force-push の衝突リスクが実質的に無い
3. commit ハッシュの書き換わりによって支障が出る作業・欠落する維持管理情報が無い

> **⚠ この方針は「共有 `.claude` リポジトリ限定」である。** 通常の開発リポジトリや、多人数が同じブランチを触るリポジトリには**そのまま適用しない**。

#### 多段の伝播は `rebase.updateRefs` で一括

git 2.38+ の `rebase.updateRefs`（`--update-refs`）を使うと、**rebase 対象のコミットを指す中間ブランチも一緒に前進する**。

```bash
# メンテナー側。java/design を rebase すると java/base も一緒に動く
git switch java/design
git -c rebase.updateRefs=true rebase main
git push --force origin main java/base java/design
```

> **【実測 2026-09-14 / git 2.46.0】** 上記 1 回の rebase で中間ブランチが更新されることを確認した。
>
> ```text
> Successfully rebased and updated refs/heads/java/design.
> Updated the following refs with --update-refs:
>         refs/heads/java/base
> ```
>
> rebase 後、`git merge-base --is-ancestor main java/base` と `... main java/design` がいずれも成功（= 両方が main を取り込み済み）。

> **⚠ 更新されるのは「ローカルに存在するブランチ」だけ。**【実測】中間ブランチ `java/base` を**ローカルに持たないクローン**で同じ rebase を実行すると、`Updated the following refs` の行そのものが出ず、**中間ブランチは黙って取り残される**（エラーにならない）。
>
> **メンテナーは全ブランチをローカルに持った状態で作業すること。** 運用に組み込むなら、rebase 前に `git fetch --all --prune` ＋ 全リモートブランチのローカル追跡ブランチ作成をスクリプト化する。

> **⚠ リモート側の force-push 保護を確認する。** GitHub の branch protection 等で force-push が禁止されていると、この運用は成立しない。共有 `.claude` リポジトリは**メンテナー限定の force-push を許可する**設定にする。

> **⚠ 恒久設定にする場合**: `git config --global rebase.updateRefs true` を全メンテナーに入れると付け忘れが無くなる。ただし**他リポジトリの rebase 挙動も変わる**ので、`git -c` での都度指定かリポジトリローカル設定（`git config --local`）を推奨する。

#### `main` を更新したときの定常手順（メンテナー）

`rebase.updateRefs` が連れて上がるのは**同一系列の中間ブランチだけ**である。系列が複数あるなら**系列ごとに rebase する**。

**① 全ブランチを fetch し、ローカル追跡ブランチを作る**

```bash
git -C <shared-claude> fetch --all --prune
for b in $(git -C <shared-claude> branch -r --format='%(refname:short)' \
           | sed 's|^origin/||' | grep -v '^HEAD$'); do
  git -C <shared-claude> branch --track "$b" "origin/$b" 2>/dev/null || true
done
```

**これを飛ばすと中間ブランチが黙って取り残される**（上の ⚠ のとおり、エラーにもならない）。

**② 系列ごとに、その系列の「葉ブランチ」で rebase する**（`--update-refs` が中間を連れて上がる）

```bash
git -C <shared-claude> switch java/ut
git -C <shared-claude> -c rebase.updateRefs=true rebase main
git -C <shared-claude> switch python/coding
git -C <shared-claude> -c rebase.updateRefs=true rebase main
```

葉が並列に複数ある系列（`java/design` と `java/ut` が兄弟など）は、**葉の数だけ rebase する**。

**③ 取り残しが無いことを検査する**

```bash
git -C <shared-claude> branch --no-merged main
```

**出力が空であること**を確認する。1 行でも出れば、そのブランチは `main` を取り込めていない。**この検査を省くと、そのブランチを使うメンバーは古い規約のまま作業し続け、しかも誰も気づかない。**

**④ まとめて force-push する**

```bash
git -C <shared-claude> push --force-with-lease origin \
    main java/base java/design java/ut python/base python/coding
```

`--force` ではなく **`--force-with-lease`** を使う（他のメンテナーの push を踏み潰さないため）。

> **`main` は rebase の対象にならない。** 上の手順で `main` は常に rebase の**土台**であり、書き換えられることがない。したがって**リモートで `main` だけ force-push を禁止しても、この運用は壊れない**（[§5-7](#cautions)）。

<a id="mirror"></a>

### §5-5 消費側クローンは「読み取り専用ミラー」

メンバー側の `.claude/` は**編集しない前提**で運用する。更新は次の 3 コマンド。

```bash
git -C .claude fetch --all --prune
git -C .claude switch <ブランチ>
git -C .claude reset --hard "origin/<ブランチ>"
```

> **⚠ `git pull --ff-only` は使えない。**【実測 2026-09-14 / git 2.46.0】メンテナーが rebase するとハッシュが変わって分岐扱いになるため、`fatal: Not possible to fast-forward, aborting.`（**終了コード 128**）で**毎回失敗する**。壊れはせず止まるだけだが、定常運用が回らない。失敗後に `reset --hard` すれば正常に復旧することも確認済み。

**保護されるもの・されないもの**:

| 対象 | `reset --hard` 後 | 根拠 |
|---|---|---|
| `.claude/settings.local.json`（**untracked かつ ignore 済み**） | ✅ **残る**【実測】 | `reset --hard` は untracked / ignored ファイルに触らない |
| `.claude/settings.local.json`（**共有リポで 1 度でも commit されたことがある**） | ❌ **上書きされる** | tracked なので reset の対象になる |
| メンバーが `.claude/` 配下で加えたローカル変更 | ❌ **破棄される** | 設計どおり（ミラーなので） |

> **⚠ 共有リポジトリの `.gitignore` に `settings.local.json` を必ず入れること。** どこか 1 ブランチにでも commit された瞬間、次の `switch` で**全メンバーの個人設定が消える**。【実測】ignore 済み・untracked であれば `switch` と `reset --hard` を挟んでも残ることを確認した。

> **⚠ `reset --hard` の前に `git status --porcelain` を確認する。** ローカル変更が残っている場合、**切替先ブランチと内容が衝突すれば `switch` はその時点で失敗する**。衝突しなければ `switch` は成功し、変更を持ち越す——**が、直後の `reset --hard` でその変更は結局失われる**。**どちらの結末も避けたいので、`switch` より前に検査し、変更があれば警告して中断する。**

> **detached HEAD 方式は採らない**: `git checkout --detach origin/<branch>` なら `reset --hard` を避けられるが、ブランチ名が `HEAD` になり、**statusline で現在の作業種別が見えなくなる**。取り違え防止のほうを優先する。

<a id="sec-5-6"></a>

### §5-6 ランチャーの責務

**責務は 4 つだけ**: ①存在確認 ②ローカル変更の検査 ③同期 ④起動。**起動フラグを一切渡さない**のがこの設計の成果である。

以下は**最小例**であり、そのまま配布できる完成品ではない（既存ランチャーとの関係は後述）。**要点は「git の各呼び出しで終了コードを検査すること」**にある。

```powershell
# start_claude_code.ps1（Windows 版・最小例）
param([string]$Branch = "main")

# 作業リポジトリのルートを基準にする（§5-7「起動はルートから」）
Set-Location $PSScriptRoot

$ClaudeDir = Join-Path $PSScriptRoot ".claude"
$SharedUrl = "https://github.com/<org>/<shared-claude>.git"

# 1. 共有クローンの存在確認（無ければ clone）
if (-not (Test-Path (Join-Path $ClaudeDir ".git"))) {
    git clone --branch $Branch $SharedUrl $ClaudeDir
    if ($LASTEXITCODE -ne 0) {
        [Console]::Error.WriteLine("clone に失敗しました。中断します。")
        exit 1
    }
}

# 2. ローカル変更の検査（switch より前に）
$dirty = git -C $ClaudeDir status --porcelain
if ($LASTEXITCODE -ne 0) {
    [Console]::Error.WriteLine(".claude/ を git リポジトリとして読めません。中断します。")
    exit 1
}
if ($dirty) {
    [Console]::Error.WriteLine(".claude/ にローカル変更があります。更新を中止しました:`n$dirty")
    [Console]::Error.WriteLine("破棄してよければ: git -C .claude reset --hard; git -C .claude clean -fd")
    exit 1
}

# 3-a. fetch（失敗しても続行 ＝ オフラインでも起動できるようにする）
git -C $ClaudeDir fetch --all --prune
if ($LASTEXITCODE -ne 0) {
    Write-Warning "fetch に失敗しました。手元にある内容で起動します（最新でない可能性があります）。"
}

# 3-b. switch（失敗したら中断。ここで進むとブランチが静かに壊れる）
git -C $ClaudeDir switch $Branch
if ($LASTEXITCODE -ne 0) {
    [Console]::Error.WriteLine("ブランチ '$Branch' への切替に失敗しました。中断します。")
    exit 1
}

# 3-c. 現在ブランチが指定と一致することを確認してから reset --hard
$current = (git -C $ClaudeDir rev-parse --abbrev-ref HEAD)
if ($LASTEXITCODE -ne 0 -or $current.Trim() -ne $Branch) {
    [Console]::Error.WriteLine("現在のブランチ '$current' が指定 '$Branch' と一致しません。reset を中止します。")
    exit 1
}

git -C $ClaudeDir reset --hard "origin/$Branch"
if ($LASTEXITCODE -ne 0) {
    [Console]::Error.WriteLine("reset --hard に失敗しました。中断します。")
    exit 1
}

# 4. 起動（起動フラグは不要）
claude
```

> ### ⚠ 終了コードを検査しないと、ブランチが「静かに壊れる」
>
> **【実測 2026-09-14 / git 2.46.0】** `switch` の失敗を無視して `reset --hard` を続けると、**現在いるブランチの名前はそのままに、中身だけが別ブランチで上書きされる**。
>
> ```text
>     switch: fatal: invalid reference: does/not/exist
>     switch の終了コード: 128
>     reset: HEAD is now at bbffd4c other 版
>     reset の終了コード: 0
>   現在のブランチ: master
>   asset.txt: other の資産（main には存在してはいけない）
>   master の先頭: bbffd4c other 版
>   origin/master の先頭: e159571 main 初版
> ```
>
> **何が起きているか**: `switch` が exit 128 で失敗しても HEAD は元のブランチに残る。そこへ `reset --hard origin/<別ブランチ>` が走ると、**元のブランチそのものを別ブランチの内容へ移動させてしまう**。
>
> **なぜ気づけないか**: **ブランチ名は変わらない。** そのため [§5-7](#cautions) で推奨する「statusline に `.claude/` の現在ブランチを表示する」という取り違え防止策が**偽陰性になる**——statusline は正しい名前を表示し続け、中身だけが別物になる。
>
> 上記 3-b（`switch` 失敗で中断）と 3-c（reset 前のブランチ名一致確認）は、**この 1 点を塞ぐためにある**。

**`fetch` と `switch` / `reset` で扱いを変える理由**: `fetch` の失敗はネットワーク不通が主因で、**手元の内容で作業を続けられる**（古いだけ）。一方 `switch` / `reset` の失敗は**「意図したブランチで作業していない」状態**を生むので、続行してはならない。

#### `reset --hard` の deny 設定

> **⚠ 「Claude には触らせないが、ランチャーには許す」という非対称を明記する。**
>
> **共有 `.claude` リポジトリの `settings.json`（`main` ブランチに置けば全ブランチへ届く）に、次の deny を入れる。**
>
> ```json
> {
>   "permissions": {
>     "deny": [
>       "Bash(git reset --hard*)",
>       "Bash(git -C * reset --hard*)"
>     ]
>   }
> }
> ```
>
> PowerShell 経由も塞ぐなら次を足す。
>
> ```json
> {
>   "permissions": {
>     "deny": [
>       "PowerShell(git reset --hard*)",
>       "PowerShell(git -C * reset --hard*)"
>     ]
>   }
> }
> ```
>
> これは **Claude Code のセッション内で Claude 自身が実行すること**を禁じる設定であって、**ランチャーがシェルスクリプトとして実行することは対象外**である（permissions は Claude のツール呼び出しにしか効かない）。
>
> **この deny は trust に依存せず必ず効く**（[§3-4](#sec-3-4)）。`allow` と違って入れ子リポジトリの不確定性（V7）の影響を受けないので、**統制として当てにしてよい**。
>
> この非対称は意図的なものであり、**混乱を招くのでチームに明示する**。「reset --hard は禁止」とだけ周知すると、ランチャーの実装がルール違反に見えてしまう。正しい周知は「**Claude に reset --hard をさせない。同期はランチャーが行う**」。
>
> **⚠ deny はコマンド文字列に対して効く。** ランチャーそのものを Claude に実行させると、`reset --hard` はスクリプトの内側で走るので **deny を通り抜ける**。[§5-7](#cautions) で「ランチャーを Claude に実行させない」を運用ルールとして置くのはこのためである。

#### 既存ランチャーとの関係

本チームには既にランチャー `start_claude_code.{ps1,sh}` が存在する（**正本は `base-dev-kit-for-cc` の `docs/launcher/`**）。上の最小例は**それを置き換える提案ではなく、案C-1 で生じる差分を示すもの**である。

| 既存ランチャーの要素 | 案C-1 での扱い |
|---|---|
| 起動オプションの 4 分類判定木（`--add-dir` / `--settings` / `--mcp-config` 等の組み立て） | **不要になる。** 案C-1 は起動フラグを渡さない（[§5-1](#sec-5-1)） |
| `.claude/` の同期（clone / fetch / switch / reset） | **新規に必要。** 上の最小例の 1〜3 |
| env・秘匿値の取り回し | **従来方針を維持する。** **分類A（秘匿値）は OS 環境変数**に置き、共有リポの `settings.json` には入れない（[§3-4](#sec-3-4) の警告ブロック） |
| `.ps1` の BOM+CRLF・`.sh` の LF という改行／エンコーディング方針 | **そのまま適用する** |

**⚠ 同名ファイルの衝突に注意する。** 既存の `start_claude_code.ps1` と新しい同期処理を**どう統合するか（置き換え／併存／マージ）は作業指示者の判断事項**とし、本書では決めない（[§7-0](#sec-7-0)）。**無自覚に上書きすると、既存ランチャーが持っていた秘匿値の受け皿が失われ、秘匿値が共有 `settings.json` へ流れ込む退行を招く。**

**`.sh` 版の要否も判断する。** 既存ランチャーは `.ps1` / `.sh` の両対応である。案C-1 でも WSL・macOS・Linux のメンバーがいるなら `.sh` 版が要る（処理内容は同一で、`$LASTEXITCODE` の代わりに `$?` を見る）。

<a id="cautions"></a>

### §5-7 運用上の注意

**起動と切替**

- **起動は必ず作業リポジトリのルートから行う。** サブディレクトリから起動すると **`.claude/settings.json` が読まれない**（`settings.json` の探索だけは親へ遡らない＝[§3-1](#sec-3-1)）。`CLAUDE.md` と skills は載るのに `permissions` だけが効かない、という分かりにくい状態になる。ランチャーの先頭で `Set-Location $PSScriptRoot` する（[§5-6](#sec-5-6)）
- **ブランチ切替はセッション開始前に行う。** 起動後に切り替えても反映されない（**要再起動**）。ランチャーで自動化しつつ、チームにも周知する
- **statusline に `.claude/` の現在ブランチを表示する。** 作業リポジトリのブランチとは別物なので、取り違えると「なぜこの指示が効かないのか」が分からなくなる。**ただしこれは万能ではない** —— ランチャーが `switch` の失敗を検査していないと、**ブランチ名は正しいまま中身だけが別物になる**（[§5-6](#sec-5-6) の実測）

**資産の置き方**

- **最初からブランチを細分化しない。** MECE に割り切れない作業は**親ブランチに寄せる**のが基本。context 消費量が実際に問題になってから分ける（分割の効果は `CLAUDE.md` と `paths:` なし `rules/` にしか効かない＝[§4-1](#sec-4-1)）
- **hooks は原則 `main` に置く。** ブランチごとに hooks を変えると、切替直後・trust 前に走る（[§3-4](#sec-3-4)）ため事故が見えにくい
- **`.claude/` を作業リポジトリの `.gitignore` に入れる。**【実測】入れておけば作業リポの `git status` は完全にクリーンなままになる

**統制**

- **ランチャーを Claude に実行させない。** `permissions.deny` は**コマンド文字列**に対して効くので、`reset --hard` がランチャーの内側で走ると deny を通り抜ける（[§5-6](#sec-5-6)）。同期はメンバー自身がランチャーを起動して行う
- **hooks・スクリプトの変更は 2 名レビューを必須にする。** 共有 `.claude` リポジトリの hooks は **trust 前でも全メンバーの端末で実行される**（[§3-4](#sec-3-4)）。実行されるコードと同じ扱いにする
- **force-push を許可するのは作業種別ブランチだけにする。** `main` はリモートで保護し、変更は PR 経由にする。**`main` は rebase の土台であって rebase 対象にならない**ので（[§5-4](#sec-5-4)）、保護しても rebase 運用は壊れない
- **メンテナーの交代手順を決めておく。** force-push 権限を持つのが 1〜2 名という前提が崩れると、rebase 運用そのものが破綻する

| 素の `claude` 起動での `deny` | 効く | **効かない**（`<Share>` の `permissions` は `--settings` 経由でしか届かない＝二重化が前提） | **効く**（`.claude/` が clone 済みで、かつ**リポジトリルートから起動した場合**）。`deny` / `ask` は trust 非依存。**`allow` は trust 依存で、入れ子リポジトリでの扱いは未確認**（V7＝[§8-2](#sec-8-2)） |
| hooks のパス解決 | 自然に解決（`${CLAUDE_PROJECT_DIR}`） | plugin 化が必要 | **自然に解決** |
| 層3 との相互作用 | 影響なし | **`disableSideloadFlags` / `managed-mcp.json` で起動不能になりうる**（[§4-3](#sec-4-3)） | **影響なし**（フラグ不使用） |
| ポータビリティ（新しいリポジトリへの適用） | 複製か submodule 登録が要る | ランチャーと `<Share>` のパス設定が要る | **`.gitignore` 1 行 ＋ ランチャー配置 ＋ clone**。`<Share>` の置き場所に依存しない |
| 主な運用コスト | submodule 更新・複製のドリフト | ランチャー経由起動の徹底 | ブランチ切替 ＋ 親追従（rebase） |

<a id="sec-6-2"></a>

### §6-2 各案を採らない理由

**現状維持（submodule / 複製）**
共通資産の実体が複数になり、submodule のピンがリポジトリごとにずれる。**「どのリポジトリが最新の規約で動いているか」が誰にも分からなくなる**のが最大の問題。作業種別ごとの出し分けは端から不可能。

**案A（`--add-dir <Share>` で共有ディレクトリを参照する）** —— **v1.2 では補助（案C）と位置づけていた経路**。**何が載るのかの詳細は [付録B](#appendix-b)**
致命的なのは **`permissions` が `--add-dir` では届かない**点。`<Share>` の `settings.json` からは `enabledPlugins` / `extraKnownMarketplaces` の 2 キーしか読まれない [\[19\]](#ref-19) ため、`deny` を効かせるには `--settings <Share>/.claude/settings.json` を別途渡す必要がある。つまり**ランチャーを経由しない素の `claude` 起動では `deny` が一切効かない**。さらに `--add-dir` の例外ロード範囲は版ごとに広がっており（skills のみ → ＋subagents → ＋commands）、**「何が載るか」が CLI の版に従属する**。案C-1 はこの従属をまるごと消す。

**案A'（D-11: `<Common>` を `--add-dir` にする逆転案）** —— **不採用（2026-09-14 決定）**
案A の変種で、作業リポジトリを主・共通資産を追加ディレクトリにする向きを逆転させ、共通資産側を主にする案。案A の起動フラグ依存と `permissions` 二重化をそのまま引き継ぐため、案C-1 が成立するなら採る理由が無い。**ドラフトは [`drafts/D-11_パターン2逆転案_改訂ドラフト.md`](./drafts/D-11_パターン2逆転案_改訂ドラフト.md) に凍結保存**する。

**案B（機能資産を層2 plugin へ集約する）** —— **併用する。対立しない**
案C-1 と排他ではない。**リポジトリ固有の機能資産は plugin に寄せる**のが案C-1 の推奨でもある（[§5-2](#assignment)）。ただし **`CLAUDE.md` / `rules` / `permissions` は plugin で運べない**（[§2-2](#matrix) ②）ため、plugin だけでは設計が閉じない。

plugin を併用する際の注意が 2 点ある。

- **v2.1.195 以降、marketplace を宣言しただけでは外部ソースの plugin は install されない。** project の `settings.json` が `enabledPlugins` で有効化していても、GitHub リポジトリや npm パッケージ由来の plugin は**メンバーが `claude plugin install` するまでロードされない**（それまで "not installed" と表示される）[\[32\]](#ref-32)。**「clone すれば即動く」は成り立たない**ので、ランチャーか onboarding 手順に install を組み込む
- **ネットワーク前提を外したいなら `archive` / `command` ソースか `@skills-dir` 型を検討する。** `archive` は HTTPS 配布の zip を `sha256` で pin でき、`command` の link mode は**キャッシュへコピーせずその場で使う**[\[33\]](#ref-33)。また **skill フォルダに `.claude-plugin/plugin.json` を置くだけで `<name>@skills-dir` という plugin になり**、marketplace も install も不要のまま agents / hooks / MCP をバンドルできる（**project の `.claude/skills/` では workspace trust の承認が先に要る**）[\[6\]](#ref-6)

**案C-2（`.claude/` を submodule にする）**
`.claude/` を git submodule として作業リポジトリに登録する案。ブランチ切替はできるが、**作業リポジトリ側に submodule のピンがコミットされる**ため、「`.claude/` の更新が作業リポジトリのコミット履歴を汚す」「ブランチを切り替えるたびに作業リポ側で差分が出る」という問題が戻ってくる。**gitignore された素の clone にすれば両方消える**（【実測】作業リポの `git status` は空のまま）。

**案D（層3 managed settings で強制する）** —— **組織に IT 統制基盤があるなら併用**
案C-1 と排他ではない。**上書きを防げるのは層3 だけ**なので、強制が要る組織は重ねる（[§4-2](#sec-4-2)）。ただし層3 はチームではなく組織の持ち物であり、チーム単独では選べない。

**`rules/` の symlink 共有**
外部 import の承認が要り、**承認後も `paths:` 付き rule は載らない**[\[16\]](#ref-16)。共有手段としては穴が 2 つある（[§3-3](#sec-3-3)）。

> **その他、検討したうえで配布設計の柱から外した経路**（claude.ai 同期 skill・Organization settings > Plugins・`--plugin-dir` / `--plugin-url`・`~/.claude/` への配布・`pluginConfigs` の commit・submodule 化）は **[付録C](#appendix-c)** にまとめてある。

<a id="sec-7-1"></a>

### §7-1 共有 `.claude` リポジトリを立てる

1. 新規リポジトリを作る（例: `<org>/shared-claude`）。**中身は `.claude/` の中身そのもの**（`CLAUDE.md` / `rules/` / `skills/` / `settings.json` … をリポジトリ直下に置く。`.claude/` という階層は作らない）
2. **`.gitignore` に `settings.local.json` を入れる**（[§5-5](#mirror) の警告）
3. 現行の共通資産を `main` ブランチへ移す。**この時点ではブランチを分けない**
4. リモートで**メンテナーの force-push を許可**する設定にする（branch protection で禁止されていないことを確認）

<a id="sec-7-2"></a>

### §7-2 ブランチを切る（必要になってから）

1. 「このブランチでしか要らない」と**実際に判断できた資産**だけを対象にする
2. `git switch -c <group>/base main` → 資産を移動 → commit
3. `git switch -c <group>/<作業種別> <group>/base` → 同上
4. **[§5-3](#sec-5-3) の命名規約を守る**（親名をそのままブランチ名にしない）
5. **push する前に、検証用リポジトリで対象ブランチを clone して確認する。** 空のリポジトリを作り、その `.claude/` として対象ブランチを clone し、**対話セッションを起動して `/context` で何がロードされているかを目視する**。skill が期待どおり載っているか・`CLAUDE.md` の内容が意図どおりかを見る。手順は [02 編 手順書の方法A](../02.配布物の開発・テスト/02.Marketplace外資産編/Marketplace外資産_開発・テスト_手順書.md) を使う

> **`main` を更新したときの検証範囲**: `main` の変更は**全ブランチへ rebase で波及する**（[§5-4](#sec-5-4)）。したがって `main` を触ったら、**代表として各系列の葉ブランチを 1 つずつ検証する**（`java/ut`・`python/coding` など）。全ブランチを毎回見る必要はないが、**`main` だけ見て済ませてはいけない** —— 系列ブランチ側の資産と衝突する変更は、`main` 単体では見えない。

<a id="sec-7-3"></a>

### §7-3 作業リポジトリ側を切り替える

各作業リポジトリで:

1. 既存の `.claude/` を退避する
   - **通常のディレクトリの場合**: `git mv .claude .claude.bak`
   - **submodule の場合**（現行の C-BCP がこれ）: **`git mv` だけでは submodule 登録が外れない。** 次の順で外す

     ```bash
     git submodule deinit -f .claude
     git rm -f .claude              # .gitmodules と index から除去
     rm -rf .git/modules/.claude    # 内部メタデータの削除
     git commit -m "chore: .claude の submodule 登録を解除"
     ```

2. `.gitignore` に `.claude/` を追加して commit
3. **リポジトリ固有だった資産を仕分ける**:
   - 指示文 → ルート `CLAUDE.md` へ移す
   - skill / agent / hooks → plugin 化するか、共有リポの適切なブランチへ移す
   - MCP → root `.mcp.json`（既にそこにあるはず）
4. `git clone --branch main <shared-claude> .claude`
5. ランチャー `start_claude_code.ps1` を配置して commit（[§5-6](#sec-5-6)。**既存ランチャーがある場合は [§7-0](#sec-7-0) (a) の判断に従う**）
6. **ルート `CLAUDE.md` に `.claude/` の由来を 1 行書いておく**（推奨）。例: 「`.claude/` は共有リポジトリ `<org>/<shared-claude>` のクローンで、本リポジトリでは gitignore されている。直接編集しない。更新は `start_claude_code.ps1` が行う」。**これが無いと、後から参加したメンバーが `.claude/` を普通のディレクトリだと思って編集し、次の同期で失う**
7. 動作確認後、`.claude.bak` を削除

<a id="sec-7-4"></a>

### §7-4 チームへの周知（最低限これだけ）

- **起動はランチャー経由**。素の `claude` でも動くが、`.claude/` が古いまま使われる。**初回はそもそも `.claude/` が存在しない**（まだ clone されていない）ので、素の `claude` では共有資産が一切載らない
- **起動は作業リポジトリのルートから**。サブディレクトリから起動すると `permissions` が効かない（[§3-1](#sec-3-1)）
- **ブランチを切り替えたら Claude Code を再起動する**
- **`.claude/` は編集しない**。直したいことがあればメンテナーへ依頼する（ローカル変更があるとランチャーが止まる）
- **個人設定は `.claude/settings.local.json` に書く**。**このファイルが `reset --hard` で消えないことは実測済みで、断定してよい**（[§5-5](#mirror)）
- **`reset --hard` は Claude にはさせない。同期はランチャーがやる**（[§5-6](#sec-5-6) の非対称）。**共有 `settings.json` に deny を入れておく**（同節にスニペット）
- **秘匿値は OS 環境変数に置く。** 共有 `.claude/settings.json` の `env` には書かない（[§3-4](#sec-3-4)）
- **初回起動時に trust ダイアログが 2 回出る可能性がある**（作業リポジトリと、入れ子リポジトリである `.claude/`）。**両方承認する**。文言は V7 の確認結果で確定する（[§8-2](#sec-8-2)）

> **⚠ この周知のうち、確度が違うものが混じっている。**
>
> - **「個人設定は消えない」は実測済みで断定できる**（[§5-5](#mirror)）
> - **「共有した `permissions` が効く」は `deny` / `ask` についてのみ断定できる**（trust 非依存）。**`allow` は入れ子リポジトリでの適用が未検証（V7）**であり、**展開前に [§8-2](#sec-8-2) の手順で確認してから周知文言を確定すること**

## §8 確認できない点・推測領域

ガバナンス設計上、根拠が公式ドキュメントに無く推測に留まる点、および未検証の点を明示する。

<a id="sec-8-1"></a>

### §8-1 公式に記載が無い（推測領域）

- **条件付きロードの発火契機**は本書の実測（[§3-2](#conditional)）が根拠で、**公式は "reads files" としか書いていない**[\[15\]](#ref-15)[\[12\]](#ref-12)[\[7\]](#ref-7)。**将来の版で Bash 経由も発火するようになる可能性は否定できない**。そうなっても案C-1 は壊れない（条件付きロードに依存していないため）が、「条件付きロードは使えない」という本書の判断そのものは版依存である
- `.claude/` を**入れ子の git リポジトリ**にする構成を、公式ドキュメントは**配布手段としては扱っていない**。ただし**入れ子リポジトリの存在自体には明示的な言及があり**、workspace trust の単位は「入れ子になった git リポジトリ（submodule など）を除いた git リポジトリのルート」と定義され、入れ子リポジトリには**対話セッションで別途 trust ダイアログが出る**とされている [\[23\]](#ref-23)（L81157・L81180）。つまり**「言及が無い」のではなく「trust の扱いが明示されている」**。ロードされること自体は[§3-1 の実測](#sec-3-1)で確認済みだが、**`permissions.allow` が実際に適用されるかは未確認**（V7＝[§8-2](#sec-8-2)）。**CLI の版が上がったら再測すること**
- `rules/` を **plugin 単体**でそのまま運ぶ仕組みは公式に記載が無い（plugin の正規コンポーネントに rules は無い）
- 3 チャネルを結合する scaffold / onboarding スクリプトの公式手順は無い（運用設計＝推測領域）
- file-based `managed-settings.json`（MDM / plist / registry 配置）のプラン非依存は、ファイル機構の性質からの**推定**で原文に明示は無い。**server-managed（admin console 経由）が Team/Enterprise 必須**である点は原文明記
- **公式ドキュメント以外の事例調査は行っていない。** 本書の「単一の既製ベストプラクティスは存在しない」（[§0](#summary) 問2）は、**公式ドキュメントが記載する配布機構を全経路棚卸しした範囲での結論**である。コミュニティの運用事例・OSS の実装パターン・他社事例は調査対象に含めていない

### §8-2 未検証（本書では測っていない）

| # | 内容 | 案C-1 への影響 | **採否をブロックするか** | 担当 | 確認方法 |
|---|---|---|---|---|---|
| **V6 ＋ V7** | **入れ子 git リポジトリ（`.claude/` が別リポジトリ）であることの影響** —— ① Windows で `settings.local.json` がどこから読まれるか（公式が「Windows は repo root を使わない例外」と示唆 [\[22\]](#ref-22)）／② **workspace trust が `.claude/` に及ぶか＝`permissions.allow` が適用されるか**（[§3-4](#sec-3-4)） | **案C-1 の中核に関わる。** `allow` が届かないなら「permissions を一元配布できる」という主張の**半分が成立しない**（`deny` / `ask` は trust 非依存なので影響を受けない） | **ブロックはしない**（`deny` は効くので統制目的は達成できる）が、**展開前に必須**——周知文言と CI（`claude -p`）運用が変わる | 作業指示者（**対話セッションが必要**） | 下記の再現手順 |

| V2 | `--settings` 経由の `permissions` マージ挙動 | **案C-1 では `--settings` を使わないため影響なし**（案A 評価用） | ブロックしない | —— | 案A を再評価する場合のみ |
| V3 | 相対パス hook の失敗と絶対パス化 | 案C-1 では `${CLAUDE_PROJECT_DIR}` が自然に効くため優先度低 | ブロックしない | メンテナー | hooks 導入時に実機確認 |
| V4 | **context 消費量の実測**（`CLAUDE.md` 外出しと skills 外出しの効果分離・**skill の `description` が切り詰められ始める件数**） | ブランチ細分化の判断基準になる。[§5-7](#cautions)「細分化しない」方針の裏付けが得られる | ブロックしない | メンテナー | `/context` を見ながら資産を増やして計測 |
| V5 | 共有リポが**大きくなったとき**の clone / switch 所要時間 | ランチャーの体感速度に直結 | ブロックしない | メンテナー | 資産が数百ファイル規模になったら測る |

#### V7 の再現手順（所要 3 分・**対話セッションが必要**）

**目的**: 作業リポジトリを trust したとき、入れ子クローンである `.claude/` の `settings.json` の `permissions.allow` が適用されるかを判定する。**`claude -p` では trust ダイアログが出ない** [\[23\]](#ref-23) ため、この検証はヘッドレスでは行えない。

1. 空のディレクトリを作り `git init` する（＝作業リポジトリ）
2. その中に `.claude/` として共有リポジトリ相当を用意する（別途 `git init` したリポジトリでよい）。作業リポの `.gitignore` に `.claude/` を入れる
3. `.claude/settings.json` に、**それ以外は何も許可しない**形で allow を 1 つだけ置く

   ```json
   { "permissions": { "allow": ["Bash(echo TRUSTPROBE:*)"] } }
   ```

4. **作業リポジトリのルートから対話セッションを起動**し、trust ダイアログを承認する。**`.claude/` について 2 枚目のダイアログが出るかどうかも記録する**（公式の記述どおりなら出る＝[§3-4](#sec-3-4)）
5. `echo TRUSTPROBE-OK` を実行させる
   - **許可プロンプトが出ずに実行された → `allow` は適用されている（V7 ＝ 可）**
   - **許可プロンプトが出た → `allow` は届いていない（V7 ＝ 否）**。stderr に `this workspace has not been trusted` が出ていないかも確認する

**V7 ＝ 否 だった場合の代替手段**（いずれも案C-1 自体は維持できる）:

| 代替 | 内容 | 代償 |
|---|---|---|
| **(a)** `.claude/` を個別に trust する | 各メンバーが `.claude/` についても trust を承認する（**公式の記述どおりならこれが既定の挙動**） | 初回セットアップのダイアログが 1 枚増える |
| **(b)** onboarding スクリプトで trust を書き込む | `~/.claude.json` の `projects["<パス>"].hasTrustDialogAccepted` を `true` にする（公式が案内している手段）[\[23\]](#ref-23) | 承認の意味が形骸化するので、**スクリプトの内容自体をレビュー対象にする** |
| **(c)** `allow` を `settings.local.json` へ寄せる | **untracked なファイルの rules は、そのフォルダを trust していなくても適用される** [\[23\]](#ref-23)（L81170） | **`allow` を一元配布できなくなる**（各自が設定する） |
| **(d)** `allow` を諦め、`deny` / `ask` だけを配る | `deny` / `ask` は trust 非依存で必ず効く | 許可の事前付与ができず、確認プロンプトが増える |

> **いずれの場合も `deny` / `ask` による統制は成立する。** V7 が否でも「**危険なコマンドを塞ぐ**」という目的は達成できる。影響を受けるのは「**あらかじめ許して確認プロンプトを減らす**」という利便性のほうである。

### A-3 どの層でも設定できるが、managed に置くと統制として機能するキー

**v1.2 の付録A が managed 専用として列挙していた次の 4 キーは、settings-reference の Scope 列が `Any file` である**——つまり **managed 専用ではない**。user / project / local にも書けるが、**managed に置いた場合は上書きできなくなる**ため統制として機能する、という性質のキーである。

| キー | Scope | 効果 | 注意 |
|---|---|---|---|
| `permissions.disableBypassPermissionsMode` | **Any file** | `--dangerously-skip-permissions` を無効化 | **project の `settings.json` に書いても、メンバーが `settings.local.json` で戻せる。** 強制したいなら managed が要る |

| `forceLoginMethod` | **Any file** | ログイン方法（Claude アカウント / API キー等）を強制 | 同上 |
| `forceLoginOrgUUID` | **Any file** | 所属組織を強制 | 同上 |

> **なぜこの区別が要るか**: 「managed 専用」だと思い込むと、**層3 の基盤が無いチームはこの 4 キーを最初から諦めてしまう**。実際にはチームの `settings.json` に commit すれば（上書きされうるものの）今日から効かせられる。逆に「commit したから強制できている」と考えるのも誤りである。

> **⚠ チームが層3 を「使える」と誤認しないこと。** **A-1 / A-2 のキーは**すべて**組織の IT 管理者が配布基盤で配るもの**であり、リポジトリに commit しても一切効かない（**A-3 の 4 キーだけが例外**）。チームが自前で握れる統制機構は [§4-1](#sec-4-1) の上 3 つだけである。

### B-2 `--add-dir` 例外ロード一覧（正本）

> `--add-dir`／`/add-dir` で追加ディレクトリの `.claude/` から自動ロードされる構成要素の**正本**。各成果物の同種の早見表は運用早見であり、**版依存の事実が食い違った場合は本表を優先**する。

| 資産 | 自動ロード | 条件・版依存 |
|---|:---:|---|
| `skills/`（`.claude/skills/`） | ✅ | **v2.1.165 以前から対象**。**live reload あり**。`--add-dir`／`/add-dir` 限定 [\[19\]](#ref-19)[\[8\]](#ref-8) |
| `commands/`（`.claude/commands/`） | ✅ | **v2.1.235+ で追加**（それ以前は非ロード）。**live reload なし**（変更後は再起動）。追加ディレクトリとプロジェクトで同名コマンドがある場合は**プロジェクト側が優先** [\[19\]](#ref-19)[\[9\]](#ref-9) |
| `agents/`（subagents・`.claude/agents/`） | ✅ | **v2.1.178+ で追加**（v2.1.165 では非ロード）。**live reload なし**（同上）[\[19\]](#ref-19)[\[9\]](#ref-9) |
| `settings.json` / `settings.local.json` の `enabledPlugins` / `extraKnownMarketplaces` | ✅ | **この 2 キーのみ**[\[19\]](#ref-19) |
| `CLAUDE.md` / `.claude/rules/` / `CLAUDE.local.md` | △ | **`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` のときのみ（all-or-nothing）**。`CLAUDE.local.md` はさらに `local` setting source が有効であること（既定で有効）が要る [\[19\]](#ref-19)[\[13\]](#ref-13) |
| `settings.json` のその他キー（**permissions / hooks / env**）・`output-styles/` | ❌ | 結合されない。物理配置か `--settings` で渡すしかない [\[19\]](#ref-19) |

**適用範囲の注意**:

- **`permissions.additionalDirectories` 設定値経由では、上記の例外は一切読まれない**（ファイルアクセスの付与のみ）[\[19\]](#ref-19)
- **Agent SDK の `additionalDirectories`(TS) / `add_dirs`(Py) は上記の例外を丸ごと受ける**。SDK が各エントリを `--add-dir` として CLI へ渡すため。**TypeScript 側の名称が settings キー `permissions.additionalDirectories` と同名だが挙動は正反対**[\[20\]](#ref-20)
- **これらは `project` setting source 経由でロードされる**。`--setting-sources` / `settingSources` で `project` を外すと載らず、**bare mode は commands と subagents をスキップする（skills は載る）**[\[20\]](#ref-20)
- **作業ディレクトリ配下のサブディレクトリ**なら、セッション途中に `/add-dir <サブディレクトリ>` で skills / commands / subagents を載せられる（プロンプトも追加作業ディレクトリの登録も発生しない。**v2.1.257+**）[\[21\]](#ref-21)

### B-3 例外ロードを絞る制御機構

| 機構 | 効き方 | 使える層 | 制約 |
|---|---|---|---|
| **共有ディレクトリの中身で絞る** | 置かないものは読まれない。**最も確実で唯一チーム主体で完結する** | 全員 | 設計・レビューの規律に依存 |
| **`claudeMdExcludes`** | `CLAUDE.md` / `rules` を**パス・glob 単位**で除外。**user / project / local / managed の全スコープで設定可・commit 可・配列はスコープ間でマージ**[\[18\]](#ref-18) | **チーム（project へ commit）** | 静的。**managed policy の `CLAUDE.md` は除外できない**[\[17\]](#ref-17) |
| **`--setting-sources` から `project` を外す** | フラグ追加ディレクトリの skills / commands / subagents が全部落ちる [\[20\]](#ref-20) | 起動側（ランチャー） | **作業リポジトリ自身の project 設定も同時に落ちる** |
| **bare mode** | **commands と subagents をスキップ。skills は載る**[\[20\]](#ref-20) | 起動側（headless） | 対話運用向けではない |
| **`--safe-mode`** | customization を全無効化 [\[34\]](#ref-34) | 起動側 | トラブルシュート用。常用しない |
| **`strictPluginOnlyCustomization`** | skills / agents / hooks / MCP を plugin ＋ managed 由来のみに制限 | **層3（managed）のみ**[\[28\]](#ref-28) | **Scope が Managed 固定。チームレベルでは使えない** |

## 付録C：事実上使えない／数えない経路

配布経路として名前は挙がるが、**チームの配布設計の柱にはできない**ものを明示する。「検討し忘れた」ではなく「検討した上で外した」ことを記録するための付録。

| 経路 | 何ができるか | 数えない理由 |
|---|---|---|
| **claude.ai 同期 skill**（`~/.claude/skills/synced/`） | claude.ai アカウントで有効化した skill が同期される。Cowork / cloud セッションでは無設定でロード、ローカルでは **`-p` 非対話実行 ＋ `CLAUDE_CODE_SYNC_SKILLS=1`** のときだけダウンロード | **個人アカウントに紐づく同期であり、チームが配る経路ではない**。さらに `synced` は**予約名**で、同名の自作 skill は enterprise / 個人 / project いずれでも黙ってスキップされる [\[5\]](#ref-5) |
| **Organization settings > Plugins**（claude.ai） | 組織として plugin を配布・許可できる | **プラン依存（Team / Enterprise）で、自チームで使えるかが未確認**（[§8-2](#sec-8-2) V1）。使えるなら共有リポの担当範囲が狭まるので、**確認する価値はある** |
| **`--plugin-dir` / `--plugin-url`** | plugin 一式をセッション単位で渡せる | 「そのセッションのみ」で恒久設定にならない。加えて層3 の `disableSideloadFlags` で**起動時に拒否されうる**（[§4-3](#sec-4-3)）。**開発・テスト用途では必須**なので、自組織で `disableSideloadFlags` を有効化することは推奨しない |
| **`rules/` の symlink 共有** | `.claude/rules/` に共有ディレクトリを symlink する | 作業ディレクトリ外を指す symlink は**外部 import 扱い**で承認が要り、**承認後も `paths:` 付き rule は載らない**[\[16\]](#ref-16) |
| **`~/.claude/` へ配る** | 全プロジェクト共通の個人設定 | **チームが `~/.claude/` へ配る公式経路は存在しない**（各自の手作業になる） |
| **`pluginConfigs` を commit する** | plugin へ渡す設定値の配布 | **project / local settings からは読まれない**。clone したリポジトリからの値注入を防ぐ設計 |
| **`.claude/` を git submodule にする（案C-2）** | ブランチ切替はできる | 作業リポジトリ側に**submodule のピンがコミットされる**ため、`.claude/` の更新が作業リポの履歴を汚す。**gitignore した素の clone にすれば両方消える**（[§6-2](#sec-6-2)） |

## 実測記録の再現手順

本書の 【実測】 は次のスクリプトで再現できる（2026-09-14 実施時のもの）。**CLI の版が上がったら測り直すこと**（[§8-1](#sec-8-1)）。

**スクリプト本体は [`./verification/`](./verification/) に置いてある。** 本書の「必要な情報を本書内に保持する」方針は**判断に必要な事実**に対するもので、**実行可能なスクリプト本体は対象外**とする（本文に埋め込むと、実行できる形で保守されず必ず陳腐化するため）。本文には**何を測って何が分かったか**を書き、**どう測るか**はスクリプトを正本とする。

| 実測 | 内容 | 再現コマンド | 対応する節 |
|---|---|---|---|
| 入れ子クローンのロード | 作業リポ（`.gitignore` に `.claude/`）の `.claude/` へ共有リポを clone し、`CLAUDE.md` / `paths:` なし rule / `settings.json` の `env` / skill の 4 つを合言葉で回収 | `bash verification/nestclone-setup.sh` → `bash verification/nestclone-run.sh` | [§3-1](#unconditional) |
| 条件付きロードの発火契機 | 1 つのサブディレクトリに 3 資産（`paths:` 付き rule の対象ファイル・`CLAUDE.md`・nested skill）を同居させ、**先行操作なし / Read ツール / Bash `cat` / Grep / Edit ツール（Read 不許可）** の 5 条件で各 1 セッション起動。先行操作用ツールと `Skill` のみ許可し、**skill は Skill ツールの起動成否で判定**（自己申告は信用しない）。`/reload-plugins` と起動時 `--add-dir` は nested skill についてのみ別途測定 | `bash verification/trigger-setup.sh` → `bash verification/trigger-run.sh`（Edit 条件のみ `trigger-edit.sh`） | [§3-2](#conditional) |
