# Agent B (round 2): P × E1〜E3 シナリオ列挙

## シナリオ

### S-B1: CI パイプライン内でのコンテキスト自動注入
- **起点の具体**: CI（GitHub Actions / GitLab CI 等）のジョブステップ
- **環境**: E2
- **いつ発動**: PR 作成・push イベント等のトリガ。または日次定期ジョブ
- **何をする**: CI ジョブ内で `llms-full.txt` を curl で取得し、後続の LLM 呼び出しのシステムプロンプトに組み込む。テスト生成・コードレビュー・ドキュメント生成等の用途
- **llms.txt への期待**: 安定した URL で取得できること。サイズが大きすぎると CI のトークンコストが上がるため、コンパクトな `llms.txt`（索引のみ）とフルテキストの `llms-full.txt` を使い分けたい
- **鮮度モデル**: F1（最新 API 仕様を常に反映したい）/ F2（安定リリースに固定したいプロジェクトも存在）
- **注記**: merge-candidate なし。CI 文脈は幅広いが起点の特性（非対話・定期実行・コスト意識）が明確に P 起点の典型

### S-B2: Claude Code の CLAUDE.md からの自動 fetch 参照
- **起点の具体**: CLAUDE.md に記述されたルールを読んだ Claude Code が fetch ツールで自動取得
- **環境**: E1
- **いつ発動**: Claude Code セッション開始時、または CLAUDE.md の指示を Claude が読んだ際
- **何をする**: CLAUDE.md に「参照先: https://raw.githubusercontent.com/.../llms.txt」のような記述が入っており、Claude Code が自律的に fetch してコンテキストに取り込む
- **llms.txt への期待**: 可能な限り小さい（`llms.txt`）こと。URL 直打ちで安定して取得できること。CLAUDE.md 原則 4.1 の観点から、メンテナー文書を読ませたくない設計が前提
- **鮮度モデル**: F1（セッション開始時に最新を引く）
- **注記**: E1 かつ P 起点の特殊ケース。メンテナーではなく「同居非メンテナーが自分の CLAUDE.md からポインタを置く」ケース

### S-B3: submodule として取り込んだ後の自動更新スクリプト
- **起点の具体**: 自動化スクリプト（git submodule update --remote を呼ぶ cron や Makefile ターゲット）
- **環境**: E2
- **いつ発動**: 週次 cron / 手動 make update / 依存更新 bot（Renovate Bot 等）
- **何をする**: cc-relative-info を submodule として取り込んだプロジェクトで、submodule を最新コミットへ追随させる。その後、CI が最新の `llms.txt` を自動でピックアップ
- **llms.txt への期待**: ファイルパスが安定していること（移動・リネームされると CI が壊れる）
- **鮮度モデル**: F1（定期追随）/ F2（submodule を特定コミットに固定して使うプロジェクト）
- **注記**: `[merge-candidate: S-B1, S-B3]` — CI パイプライン内での取得（S-B1）と submodule 経由の取得（S-B3）はトリガ経路が異なるが、利用者が感じる「自動更新したい」ニーズは共通

### S-B4: Renovate Bot / Dependabot 類似の依存更新自動化
- **起点の具体**: 外部依存更新ツール（Renovate Bot / GitHub Dependabot / 自作更新スクリプト）
- **環境**: E2
- **いつ発動**: 特定 URL のハッシュが変化したことを検知したとき、または定期チェック
- **何をする**: `llms.txt` の URL をウォッチ対象として登録し、内容変化時に PR を自動作成して「新しい llms.txt 版が利用可能」と通知する
- **llms.txt への期待**: URL の永続性。コンテンツのハッシュ比較ができること（`ETag` 対応 / バイナリ差分）
- **鮮度モデル**: F1（変化追跡）/ F2（変化があっても特定版を維持する選択肢）
- **注記**: `[merge-candidate: S-B3, S-B4]` — submodule 更新（S-B3）と URL ウォッチ（S-B4）は実装手段が違うが、利用者の目的（更新検知と通知）は近い

### S-B5: RAG パイプラインへの定期投入
- **起点の具体**: バッチ処理（Python スクリプト / LangChain Pipeline / LlamaIndex 等）
- **環境**: E3
- **いつ発動**: 日次・週次バッチ、または手動トリガ
- **何をする**: `llms-full.txt` を取得してベクトル DB（Pinecone / Chroma / pgvector 等）に投入し直す。RAG インデックスを最新状態に保つ
- **llms.txt への期待**: `llms-full.txt` のドキュメント本文が充実していること。各セクションの区切りが明確で chunk 分割しやすいこと
- **鮮度モデル**: F1（インデックスを常に最新化）/ F2（実験・検証時に版を固定したい）
- **注記**: E3 の典型。リポジトリとは無関係な独立処理パイプラインとして動作

### S-B6: カスタム Claude Agent への system プロンプト自動組み込み
- **起点の具体**: API 直叩き（Anthropic Messages API / Bedrock / Vertex AI）
- **環境**: E3
- **いつ発動**: Agent 起動ごと、または起動前の初期化フェーズ
- **何をする**: `llms.txt` を HTTP GET して system プロンプトに直接埋め込む。「Claude Code の機能一覧」「MCP サーバー一覧」等を Claude に常に認識させた状態でエージェントを起動する
- **llms.txt への期待**: サイズが小さいこと（`llms.txt` のリンク索引のみで十分なケースと、`llms-full.txt` を必要とするケースがある）。raw テキスト形式で取得できること
- **鮮度モデル**: F1（最新の Claude Code 機能を常に反映）
- **注記**: `[merge-candidate: S-B5, S-B6]` — RAG 投入（S-B5）と system プロンプト直接組み込み（S-B6）はアーキテクチャが違うが、P 起点で `llms-full.txt` を処理する点は共通。ただし期待するファイル形式・サイズが異なるため分けて扱う価値あり

### S-B7: GitHub Actions での LLM-assisted コードレビュー自動化
- **起点の具体**: GitHub Actions workflow（PR トリガ）
- **環境**: E2
- **いつ発動**: PR open / push イベント
- **何をする**: PR の diff を LLM に送る前処理として、対象コードに関連する SDK / フレームワークの `llms.txt` をコンテキストとして付与。「このコードは Claude Code SDK の仕様に準拠しているか？」をチェックさせる
- **llms.txt への期待**: 特定フレームワーク（Anthropic SDK / Spring Framework 等）の API リファレンスへのリンクが索引化されていること。`llms.txt` の索引から必要な URL だけを絞り込んで取得できる構造
- **鮮度モデル**: F1（コードが使っている最新 SDK 仕様を参照）/ F2（SDK バージョンを固定しているプロジェクトは対応版 llms.txt を固定したい）
- **注記**: S-B1 と CI という点は共通だが「コードレビュー特化」「フレームワーク特定版の llms.txt への要求」が異なる点として分けた。`[merge-candidate: S-B1, S-B7]` — ただしレビュー用途の特殊要求（フレームワーク特定版）は統合時に情報が失われる可能性あり

### S-B8: VSCode / Cursor 等エディタ拡張からの自動コンテキスト注入
- **起点の具体**: エディタ拡張が内部で API を呼ぶ自動フロー（ユーザー操作起点ではなく拡張のバックグラウンド処理）
- **環境**: E3
- **いつ発動**: ファイル開閉 / コード補完リクエスト発生時 / 設定された間隔での定期更新
- **何をする**: エディタ拡張が `llms.txt` を定期的に fetch してキャッシュし、補完・説明リクエスト時に関連部分をコンテキストとして挿入する
- **llms.txt への期待**: HTTP GET で安定取得できること。キャッシュ制御ヘッダ（Cache-Control / ETag）が使えること
- **鮮度モデル**: F1（補完精度のために常に最新を使いたい）
- **注記**: P 起点だが人間がエディタを使う文脈と重なる。H と P の境界ケース

### S-B9: 社内ナレッジ基盤への定期同期
- **起点の具体**: 社内データ同期バッチ / ETL ジョブ
- **環境**: E3
- **いつ発動**: 週次バッチ、または Slack bot のコマンドをトリガにした非同期ジョブ
- **何をする**: `llms-full.txt` を取得して社内 Confluence / Notion / Vector DB に同期。社内 LLM チャットボットが Claude Code や MCP のドキュメントに答えられるようにする
- **llms.txt への期待**: `llms-full.txt` の本文が充実していること（索引先をクロールせずに済む）。ライセンス上の問題がないこと（商用利用可能なコンテンツか）
- **鮮度モデル**: F1（週次追随）/ F2（社内基盤の更新コストを下げるため半年ごとに固定する選択肢も）
- **注記**: E3 の典型。RAG 投入（S-B5）と近いが、ターゲットが社内知識基盤（Confluence 等）であり、ドキュメント形式への変換要求が異なる。`[merge-candidate: S-B5, S-B9]` — 統合候補だが宛先システムの違いが要求差に繋がる可能性

### S-B10: プロジェクトテンプレートへの版固定 llms.txt バンドル
- **起点の具体**: プロジェクトテンプレート生成ツール（`cookiecutter` / `cargo generate` / `create-next-app` 等）
- **環境**: E2（生成直後のリポジトリ内に配置）
- **いつ発動**: プロジェクト新規作成時のスキャフォールド処理
- **何をする**: テンプレートのスキャフォールド実行時に、対象フレームワーク（Spring 5.3 等）の版固定 `llms.txt` スナップショットを自動コピーしてプロジェクト内に配置する
- **llms.txt への期待**: 特定バージョン対応の snapshot が取得できること（tag / commit 指定の URL 体系）
- **鮮度モデル**: F2（プロジェクト作成時点の版を固定し、以後は変えない）
- **注記**: P 起点 × F2 の典型例。glossary 6.1「プロジェクトテンプレート」の定義に正確に対応するシナリオ

### S-B11: cc-relative-info 内 CI による自己検証（E1 × P）
- **起点の具体**: 本リポジトリの GitHub Actions（or ローカル pre-commit hook）
- **環境**: E1
- **いつ発動**: 本リポジトリへの push / PR 時
- **何をする**: 生成済み `llms.txt` の形式検証・リンク到達確認・サイズチェックを自動実行する。同居非メンテナーとしての観点ではなく、CI が生成物の品質を保証する文脈
- **llms.txt への期待**: 検証可能な形式的仕様（URL パターン / セクション構造）が明確であること
- **鮮度モデル**: F1（常に最新の生成物を検証）
- **注記**: E1 × P だがメンテナー文脈に近い。ただし「自動検証をかける CI ジョブ」を「外部利用者目線でどう見えるか」を考えると、品質シグナルとして llms.txt が信頼できるかを確認したい同居非メンテナーの自動フロー（例: 自分のプロジェクトの CI が cc-relative-info をチェックする）とも読める。境界が曖昧

### S-B12: 多リポジトリ横断のドキュメント監視ダッシュボード
- **起点の具体**: 定期実行スクリプト / cron ジョブ
- **環境**: E3
- **いつ発動**: 日次 cron
- **何をする**: cc-relative-info が提供する 47 リポジトリ分の `llms.txt` を一括取得し、各リポジトリのドキュメント更新状況をダッシュボード（Grafana / 社内 Slack チャンネル等）に送信する。コレクション性（glossary 1.4）を活かした横断モニタリング
- **llms.txt への期待**: 全 47 ファイルが統一フォーマットで揃っていること（コレクション性の活用）。変更差分を比較できる安定した URL 体系
- **鮮度モデル**: F1（差分検知が目的のため最新追随が前提）
- **注記**: コレクション性（glossary 1.4）を P 起点で活かす典型例。他のシナリオと性質が異なる「横断利用」カテゴリ

### S-B13: llms.txt を素材とした LLM ファインチューニング / 評価データセット構築
- **起点の具体**: バッチ処理スクリプト（Python）
- **環境**: E3
- **いつ発動**: データセット構築作業の一環として手動またはパイプライン内で実行
- **何をする**: `llms-full.txt` を取得し、QA ペア生成・要約・分類等の前処理パイプラインに流してファインチューニング用データセットを構築する。または評価ベンチマークの参照ドキュメントとして利用
- **llms.txt への期待**: `llms-full.txt` のドキュメント本文が構造化されていること。ライセンス的に機械処理・再配布が可能なコンテンツであること
- **鮮度モデル**: F2（再現性のためにデータセット構築時の版を固定したい）/ F1（定期更新で継続的に鮮度の高いデータを取り込む場合）
- **注記**: F2 寄りのユースケースだが、定期的な再構築フローを持つ場合は F1 にもなる。`[merge-candidate: S-B5, S-B13]` — RAG 投入（S-B5）とデータセット構築（S-B13）はパイプライン前半（llms-full.txt 取得・chunk 分割）が共通だが目的が大きく異なる

| `[merge-candidate: S-B3, S-B4]` | submodule 更新 vs URL ウォッチ型更新 | 更新検知・通知という目的は共通。実装詳細（git vs HTTP）が異なるだけなら統合可 |

| `[merge-candidate: S-B5, S-B13]` | RAG 投入 vs ファインチューニングデータセット構築 | 前処理は共通だが目的が全く異なる（運用推論 vs 学習データ構築）。F2 要求が S-B13 に強い点も差異 |

## 注記・気付き

1. **E1 × P のシナリオが少ない**: E1（本リポジトリ内）の P 起点は「CI による自己検証（S-B11）」と「CLAUDE.md からの自動 fetch（S-B2）」程度。E1 × P は本質的に少なくて当然（本リポジトリはコンテンツ生成側であり、P 起点で自己参照する文脈は限られる）

2. **E3 × P がボリュームゾーン**: RAG 投入（S-B5）、API 直叩き（S-B6）、社内同期（S-B9）、データセット構築（S-B13）など、外部環境での自動処理パイプラインが P × E3 の中核

3. **F2 要求が顕在化しにくい**: F2（版固定）を明示的に求めるシナリオはプロジェクトテンプレート（S-B10）・データセット構築（S-B13）程度。CI や RAG は F1 寄りだが、実際には「フレームワーク 5.x 系だけ欲しい」ニーズが隠れている可能性

4. **コレクション性（glossary 1.4）が P 起点でも効く**: S-B12 はコレクション性の P 起点での活用典型。横断モニタリング・横断ベンチマーキングは human が意識しない形で自動化されうる

5. **llms.txt サイズへの関心が高い**: P 起点はトークンコスト・ネットワーク転送コストを意識するため、`llms.txt`（索引のみ）と `llms-full.txt`（フルテキスト）の使い分け設計が重要

6. **URL 永続性への要求**: P 起点のほぼ全シナリオで「URL が変わらないこと」「ファイルパスが安定していること」が暗黙の前提として共通する。人間が都度 URL を確認できる H 起点と異なる特性

## glossary-proposal

### 自動投入パイプライン (ingest pipeline)
- **提案理由**: S-B5 / S-B6 / S-B9 / S-B13 を総称する語として「自動投入パイプライン」または「LLM インジェストパイプライン」が繰り返し登場する。現在 glossary の「取り込み (ingest)」（5.1）は動詞定義のみで、パイプライン全体を指す名詞定義がない
- **暫定定義**: P 起点で `llms.txt` / `llms-full.txt` を HTTP 取得し、ベクトル DB・system プロンプト・社内知識基盤・学習データセット等の何らかのターゲットシステムに変換・投入する自動処理の連鎖。RAG パイプラインはそのサブセット
- **適用範囲**: P 起点 × E3 のシナリオ群（S-B5, S-B6, S-B9, S-B13 相当）

### URL 永続性要求 (URL stability requirement)
- **提案理由**: P 起点のほぼ全シナリオで暗黙の前提として登場するが、現在 glossary に定義がない。H 起点との本質的差異を説明する概念として独立定義する価値がある
- **暫定定義**: P 起点（CI / バッチ / 自動スクリプト）のユーザーが `llms.txt` に対して持つ、「ファイルの URL・パスが変更されると自動処理が壊れる」という特性に由来する安定性要求。H 起点では人が都度確認できるため低コストで解決できるが、P 起点では URL 変更がサイレントなシステム障害に直結する
- **適用範囲**: 軸 1 P × 全 E における共通要求として横断的に適用
