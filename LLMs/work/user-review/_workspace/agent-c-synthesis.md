# Agent C (round 2): ユーザーシナリオ統合（P0.1 Synthesis）

## 全体所感

Sonnet A（H × E2/E3）の 15 件は SDK 調査・コレクション横断・F2 保守・非エンジニア利用まで幅広く H 起点を捉え、Sonnet B（P × E1〜E3）の 13 件は CI / RAG / 社内同期 / プロジェクトテンプレートまで自動化を網羅した。両者で「フレームワーク版固定（F2）」「コレクション横断」「メタインデックス」「CLAUDE.md 経由の間接参照」など本リポジトリ独自価値に触れるシナリオが複数挙がっており、軸 3（F1/F2）を加えた分類の妥当性も実証された。一方で **E1 × H（同居非メンテナー）**、**発見経路**、**ライセンス境界** が両者ともに不足しており、補完が必要。CLAUDE.md 原則 4.1 の徹底適用も統合の論点として残った。

## 統合プロセス

### B の merge-candidate 評価（6 ペア）

| # | ペア | 判定 | 統合後の扱い | 理由 |
|---|---|---|---|---|
| 1 | S-B1 × S-B3（CI 直接取得 vs submodule） | **統合する（軽量）** | 「自動更新パイプライン」シナリオ内のサブパターンとして扱う | 利用者目線では「自動で最新 llms.txt を持ってくる」共通ニーズ。実装差（HTTP vs git）はシナリオの「典型ユースケース」内に併記すれば情報損失なし |
| 2 | S-B3 × S-B4（submodule vs URL ウォッチ） | **統合する** | 同上のサブパターン | 「更新検知と取り込み」が目的。Renovate / submodule update の差は llms.txt への要求（URL 永続性・パス安定性）に関する**同じ要求**を生む |
| 3 | S-B1 × S-B7（汎用 CI vs コードレビュー特化 CI） | **統合する**（バリアントとして併記） | 「F2（フレームワーク版固定）への期待」を統合先シナリオの注記に明示 | S-B7 固有の「対象コードが使う SDK のバージョン特定 llms.txt」要求は F2 軸として残し、シナリオ自体は CI 自動化と統合 |
| 4 | S-B5 × S-B6（RAG 投入 vs system プロンプト直接組み込み） | **統合しない** | 別シナリオ（Scenario 4 系と Scenario 5 系に分割）| ターゲット（永続的ベクトル DB vs 都度の system プロンプト）と llms.txt への形式要求（chunk 分割しやすさ vs サイズ最小化）が異なり、本質的な利用者期待が分岐する |
| 5 | S-B5 × S-B9（汎用 RAG vs 社内知識基盤同期） | **統合する** | バリアントとして併記 | 宛先システム（Vector DB / Confluence / Notion）の違いはあるが、`llms-full.txt` を取得して chunk 化し別システムに同期する処理構造は同一。ライセンス要求は注記で残す |
| 6 | S-B5 × S-B13（RAG 投入 vs FT データセット構築） | **統合しない** | 別シナリオ | 鮮度モデルが本質的に逆向き（運用 RAG は F1 寄り、データセット構築は F2 寄り）。再現性要求の有無も決定的に異なり、CLAUDE.md 読まれる/読まれない判定も別 |

### A/B 横断の統合

- **S-A11 × S-B1 / S-B7**: A の「CI テスト失敗時に人が Claude Code 起動 → Claude が自律参照」は **H 起点だが裏で P 的動作**を持つ境界ケース。B の S-B1（CI コンテキスト自動注入）と異なり、起点は人で参照は自律的。これは中間カテゴリ **H/P 境界（人が起点・Claude が自律参照）** として独立シナリオに残す価値あり → Scenario 2 に集約。
- **S-A1 / S-A2 / S-A8 / S-A11**: いずれも「E2 で Claude Code が llms.txt を索引利用する」共通パターン → Scenario 1 に統合。SDK 別の差異は典型ユースケース内で例示。
- **S-A3 / S-A5 / S-A10 / S-A15**: いずれも「E3 で人が llms.txt / llms-full.txt を Claude に貼って質問・執筆する」 → Scenario 3 に統合。執筆補助（S-A15）と PM スコーピング（S-A10）はバリアント。
- **S-A6（コレクション横断比較） × S-B12（多リポ監視ダッシュボード）**: コレクション性活用は共通だが、起点（H 一回限り vs P 定期）と目的（選定判断 vs 監視通知）が異なる → コレクション性活用シナリオを独立化（Scenario 6）し、H/P 両起点を併記。
- **S-A7（CLAUDE.md 経由間接参照） × S-B2（E1 × P で CLAUDE.md からの自動 fetch）**: ともに「CLAUDE.md に llms.txt の URL を書いて Claude が自律 fetch」 → 統合し、E1（同居非メンテナー）と E2（外部リポメンテナー）のバリアントとして併記。
- **S-A4 / S-A12 / S-B10 / S-B13**: F2 関連を集約 → Scenario 5（版固定）に統合。
- **S-A14 / S-B5 / S-B6 / S-B9**: P 起点 LLM パイプラインに統合 → Scenario 4（自動投入パイプライン）。S-A14（H が初期設定、運用は P）はここに含める。
- **S-A13（非エンジニア PM の要旨把握）**: 単発の希少シナリオだが、評価軸（記述スタイルの可読性）が技術ユーザーと異なる。独立シナリオ化はせず、Scenario 3 内の注記として残す。
- **S-A9（cc-extensions メタインデックス活用）**: メタインデックス（glossary 1.3）の二段階ナビゲーションが本リポジトリ固有価値であり、独立扱い → Scenario 1 のメタインデックス利用バリアントとして併記。
- **S-B11（E1 × P 自己検証 CI）**: メンテナー文脈に近く、ユーザーレビューの対象外（glossary 3.1）。ただし「同居非メンテナーが自分の CI から cc-relative-info の品質を検証する」読み替えは利用者シナリオに該当 → Scenario 4 内の注記として残す。

### 鮮度モデル軸の評価

- **F1 と F2 で利用者期待が大きく異なるのは「版固定保守」「移行ガイド執筆」「FT データセット構築」「プロジェクトテンプレートバンドル」**。これらは Scenario 5（版固定 / F2 中心）として独立。
- **F1+F2 両対応が同一シナリオ内で発生するパターン**: 移行ガイド（S-A12）と一部の CI（S-B7）は同時利用。これらは「F2 提供が前提だが F1 も併用」と注記。
- **F1 単独で十分なシナリオ**（Scenario 1, 2, 3, 4 の主流ケース）は F1 を default としつつ「将来 F2 拡張時の対応」を含意として残す。
- **F2 単独ニーズの代表**: レガシー保守エンジニア（S-A4）・プロジェクトテンプレート（S-B10）が最も純粋。これらは現状の本リポジトリでは充足できない可能性が高く、提供側課題として明示。

### 抜けの補完

1. **E1 × H の同居非メンテナー利用者（A スコープ外、glossary 3.3 で定義）**: A は H × E2/E3 のみだったため、本来必要なこのカテゴリが空白。**Scenario 7 として補完**。例: cc-relative-info を `git clone` または submodule で同階層に置き、自分の OSS プロジェクトの作業中に「ローカルパスから llms.txt を読み込む」運用。
2. **発見経路の抜け（glossary 6.2）**: A も B も「URL / パスを既に知っている」前提のシナリオが多い。発見経路自体は P0.1 のスコープ外だが、各シナリオに「発見経路の前提条件」を注記すべき。
3. **想定外ペルソナ**:
   - **教育者 / 講師**: Claude Code 講座や MCP ワークショップの教材として llms.txt を使う → Scenario 3 のバリアントに含める。
   - **アクセシビリティ・翻訳パイプライン**: llms-full.txt を機械翻訳して多言語版を生成（glossary 1.1 で言及あり）→ Scenario 4 のバリアント。
   - **MCP サーバー実装が llms.txt を Resource として配信**: MCP → MCP の連鎖（B が抜けと指摘）→ 注記として残す（独立シナリオ化はしない、希少すぎる）。
4. **CLAUDE.md 原則 4.1 の遵守確認**: A/B の全シナリオで「利用者としての Claude は CLAUDE.md を読まない」前提が共有されているが、唯一の例外候補は **S-A7 / S-B2（CLAUDE.md 経由間接参照）**。これは「**利用者の CLAUDE.md**（cc-relative-info ではなく利用者側の CLAUDE.md）に本リポジトリの llms.txt URL を書く」シナリオであり、本リポジトリの CLAUDE.md は読まれない。原則違反なし。

## 最終シナリオ（7 個）

> 注: 集約目標は 3〜5 個だったが、CLAUDE.md 原則の判定パターンと鮮度モデルが大きく分岐するため**7 個に分離した**。3〜5 への再集約は「作業指示者への確認事項」に提示する。

### Scenario 1: E2 で Claude Code が SDK/フレームワーク索引として llms.txt を利用

- **想定ユーザー像（ペルソナ）**: Anthropic SDK / MCP SDK / Spring / AnswerDotAI 系ライブラリを使う個人〜中規模チーム開発者。Claude Code を作業エディタとして使い、ライブラリ仕様を頻繁に確認する。
- **典型ユースケース**:
  - 自プロジェクトで Claude Code 利用中、`anthropic-sdk-python` の API シグネチャを確認したい
  - MCP サーバー実装中に `resources` / `tools` / `prompts` 仕様の差を確認したい
  - cc-extensions メタインデックスから既存 Skill / Rule の一覧を取得し導入判断（二段階ナビゲーション）
- **llms.txt への期待**:
  - 情報粒度: **索引としての `llms.txt`** が中心。URL リンクが機能し、必要に応じて上流ドキュメントへ遷移。`llms-full.txt` も補助的に取り込み。
  - 鮮度モデル: **F1**（SDK / 仕様は継続進化）
  - 形式: 機能別セクション分けが明確。コレクション横断時に同フォーマット。
  - その他: メタインデックス（`cc-extensions/llms.txt`）の二段階ナビゲーションが破綻なく機能すること
- **元シナリオ ID**: S-A1, S-A2, S-A8, S-A9
- **CLAUDE.md を読むか**:
  - 利用者としての Claude: **no（原則通り、実害大）** — 本リポジトリの CLAUDE.md はメンテナー向けであり、利用者 Claude が読むとコンテキストを浪費し、かつ「ブランチ運用ルール」「Skill 一覧」など利用者には不要な情報で誤誘導されるリスクがある
  - 人間利用者: **no（原則通り）** — 開発者は llms.txt の URL/パスを得れば足り、CLAUDE.md を読む必要なし

### Scenario 2: 人が起点で Claude Code が自律的に llms.txt を参照（H/P 境界）

- **想定ユーザー像（ペルソナ）**: Claude Code を運用設定込みで使う開発者。CI 失敗時の調査・自プロジェクトの CLAUDE.md に参照先を埋め込んだ運用者。
- **典型ユースケース**:
  - CI が失敗 → 開発者が Claude Code に「最新の MCP SDK 変更点を確認して」と指示 → Claude が自律的に本リポジトリの llms.txt を参照
  - 自プロジェクトの CLAUDE.md に `https://raw.githubusercontent.com/.../llms.txt` を「参照先」として記載 → Claude Code セッション開始時に自動 fetch
- **llms.txt への期待**:
  - 情報粒度: 索引（`llms.txt`）が中心。Claude が自律判断で必要箇所のみ深掘り。
  - 鮮度モデル: **F1**（変更追跡が主目的）
  - 形式: 安定 URL、リンクが切れていないこと、CLAUDE.md からポインタしやすい raw URL
  - その他: **URL 永続性要求**（B の glossary-proposal）が決定的に重要
- **元シナリオ ID**: S-A7, S-A11, S-B2
- **CLAUDE.md を読むか**:
  - 利用者としての Claude: **no（原則通り、実害大）** — Claude が自律参照する文脈だからこそ、本リポジトリの CLAUDE.md を間違って取り込ませない設計が重要
  - 人間利用者: **no（原則通り）** — 設定者は URL のみ参照すれば足る

### Scenario 3: E3 で人が llms-full.txt を Claude に貼って質問・要約・執筆補助

- **想定ユーザー像（ペルソナ）**: Web 版 Claude / API 直叩きのスクリプトを使うエンジニア、テックライター、PM、非エンジニアのプロダクト担当者、教育者。
- **典型ユースケース**:
  - Claude Code の使い方を聞く前に `llms-full.txt` を会話の最初に貼り付け
  - SDK の非同期 API 仕様を学習データの古さを補うため llms-full.txt で system プロンプト補強
  - PM が「Anthropic API でできること」のスコーピング、テックライターが記事執筆補助
  - 教育者がワークショップ教材として llms.txt を配布
- **llms.txt への期待**:
  - 情報粒度: **`llms-full.txt` の全文取り込み**が中心。索引（`llms.txt`）も併用。
  - 鮮度モデル: **F1**（最新 API 仕様・最新機能の取得が主目的）
  - 形式: クロール不要で 1 ファイル完結。raw URL で機械的に取得可能。バージョン / 更新日明示。**記述スタイルが過度に技術的でないこと**（非エンジニア配慮）
  - その他: ライセンス上、再配布・引用が可能であること（テックライター・教育者向け）
- **元シナリオ ID**: S-A3, S-A5, S-A10, S-A13, S-A15
- **CLAUDE.md を読むか**:
  - 利用者としての Claude: **no（原則通り）** — llms-full.txt のみ取り込めば足り、CLAUDE.md は不要。E3 では取り込めない設定の方が望ましい
  - 人間利用者: **読まれてもよい（読み手が人）** — テックライターが本リポジトリの構造を把握するために CLAUDE.md を読むことは原則の主たる適用対象外だが、推奨はしない

### Scenario 4: P 起点の自動投入パイプライン（CI / RAG / 社内同期 / エディタ拡張）

- **想定ユーザー像（ペルソナ）**: DevOps エンジニア、ML エンジニア、社内ナレッジ基盤運用者、エディタ拡張開発者。
- **典型ユースケース**:
  - CI ジョブ内で `llms-full.txt` を curl 取得 → 後続 LLM 呼び出しのシステムプロンプトに組み込み（コードレビュー・テスト生成・ドキュメント生成）
  - 日次 / 週次バッチで `llms-full.txt` を vector DB（Pinecone / Chroma / pgvector）に再投入
  - 社内 Confluence / Notion / Slack bot 知識基盤への定期同期
  - VSCode / Cursor 拡張がバックグラウンドで定期 fetch しキャッシュ
  - submodule 更新 / Renovate 類似ツールでの更新検知 PR 自動化
  - H が初期設定し以後 P 運用（ローカル RAG の初期投入）
- **llms.txt への期待**:
  - 情報粒度: **`llms.txt`（索引、サイズ最小）と `llms-full.txt`（全文）の明確な使い分け**。chunk 分割しやすい構造化。
  - 鮮度モデル: **F1（中核）+ F2（可能なら）** — 多くは F1 だが「特定 SDK バージョンに固定したい」「半年ごとに固定したい」需要も並存
  - 形式: **URL 永続性**（B の glossary-proposal）、ETag / Cache-Control 対応、ハッシュ比較可能、ファイルパス安定、ライセンス明示
  - その他: 自リポジトリの CI（同居非メンテナー視点）が本リポジトリの提供物の品質シグナルを検証できると好ましい
- **元シナリオ ID**: S-A14, S-B1, S-B3, S-B4, S-B5, S-B6, S-B7, S-B8, S-B9（+ S-B11 の同居非メンテナー読み替えバリアント）
- **CLAUDE.md を読むか**:
  - 利用者としての Claude: **no（原則通り、実害大）** — トークンコスト・処理時間が直接コストに跳ね返る P 起点では、CLAUDE.md 取り込みは絶対に避けたい。誤って組み込まれると CI コストや RAG ノイズの原因になる
  - 人間利用者: **no（原則通り）** — DevOps / ML エンジニアが初期設定時に CLAUDE.md を読む必要はない（README で十分）

### Scenario 5: 版固定（F2）ニーズ — 保守 / 移行 / プロジェクトテンプレート / FT データセット

- **想定ユーザー像（ペルソナ）**: レガシー保守エンジニア、フレームワーク移行担当シニア、プロジェクトテンプレート整備者、ML 研究者（FT データセット構築）。
- **典型ユースケース**:
  - Spring Framework 5.3.x の凍結配布 llms.txt を Claude Code に読ませて保守作業
  - 5.x → 6.x 移行ガイド作成で F2 snapshot（5.x）と F1 最新（6.x）を**同時利用**
  - `cookiecutter` / `cargo generate` 等プロジェクトテンプレートに版固定 llms.txt をバンドル
  - FT データセット / 評価ベンチマークの参照ドキュメントとして再現性確保のため版固定
- **llms.txt への期待**:
  - 情報粒度: 索引・全文両方。**版が明示**されていること。
  - 鮮度モデル: **F2（中核）、移行ガイドでは F1 と併用**
  - 形式: tag / commit / バージョンタグで識別可能な URL 体系。snapshot のチェックサム公開（FT 用途で再現性確保）。ライセンス明示。
  - その他: 「最新版との混在がないこと」が決定的。**現状本リポジトリは F2 を提供していない可能性が高く、提供側課題**
- **元シナリオ ID**: S-A4, S-A12, S-B10, S-B13
- **CLAUDE.md を読むか**:
  - 利用者としての Claude: **no（原則通り、実害大）** — 版固定 snapshot を扱う文脈で本リポジトリ全体の CLAUDE.md（最新版）を取り込むのは、版混在の害が具体的に発生する
  - 人間利用者: **no（原則通り）** — 保守エンジニアは特定版の llms.txt を取得できればよい

### Scenario 6: コレクション横断利用（H ライブラリ選定 / P 定期監視）

- **想定ユーザー像（ペルソナ）**: ライブラリ選定を行うテックリード（H 起点）、ドキュメント監視ダッシュボード運用者（P 起点）。
- **典型ユースケース**:
  - 「FastAPI vs Flask vs Django」の非同期サポート差異比較を Claude に依頼（H）
  - 47 リポジトリ分の llms.txt を一括取得し、ドキュメント更新差分を Grafana / Slack に通知（P）
  - 横断ベンチマーキング（複数 SDK の API 命名規則の統計分析）
- **llms.txt への期待**:
  - 情報粒度: 索引（`llms.txt`）中心。横断比較で深掘りが必要な箇所のみ `llms-full.txt`。
  - 鮮度モデル: **F1**（最新断面の比較が主目的）
  - 形式: **コレクション性**（glossary 1.4）— 全リポジトリで統一フォーマット。共通の「機能」「API」「設定」セクション軸。
  - その他: 比較容易性のための共通スキーマ（できれば JSON 化されたメタデータ）
- **元シナリオ ID**: S-A6, S-B12
- **CLAUDE.md を読むか**:
  - 利用者としての Claude: **no（原則通り）** — 横断比較は llms.txt 群のみで完結
  - 人間利用者: **no（原則通り）** — テックリードは公開物（llms.txt 一覧）のみ参照

### Scenario 7: E1 × H 同居非メンテナー（A スコープ外の補完）
