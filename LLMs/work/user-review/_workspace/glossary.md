# Glossary (用語辞書)

> P0.1 以降のユーザーレビュー活動で使用する用語の定義集。
> Agent や作業指示者が**同じ語を別解釈で扱う**ことを防ぐための単一情報源。
> 「説明に "おそらく" や "多分" が必要になった名詞」は即座にここに登録する。

最終更新: 2026-05-26

---

## 0. 運用ルール

### 0.1 登録基準

以下のいずれかに該当する用語は本ファイルに登録する:
- 一般名詞だが本リポジトリ固有の意味を持つもの
- 複数の解釈が成立しうるもの
- 説明時に「おそらく」「多分」「だいたい」等のヘッジ表現が必要になったもの
- ブレスト・議論で複数の Agent が同じ語を別の意味で使う可能性があるもの

### 0.2 Agent への適用ルール

- Agent はタスク実行前に本ファイルを必読
- Agent が**未定義の一般名詞を新たに使う場合**は、本ファイルに定義候補を提案する（Agent の出力ファイル末尾に "glossary-proposal" セクションを設ける）
- Agent は「定義済み用語」を本ファイル定義から逸脱して使ってはならない

### 0.3 更新フロー

- 用語追加・修正は作業指示者の確認を経て確定（暫定追加は OK、確定マークは別途）
- 確定済み定義には項番に `[確定]` マークを付与
- 未確定（暫定）の項番には `[暫定]` マークを付与

## 1. 本リポジトリの根本概念

### 1.1 [確定] llms.txt / llms-full.txt

`llms.txt`: AnswerDotAI が提唱する仕様 (https://llmstxt.org/) に基づく、LLM 向けのリポジトリ・ドキュメント索引ファイル。1 ファイルで読める範囲のリンク集として機能する。

`llms-full.txt`: 同仕様の **フルテキスト版**。索引先のドキュメント本文を結合した状態で提供する。サイズが大きいかわりに RAG / 翻訳パイプライン等で URL クロールせずに利用できる。

本リポジトリは両方を生成・提供する前提。

### 1.2 [確定] 本リポジトリの提供物

- 47 リポジトリ分の個別 `llms.txt` / `llms-full.txt`（Anthropic / MCP / AnswerDotAI / Spring 等。`LLMs/work/gen-out/` 配下）
- cc-extensions メタインデックス（複数リポジトリの Claude Code Skills / Rules / Agents を集約した二段階索引）
- Claude Code 公式 / MCP 公式の `llms.txt` をミラー
- AnswerDotAI の公式関連リポジトリの submodule 集

### 1.3 [確定] メタインデックス

複数の個別 `llms.txt` を集約して**さらに上位の索引**を構成したもの。本リポジトリでは `cc-extensions/llms.txt` がこれに該当する。

利用パターンは「メタインデックス → 個別 llms.txt → 上流ドキュメント」の**二段階ナビゲーション**となる。

### 1.4 [確定] コレクション性

複数の個別 llms.txt が**同じフォーマット**で揃っていることによる横断利用の容易性。本リポジトリの独自価値の一つ。

## 2. ユーザー分類軸

### 2.1 [確定] 軸 1: 消費の起点

| 区分 | 内容 |
|---|---|
| **H** | 人がインタラクティブに Claude / ツールを使う |
| **P** | プログラマブル・非対話（CI / 自動 Agent / API 直叩き / hook / バッチ等）|

軸境界が曖昧なケース（人が起点だが裏で Agent が動く等）は両分類で扱う、または中間カテゴリを認める。

### 2.2 [確定] 軸 2: 消費の場

| 区分 | 内容 |
|---|---|
| **E1** | 本リポジトリ内（`cc-relative-info` を作業ディレクトリにしている環境） |
| **E2** | 他リポジトリ内（別プロジェクトで作業中の Claude Code 等） |
| **E3** | リポジトリ非依存（Web 版 Claude / API 直叩き / 独立環境のツール） |

### 2.3 [確定] 軸 3: 鮮度モデル

| 区分 | 内容 |
|---|---|
| **F1. 最新追随** | 上流リポジトリの最新断面を継続的に追跡。鮮度が常に最大化される |
| **F2. 版固定** | 上流の特定 tag / branch / commit に固定した snapshot。version-pinned。例: Spring Framework 5.3.x 系のドキュメントが欲しい保守エンジニア |

軸 1/2 のどの組合せでも F1/F2 のどちらも取り得る（直交関係）。

## 3. メンテナーと利用者

### 3.1 [確定] メンテナー (maintainer)

**本リポジトリ自身の整備**（コード追加・修正・スクリプト改修・運用ルール更新等）を行う者。

メンテナー作業は本ユーザーレビューの**対象外**。

### 3.2 [確定] 利用者 (user)

本リポジトリの公開物（`llms.txt` / `llms-full.txt` / メタインデックス）を**参照する者**。メンテナーではないが、本リポジトリと同居している作業者も含む（後述「同居非メンテナー」）。

利用者には**人間**と**LLM（利用者としての Claude）**の両方がある。

### 3.3 [確定] 同居非メンテナー

本リポジトリを `git clone` または submodule として**自身の作業環境に同居させている**が、本リポジトリの整備はしない利用者。例:
- 自分の OSS リポジトリと cc-relative-info を同階層に置いて Claude Code から参照
- 社内モノレポの一隅に取り込んで別サブプロジェクトで作業

このカテゴリは E1 × H で発生する重要な利用者タイプ。

## 4. CLAUDE.md 原則 [確定]

### 4.1 原則

> **本リポジトリにおける `CLAUDE.md` は、本リポジトリのメンテナンスを行う Claude Code 向けのドキュメントである。本リポジトリの利用者（llms.txt / llms-full.txt を参照したい者）が読む必要がある情報は書かれていないし、書かれるべきでもない。**
>
> **利用者としての Claude にとって、`CLAUDE.md` を読むことはコンテキストを無駄に消費するデメリットはあっても、メリットがない。したがって利用者としての Claude には原則読まれるべきでない。**

### 4.2 適用範囲

- 本原則は `CLAUDE.md` / `.claude/CLAUDE.md` / `LLMs/CLAUDE.md` / `Extensions/CLAUDE.md` 等、**本リポジトリ内のすべての CLAUDE.md 系メンテナー文書**に適用される
- 利用者向けの公開情報（`llms.txt` / `llms-full.txt` / `README.md`）には適用されない

### 4.3 各シナリオでの判定パターン

シナリオの「CLAUDE.md 読む？」判定は以下のラベルから選ぶ:

| ラベル | 意味 |
|---|---|
| **no（原則通り）** | 原則 4.1 に従い、利用者としての Claude には読まれない |
| **no（原則通り、実害大）** | 原則通り読まれるべきでないが、加えて誤って読まれた場合の害が具体的に発生する |
| **読まれてもよい（読み手が人）** | 読み手が人間なら原則の主たる適用対象外で、害がない範囲なら読まれてよい |
| **例外（特定条件）** | 上記以外の例外ケース。条件と理由を併記すること |

### 4.4 [派生残タスク]

本原則を本リポジトリの `CLAUDE.md` の**記載ルール・メンテナンスルール**として、適切な場所（候補: `.claude/CLAUDE.md` のメタ規則セクション）に明示する必要がある。`_progress.md` のバックログで管理。

## 5. 行為動詞の用法

### 5.1 [確定] 用語マッピング

| 用語 | 使用場面 | 例 |
|---|---|---|
| **消費 (consume)** | 有限リソース（コンテキスト・トークン）が対象 | 「コンテキストを消費」「トークンを消費」 |
| **参照 (reference)** | 情報源を読みに行く一般的な行為 | 「llms.txt を参照」 |
| **取り込み (ingest)** | 情報源を自分の処理対象に組み込む | 「llms.txt を system プロンプトに取り込む」 |
| **索引利用 (index lookup)** | ナビゲーション索引を辿る行為 | 「索引から目的のドキュメントへ遷移」 |

### 5.2 [確定] 補足

- 「消費」は**有限リソースの食い潰し**ニュアンスを残したい場合に限定して使用する
- 「索引消費」「ドキュメント消費」のような曖昧用法は避ける

## 6. その他の専門用語

### 6.1 [確定] プロジェクトテンプレート (project template / project scaffold)

新規プロジェクトを作成する際、利用者の選択に基づいて初期ファイル構成・依存関係定義・設定ファイル等を一括生成するツールまたはリポジトリ。代表例:
- `npx create-react-app`
- `cargo new`
- `cookiecutter`
- `nbdev_new`
- GitHub の Template Repository 機能

→ ここでは**狭義の意味**（プロジェクト初期化時のスキャフォールド）に限定して使用する。
→ より広範な「特定バージョン断面の llms.txt 配布」は**鮮度モデル F2（版固定）**に該当し、本用語とは別概念。

### 6.2 [確定] 発見経路

利用者が本リポジトリの存在を**初めて知る経路**。Web 検索 / GitHub Topic / 口コミ Slack / Claude の自律提案など。

シナリオで「URL を知った状態」を前提にする場合は、発見経路の話を別途切り出すこと。

### 6.3 [確定] 凍結配布 / version-pinned distribution

ある時点での `llms.txt` / `llms-full.txt` の snapshot を、特定バージョンのドキュメントとして提供する形態。鮮度モデル F2 に対応。

例: Spring Framework 5.3.x 系のドキュメントを参照したい保守エンジニア向けに、その版に対応した snapshot を提供する。

## 8. glossary-proposal セクション（Agent からの追加提案受付）

Agent が新規用語の追加を提案する場合、本ファイルではなく**自身の出力ファイル末尾**に以下のフォーマットで記載すること:

```markdown
## glossary-proposal

### <用語名>
- 提案理由: <なぜ定義が必要か>
- 暫定定義: <Agent の提案する定義>
- 適用範囲: <どの文脈で使うか>
```

作業指示者がレビューし、確定したものを本 glossary.md に追記する。
