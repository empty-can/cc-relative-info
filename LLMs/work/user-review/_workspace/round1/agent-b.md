# Agent B: P × E1〜E3 シナリオ列挙

## シナリオ

### S-B1: Claude Code SessionStart hook での自動コンテキスト注入
- **起点の具体**: hook 経由（`settings.json` の `SessionStart` hook）
- **環境**: E2（cc-relative-info 以外の作業リポジトリ）
- **いつ発動**: Claude Code セッション開始時に自動実行
- **何をする**: 対象リポジトリの `llms.txt` を取得して初期プロンプトに付加し、LLM がセッション開始直後から対象コードベースの構造・API を把握した状態にする
- **llms.txt に期待すること**: セッションの最初の 1 ファイルとして読み切れるサイズ（数百〜数千トークン）。API エンドポイント・主要ファイル・概要説明が揃っていること
- **注記**: `[merge-candidate: S-B2, S-B3]` — hook / CI / 手動スクリプトのどれで叩かれても「コンテキストに注入する」行為は同じ

---

### S-B2: CI パイプラインでのコード生成前コンテキスト注入
- **起点の具体**: CI（GitHub Actions / CircleCI 等）
- **環境**: E2（CI が対象リポジトリのワークフローとして動く）
- **いつ発動**: PR 作成・push トリガーで LLM によるコード補完・レビュー補助が走る前に
- **何をする**: LLM エージェントのシステムプロンプトに `llms.txt` を差し込み、対象ライブラリの API 仕様を事前に覚えさせてからコード生成・レビューを実行する
- **llms.txt に期待すること**: 関数シグネチャ・型定義・エンドポイント一覧が機械読み取りしやすい形式で収録されていること
- **注記**: `[merge-candidate: S-B1, S-B3]` — 注入先がシステムプロンプトである点で本質的に同じ

---

### S-B3: 自動化スクリプトでの llms.txt 取得・キャッシュ更新
- **起点の具体**: バッチ処理（cron / スケジューラ）
- **環境**: E3（リポジトリに依存しないスタンドアロンな定期実行）
- **いつ発動**: 毎日・毎週など定期実行
- **何をする**: cc-relative-info または各ライブラリの公式 `llms.txt` を取得してローカルキャッシュを更新。ローカルの LLM ツールやエディタプラグインが参照するキャッシュストアを新鮮に保つ
- **llms.txt に期待すること**: 安定した URL・フォーマット。差分検知しやすい構造（更新日や version ヘッダー等があると理想）
- **注記**: `[merge-candidate: S-B1, S-B2]` — 結局このキャッシュが S-B1/S-B2 のコンテキスト注入に使われる

---

### S-B4: LLM エージェントの自律的な llms.txt 参照（Agent の動的 tool use）
- **起点の具体**: 自動 Agent（tool use / function calling）
- **環境**: E3（エージェントフレームワーク自体はリポジトリ非依存）
- **いつ発動**: エージェントが「このライブラリの使い方を調べる」タスクを受け取ったとき、tool use で `llms.txt` の URL を叩く
- **何をする**: `fetch_url` ツールや `web_search` ツールで `llms.txt` を取得し、その内容を元に「どのドキュメントページを次に読むか」を決定するナビゲーションステップとして使う
- **llms.txt に期待すること**: 主要ドキュメントへの相対・絶対 URL が充実していること。エージェントがリンクを辿れる構造であること
- **注記**: 「人間の対話が起点→エージェントが自律的に動く」の境界ケース。P 起点としてカウントする（エージェントのツール実行は非対話的）

---

### S-B5: IDE / エディタプラグインによる補完コンテキスト注入
- **起点の具体**: 外部ツール（VS Code 拡張・Cursor・Copilot 等のプラグイン）
- **環境**: E2（ユーザーが作業している任意のリポジトリ）
- **いつ発動**: ファイルを開いた時・補完リクエスト時にプラグインが自動実行
- **何をする**: import しているライブラリの `llms.txt` を解決して補完エンジンのコンテキストウィンドウに追加する。補完精度を上げる
- **llms.txt に期待すること**: API シグネチャ・型・使用例が簡潔に収録されていること。`llms-full.txt` は重すぎるため `llms.txt` の軽量版が優先される
- **注記**: `[merge-candidate: S-B6]` — プラグインが行う処理と RAG パイプラインが行う処理は同質

---

### S-B6: RAG パイプラインへの llms.txt インデックス登録
- **起点の具体**: バッチ処理（インデックス構築スクリプト）
- **環境**: E3（RAG システムはリポジトリ非依存）
- **いつ発動**: ライブラリ情報の RAG インデックスを構築・更新する際に実行
- **何をする**: `llms.txt` を起点にリンクを収集し、各ドキュメントページをクロール→チャンク→ベクトルDBに格納。`llms.txt` は「クロール対象 URL の種まき」として使われる
- **llms.txt に期待すること**: ドキュメントページへの URL が網羅的に列挙されていること。`llms-full.txt` はチャンク素材としても直接使える
- **注記**: `[merge-candidate: S-B5]` — 最終的にコンテキスト注入に使われる点では S-B5 と同質。ただしスケールが大きく URL 網羅性の重要度が高い

---

### S-B7: LLM API 直叩きスクリプトでのシステムプロンプト構築
- **起点の具体**: API 直叩き（Python / Node.js スクリプト）
- **環境**: E3（スクリプトはリポジトリ非依存に動く）
- **いつ発動**: 開発者が LLM API を使ったツールや実験スクリプトを実行するとき
- **何をする**: `llms.txt` をファイル読み込みまたは URL fetch して、`system` パラメータに付加してから LLM API を呼び出す。「このライブラリを使ったコードを書いて」という質問の精度を上げる
- **llms.txt に期待すること**: トークン効率が良いこと。システムプロンプトに収まるサイズ（数千トークン以内）。`llms-full.txt` の選択的利用も考えられる
- **注記**: `[merge-candidate: S-B1, S-B2]` — 呼び出し方法の違いだけで「LLM にコンテキストとして渡す」本質は同じ

---

### S-B8: ドキュメント検証・リンク切れチェックの自動化
- **起点の具体**: CI / バッチ処理
- **環境**: E2 / E3（対象ライブラリのリポジトリまたはスタンドアロン）
- **いつ発動**: ライブラリのリリース時・定期実行
- **何をする**: `llms.txt` に列挙された URL を自動巡回してリンク切れ・コンテンツ変更を検出する。ドキュメント整合性の監視ツールとして使う
- **llms.txt に期待すること**: URL が網羅的で機械的に抽出しやすいこと。Markdown リンク形式が整っていること
- **注記**: llms.txt を「消費」ではなく「監視基盤」として使うケース。P 起点だが目的が情報取得ではなく品質監視

---

### S-B9: 多リポジトリ横断のコード生成エージェント
- **起点の具体**: 自動 Agent（マルチリポジトリ横断エージェント）
- **環境**: E1（cc-relative-info の cc-extensions メタインデックスを起点に）
- **いつ発動**: 「Claude Code の Skill/Rule/Agent を組み合わせた実装を生成して」という自動タスクで発動
- **何をする**: cc-extensions メタインデックス（cc-relative-info の `llms.txt`）を参照して、参照先の各 Skill/Rule リポジトリの `llms.txt` を段階的に取得。二段階索引を辿ってコード生成の材料を収集する
- **llms.txt に期待すること**: メタインデックスとして、配下の個別リポジトリへのリンクが整理されていること。二段階で辿れる構造であること
- **注記**: cc-relative-info 固有のシナリオ。メタインデックスとしての llms.txt の用途

---

### S-B10: プロジェクト初期化スクリプトでのテンプレート選択支援
- **起点の具体**: 自動化スクリプト（project scaffolding ツール）
- **環境**: E3（スタンドアロンなプロジェクト生成ツール）
- **いつ発動**: `create-xxx-app` 系のスキャフォールディングコマンド実行時
- **何をする**: 利用ライブラリの `llms.txt` を取得してプロジェクトテンプレートに埋め込む。生成されたプロジェクトの `.claude/` や `CLAUDE.md` に最初から索引が入った状態を作る
- **llms.txt に期待すること**: プロジェクトテンプレートに同梱できる程度のサイズ。コピー配置後も陳腐化が少ない内容
- **注記**: llms.txt を「成果物の一部」として配布するケース

### S-B11: LLM ベースのコードレビューボットの依存ライブラリ知識補完
- **起点の具体**: CI（PR レビューボット）
- **環境**: E2（任意のリポジトリの CI）
- **いつ発動**: PR が作成・更新されるたびに
- **何をする**: PR の `package.json` / `requirements.txt` / `go.mod` などを解析して依存ライブラリを特定し、該当する `llms.txt` を cc-relative-info から取得してレビューボットのコンテキストに注入する。「このライブラリのベストプラクティスに沿っているか」のレビューができるようにする
- **llms.txt に期待すること**: 主要な API・ベストプラクティス・アンチパターンが含まれていること。ライブラリ名から URL が予測しやすい命名規則であること
- **注記**: S-B2 と似ているが、「依存ライブラリを動的に解決して索引を引く」点が異なる。マルチライブラリ対応の動的な参照

### S-B12: セキュリティスキャンエージェントでの API 仕様照合
- **起点の具体**: 自動 Agent（セキュリティスキャンパイプライン）
- **環境**: E2 / E3
- **いつ発動**: セキュリティ監査・脆弱性スキャン実行時
- **何をする**: `llms.txt` から API エンドポイント・認証方式・データフローを把握し、コードの実装が API 仕様と乖離していないかを自動チェックする。既知の非推奨 API 使用を検出するなど
- **llms.txt に期待すること**: 廃止・非推奨 API の明示、認証・権限に関する記述が含まれていること
- **注記**: 情報取得ではなく「仕様との照合」用途。llms.txt の活用用途の広がりとして記録

### S-B13: ドキュメント自動翻訳・ローカライズパイプライン
- **起点の具体**: バッチ処理（翻訳ワークフロー）
- **環境**: E3（スタンドアロンな翻訳パイプライン）
- **いつ発動**: ライブラリのバージョンアップや定期翻訳更新時
- **何をする**: `llms.txt` の URL リストを起点にドキュメントページを取得し、LLM で翻訳する。翻訳対象ページの発見・優先順位付けに `llms.txt` を活用する
- **llms.txt に期待すること**: ドキュメントページへの網羅的なリンクと各ページの概要（翻訳優先度の判断材料）
- **注記**: `[merge-candidate: S-B6]` — URL リストとして使う点は RAG インデックス構築と同じ

### S-B14: OpenAPI / MCP スキーマ生成の補助コンテキスト
- **起点の具体**: API 直叩き（スキーマ生成スクリプト）
- **環境**: E3
- **いつ発動**: MCP サーバーや REST API のスキーマ定義ファイルを LLM で自動生成する際
- **何をする**: 対象ライブラリの `llms.txt` を参照してツール名・パラメータ・説明を把握した上で、LLM に `mcp_schema.json` や `openapi.yaml` を生成させる
- **llms.txt に期待すること**: ツール・関数シグネチャが明示されていること。MCP 関連リポジトリの llms.txt では tool 定義の記述が特に重要
- **注記**: cc-relative-info が MCP 関連リポジトリの llms.txt を収録している点に直結するシナリオ

## 統合候補サマリ

| グループ | 該当シナリオ | 統合の根拠 |
|---|---|---|
| **コンテキスト注入グループ** | S-B1, S-B2, S-B3, S-B7 | hook / CI / バッチ / API 直叩きの違いだけで「llms.txt を取得してシステムプロンプトに渡す」行為は同じ |
| **URL リスト活用グループ** | S-B6, S-B13 | クロール・翻訳いずれも「llms.txt に書かれた URL リストを起点に次のアクションを起こす」点で同質 |

## 注記・気付き

1. **P 起点の「自動性」の程度**: hook・CI・バッチ・エージェント tool use の区別は技術レイヤーの違いだが、利用者視点では「自動的に llms.txt が取り込まれる」という体験は同じ。S-B1〜S-B3・S-B7 の統合優先度が高い

2. **cc-relative-info 固有性の高いシナリオ**: S-B9（メタインデックスの二段階参照）は本リポジトリが cc-extensions 索引を持つ特性と直結しており、他の汎用シナリオとは切り分けて評価すべき

3. **llms.txt の「消費」vs「発見」**: S-B4・S-B9 は llms.txt を「コンテンツを読む」ためではなく「次に何を読むかを決める」ナビゲーションとして使う。これは他のシナリオと質的に異なる用途

4. **非コード生成用途の盲点**: S-B8（リンク切れ監視）・S-B12（セキュリティ照合）・S-B13（翻訳）は LLM コード生成支援以外の用途。列挙時に「コード生成支援」に引っ張られがちで、これらの用途は意識的に拾った

5. **E1 環境のシナリオが少ない**: cc-relative-info を作業ディレクトリにした P 起点シナリオとして S-B9 のみ。「メンテナー作業除外」の制約により E1 シナリオが自然に絞られる

6. **llms-full.txt の使い分け**: S-B6（RAG インデックス）・S-B7（API 直叩き選択的利用）では `llms-full.txt` の方が適切な場面がある。`llms.txt` vs `llms-full.txt` の選択基準がシナリオ依存

## 自己評価

- **列挙数**: 14 件
- **統合候補が多そうか / 少なそうか**: 多い。コンテキスト注入グループ（S-B1/B2/B3/B7）が 4 件で最大のクラスタ。全体の 1/3 程度が統合候補
- **網羅性に対する自信**: 中。P 起点の主要なシーン（hook / CI / バッチ / エージェント / IDE プラグイン / RAG / API 直叩き）は押さえた。一方でエンタープライズ用途（ガバナンス・コンプライアンス監査での API 仕様照合）や、LLM ランタイム以外のツール（LSP サーバー、言語解析ツール）での利用は薄い可能性がある
- **特に注目すべきシナリオ ID**: S-B4（エージェントの動的 tool use）、S-B9（メタインデックス二段階参照）
- **抜けがありそうな領域**: エンタープライズ IT 管理ツール（依存ライブラリのライセンス・脆弱性管理）での llms.txt 活用、Jupyter Notebook / データサイエンス環境での自動コンテキスト注入、LLM プロキシ・ゲートウェイレイヤーでの自動付加
