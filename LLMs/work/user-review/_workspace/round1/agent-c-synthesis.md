# Agent C: ユーザーシナリオ統合（P0.1 Synthesis）

## 全体所感

A（H × E2/E3、14 件）は人がインタラクティブに索引を消費する文脈を「個人開発者の単発質問」から「組織オンボーディング」「意思決定者の俯瞰」まで広く拾えている。B（P × E1〜E3、14 件）は hook / CI / バッチ / Agent tool use / IDE プラグイン / RAG といった自動経路を網羅し、merge-candidate flag を 8 件に明示して統合余地を提示した。A は鮮度・E2/E3 境界・コレクション性に、B はコンテキスト注入の同質性とメタインデックス二段階参照（S-B9）に強みがある。一方で **E1 × H の「同居する非メンテナー利用者」と「llms.txt の発見経路」** に明確な空白が見える。統合は概念軸（消費形態）でまとめると 3〜5 個に綺麗に収束する。

## 統合プロセス

### B の merge-candidate 評価

| グループ | flag が立つシナリオ | 判断 | 残す代表 / 取り込む要素 | 区別すべき本質的違い（あれば） |
|---|---|---|---|---|
| コンテキスト注入グループ | S-B1（hook） / S-B2（CI） / S-B3（cron キャッシュ） / S-B7（API 直叩き system プロンプト） | **統合する** | 「自動経路で LLM の system プロンプトに `llms.txt` を注入する」という抽象シナリオに統合。発火元（hook / CI / cron / スクリプト）は実装バリアントとして注記 | 鮮度要件は CI（実行毎に最新） vs cron キャッシュ（数日遅れ許容）で差があるが、利用者から見た期待は同じ「自動で新鮮な索引が降ってくる」 |
| URL リスト活用グループ | S-B6（RAG インデックス構築） / S-B13（翻訳パイプライン） | **統合する** | 「`llms.txt` を URL シードとして利用し、リンク先を網羅クロールする」用途に統合 | クロール後の処理（ベクトル化 vs 翻訳）は llms.txt への要求性質を変えない |
| IDE / RAG グループ | S-B5（IDE 補完プラグイン） / S-B6（RAG） | **統合しない** | S-B5 は軽量 `llms.txt` を即時 inline、S-B6 は `llms-full.txt` まで使って index 構築 | サイズ要求と鮮度要求が逆。S-B5 は「軽さ最優先・最新性は妥協」、S-B6 は「網羅性最優先・サイズ無制限」 |

その他、明示 flag のない隣接ケースもあわせて整理:

- **S-B4（Agent tool use）と S-B9（メタインデックス二段階）**: 統合**しない**。S-B4 はリポジトリ非依存・任意ライブラリの llms.txt をエージェントが自律 fetch するパターン。S-B9 は cc-relative-info の cc-extensions メタインデックスを起点に二段階で辿る本リポジトリ固有パターン。後者は「コレクション性」が核なので独立シナリオ化したい。
- **S-B8（リンク切れ監視） / S-B12（セキュリティ照合）**: いずれも統合候補が立っていないが、**「消費ではなく検証」用途**としては同質。ただし量が少なく代表性も低いため、最終 5 シナリオには含めず「想定外の用途」として注記に回す。
- **S-B10（プロジェクトスキャフォールド時に同梱）**: コンテキスト注入グループに近いが、「同梱時点で凍結された llms.txt をプロジェクト成果物として配る」点で鮮度モデルが正反対。最終シナリオの中ではコンテキスト注入グループの**注記（陳腐化リスク）**として扱う。

### 抜けの補完

A/B 両方の出力を俯瞰した上で、以下の不足を補完する。

1. **E1 × H の利用者シナリオ（最重要）**: A はメンテナーを除外したことで E1 × H をほぼスキップしている。B も E1 は S-B9（Agent）一件のみ。しかし現実には「`cc-relative-info` を `git clone` または submodule で同居させ、別フォルダで Claude Code を立ち上げて作業する非メンテナー」が存在する。**Scenario 4 として独立**させる。
2. **発見経路の抜け**: A の自己評価でも指摘あり。Web 検索 / GitHub Topic / 口コミ Slack / Claude が自律的に提案、のいずれかで「初めて URL を知る」フェーズが必要。これは Scenario 3（外部探索者）に組み込む。
3. **鮮度要求の分離**: コンテキスト注入グループに S-B10（同梱配布）を混ぜると鮮度モデルが破綻するため、**Scenario 1 の中で「ライブラリの新リリース直後は索引が遅れ得る」**ことを明示注記し、S-B10 のような凍結配布は対象外と切り分ける。
4. **「消費ではなく検証」用途**: S-B8 / S-B12 は最終 5 シナリオの枠を取るほど代表性がないため、**「想定外の用途」セクション**で言及して将来再評価する。
5. **想定外ペルソナ**: A の S-A13（採用可否を判断する EM）と S-B14（MCP スキーマ自動生成）は、いずれも「llms.txt の構造そのものを参考にする側」。実装者ではなく**設計者・規格適用者**という独立ペルソナとして Scenario 3 に位置づけ直す。

## 最終シナリオ（5 個）

### Scenario 1: 開発作業中の H 主導／P 補助コンテキスト消費

- **想定ユーザー像（ペルソナ）**: 任意の OSS や SDK を実装に使う**個人〜小規模チーム開発者**。Claude Code / Cursor / IDE プラグインを起動した状態で、`anthropic` / `mcp` / `spring-boot` 等の API を呼び出すコードを書いている。Claude Code の設定（CLAUDE.md / hook / Skill / MCP server）経由で本リポジトリの `llms.txt` が**自動的に**コンテキストに入っている、あるいは IDE プラグインが import 解析から該当索引を引いてくる。利用者は llms.txt の存在を意識していないことも多い。
- **典型ユースケース**:
  - 「`Server` クラスの tool 登録の正しいシグネチャは?」（S-A1）
  - 「Spring Boot 4 に上げると SecurityConfig はどう変わる?」（S-A2）
  - 「今日リリースされた anthropic SDK の変更点は?」（S-A8）
  - 「MCP Transport と Anthropic stream_manager の連携方法」（S-A12）
- **llms.txt への期待**:
  - 情報粒度: 関数シグネチャ・型・主要クラスと一行要約、公式 doc への直リンク。トークン効率優先で `llms.txt`（軽量版）が主役、`llms-full.txt` は必要時のみ
  - 鮮度: **数日〜1 週間以内に上流追随**してほしい。新リリース直後は遅れがあり得る点を利用者が許容できる程度に明示
  - 形式: 機械可読な統一フォーマット。リンク URL が live であること
  - その他: 複数ライブラリの索引が**同じフォーマットで揃っている**こと（横断質問が可能）
- **元シナリオ ID**: S-A1, S-A2, S-A8, S-A12, S-B1, S-B2, S-B3, S-B5, S-B7, S-B11（+ 注記として S-B10）
- **本リポジトリ CLAUDE.md を読むか**: **no**。利用者は本リポジトリの運用ルールを知らずに索引のみを受動的に消費する。`CLAUDE.md` は実装ガイドであり利用者文脈には不要。

### Scenario 2: API / Agent からのプログラマブル索引消費

- **想定ユーザー像（ペルソナ）**: LLM API を直接叩く**スクリプト書き・エージェントフレームワーク開発者・RAG / 翻訳パイプライン構築者**。コードは人が書くが、llms.txt の消費自体は完全に非対話で、エージェントが tool use で fetch するか、バッチがインデックス化する。
- **典型ユースケース**:
  - 複数 SDK の Tool 定義方法を Claude API で一気に比較要約（S-A5）
  - 自作コーディングエージェントの system プロンプトに `llms.txt` を貼って trial（S-A10）
  - Agent が「このライブラリの使い方」を tool use で動的取得（S-B4）
  - `llms.txt` を URL シードに RAG / 翻訳パイプラインがクロール（S-B6, S-B13）
  - MCP スキーマや OpenAPI を LLM に生成させる際の補助コンテキスト（S-B14）
- **llms.txt への期待**:
  - 情報粒度: **URL 網羅性が最優先**。`llms-full.txt` がチャンク素材として直接使えること
  - 鮮度: cron キャッシュで日次更新できる程度の安定性。版識別子（更新日 / commit hash）があると差分検知が楽
  - 形式: 機械抽出が容易な Markdown 構造。リンク行が一貫した記法
  - その他: **複数リポジトリ分が一括 fetch しやすい**（`targets.txt` のような目録 / 安定 URL）
- **元シナリオ ID**: S-A5, S-A10, S-B4, S-B6, S-B7（再掲）, S-B13, S-B14
- **本リポジトリ CLAUDE.md を読むか**: **no**。プログラム消費者にとっては URL とフォーマットだけが契約面。

### Scenario 3: 外部からの非対話的探索者・規格採用判断者

- **想定ユーザー像（ペルソナ）**: 本リポジトリのリポジトリ存在を**初めて知った段階**の人。Web 検索や口コミでたどり着き、ブラウザの Claude.ai に URL を貼って質問する。あるいは EM / プラットフォーム責任者として「llms.txt は自社で採用すべきか」を評価している。手書きで llms.txt を書こうとしている小規模 OSS 作者も含む。
- **典型ユースケース**:
  - Web 版 Claude に cc-extensions の URL を貼って「Skill の書き方が分かる doc を教えて」（S-A4）
  - 「llms.txt の正しいフォーマットを教えて」と仕様サンプル探索（S-A7）
  - 採用事例と典型フォーマットの調査による意思決定（S-A13）
  - 社内 LLM 活用ガイドのリンク集として本リポジトリを引用（S-A9）
- **llms.txt への期待**:
  - 情報粒度: **コレクション全体を俯瞰できる**入口（リポジトリ一覧・対象技術・索引 URL のリスト）
  - 鮮度: 採用判断には絶対鮮度より「継続的に更新されている事実」が重要
  - 形式: GitHub Pages / README の読みやすさが重要。`llms.txt` 単体だけでなく**それを束ねる README / インデックスページ**が決定打になる
  - その他: 採用事例の多様性（複数 OSS の生きた llms.txt が同居している事実）が価値
- **元シナリオ ID**: S-A4, S-A7, S-A9, S-A13
- **本リポジトリ CLAUDE.md を読むか**: **状況による**。EM / 規格採用判断者は「このリポジトリはどう運用されているか」を確認するため CLAUDE.md を覗く可能性がある。一方、単発探索者は読まない。基本は no と想定し、読まれる場合の備えは持っておく。

### Scenario 4: 同居しつつ別フォルダで作業する非メンテナー利用者（E1 × H）

- **想定ユーザー像（ペルソナ）**: 本リポジトリを **`git clone` または submodule として同居**させ、ただし作業対象は別フォルダの**非メンテナー**。例えば: 自分の OSS リポジトリと cc-relative-info を同階層に置き、Claude Code から相対パスで索引を読ませる開発者。または、社内モノレポの一隅に cc-relative-info を取り込んで、別のサブプロジェクトで作業しているエンジニア。
- **典型ユースケース**:
  - 「自分の OSS に llms.txt を導入したい」とき、本リポジトリ内の cc-extensions 索引と `generate-llms-txt` Skill のドキュメントを横断参照（S-A6）
  - Claude Code の Rules / Agents を試す前に cc-extensions 索引から実例を眺める（S-A11）
  - 新入エンジニアが clone 直後にコレクション全体を Claude に俯瞰させる（S-A14）
- **llms.txt への期待**:
  - 情報粒度: **二段階構造**（メタインデックス → 個別リポジトリ索引）が機能していること
  - 鮮度: ローカルに存在するので git pull タイミング=利用者制御。鮮度は副次的
  - 形式: 相対パスでもアクセスできるよう、URL だけでなく**リポジトリ内パスから辿れる構造**
  - その他: 本リポジトリ自身の `CLAUDE.md` を**読まなくても**索引が自己完結している必要がある（利用者はメンテナー文書を読まない前提）
- **元シナリオ ID**: S-A6, S-A11, S-A14（部分）
- **本リポジトリ CLAUDE.md を読むか**: **no（が、誤って読まれるリスクが最も高い）**。clone した瞬間にルート `CLAUDE.md` がコンテキストに入りやすく、メンテナー文書なのに利用者視点を侵すノイズになる。利用者向けには README が独立して機能する必要がある。

### Scenario 5: cc-extensions メタインデックスの二段階ナビゲーション利用

- **想定ユーザー像（ペルソナ）**: **Claude Code 拡張（Skill / Rule / Agent / Plugin）を組み合わせて何かを作りたい**人またはエージェント。E2 にいる人間がブラウザで cc-extensions メタインデックスを読む場合と、E3 にいるエージェントがマルチリポジトリ横断で自動収集する場合の両方を含む。
- **典型ユースケース**:
  - 「Skill / Rule / Agent を組み合わせた実装を生成して」というタスクで、エージェントがメタインデックスを起点に各拡張リポジトリの索引を段階的に取得（S-B9）
  - 人が「他の人はどんな Rules / Agents を書いているか」をブラウズ（S-A11、Scenario 4 と部分的重複）
  - cc-extensions の典型実装例から自分用の Skill を試作するための素材集め
- **llms.txt への期待**:
  - 情報粒度: メタインデックス階層では**カテゴリ別の俯瞰**、個別索引では**実装に使えるコード片への直リンク**
  - 鮮度: cc-extensions リポジトリ群は変化が速いため**週次更新**が望ましい
  - 形式: **二段階で辿れる**ことが必須。メタ → 個別の遷移がリンクで完結すること
  - その他: 個別リポジトリの索引が**一定品質**で揃っていること（穴があると二段階ナビが破綻）
- **元シナリオ ID**: S-A11, S-B9（+ Scenario 4 と相互参照）
- **本リポジトリ CLAUDE.md を読むか**: **状況による**。エージェントが自動収集する場合は no。人がブラウズする場合、cc-extensions の意図を理解したくて `Extensions/` 側のドキュメントには触れたくなる可能性があるが、ルート `CLAUDE.md` は不要。

## C1 への含意（レビュアー Claude の情報制限方針）

最終 5 シナリオのうち **4 シナリオで CLAUDE.md は no、1 シナリオ（Scenario 3）が状況による、1 シナリオ（Scenario 5）が状況による**。**利用者の標準体験は「CLAUDE.md を読まずに索引だけを消費する」** であり、ユーザーレビュー実施時のレビュアー Claude もこの前提に合わせる必要がある。

### 推奨方針

1. **CLAUDE.md / `.claude/CLAUDE.md` / `LLMs/CLAUDE.md` 等のメンテナー文書を、レビュアー Claude のコンテキストから明示的に遮断する**。これらは「本リポジトリをどう整備するか」の文書であり、利用者目線の評価を歪める。
2. **レビュアーには `llms.txt` / `llms-full.txt` / 公開 README / cc-extensions メタインデックス のみを与える**。利用者が実際に触る面と一致させる。
3. **メンテナー文書が必要なシナリオ（Scenario 3 の EM、Scenario 5 のブラウズ人間）も、まず利用者面のみで判断させ、必要に応じて段階的に CLAUDE.md を開示するレビューフローにする**。

### sub-agent 起動方式（(a)/(b)/(c)）の推奨

選択肢の具体は本ドキュメントでは未確認だが、上記方針から **「メンテナー文書を見ない独立 sub-agent を起動する方式」が最適** と推定する。具体的には:

- **(a) 共通プロンプトでメインセッションが直接レビュー**: メインのコンテキストに既に CLAUDE.md 群が入っている可能性が高く、漏洩リスク大。**非推奨**。
- **(b) sub-agent を起動し、CLAUDE.md を読まないよう制約を渡す**: 明示的に読まないという指示は守られない可能性がある。**条件付き可**。
- **(c) sub-agent を起動し、レビュー対象として与えるファイル群を `llms.txt` 系と README に限定する**: ホワイトリスト方式で物理的に CLAUDE.md にアクセスさせない。**強く推奨**。

→ **(c) を採用すべき**。Scenario 3 / 5 のように一部 CLAUDE.md を覗き得るペルソナについては、別途「CLAUDE.md ありプロファイル」を 1 件追加して 2 ロール構成にする案も検討余地あり。

## 想定外のペルソナ・浮かび上がった発見

- **「llms.txt を消費しない人」の存在**: S-B8（リンク切れ監視）/ S-B12（セキュリティ照合）が示すように、llms.txt は**コンテンツ消費ではなく仕様照合・品質監視の基盤**になり得る。最終 5 シナリオには含めなかったが、本リポジトリの将来用途として注目。
- **「凍結配布」モデル**: S-B10（プロジェクトテンプレート同梱）は鮮度モデルが他と正反対。本リポジトリが「ある時点の snapshot を配布」する用途を持つ場合、独立シナリオが必要になる。
- **設計者・規格採用者ペルソナ**: S-A13 / S-A7 / S-B14 は実装利用者ではなく「llms.txt 自体を作る側 / 採用判断する側」。本リポジトリが「実例の博物館」として機能するという独自価値が浮上した。
- **CLAUDE.md の意図せぬ侵食リスク**: Scenario 4 で顕在化した通り、リポジトリを clone した瞬間にルート CLAUDE.md がコンテキストに入ってしまう。**利用者向け README とメンテナー向け CLAUDE.md の役割分離**が運用上の重要論点。
- **発見経路の網羅不足**: 本ブレストでは「URL を知った状態」を前提にしたシナリオが大半。実際の発見経路（Web 検索 / GitHub Topic / 口コミ / Claude の自律提案）の網羅は別 P で扱う価値あり。
