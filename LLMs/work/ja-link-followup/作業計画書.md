# 作業計画書: latest.md / latest-detail.md への ja セクションリンク追従強化

最終更新: 2026-06-21 / 起票: feature/LLMs セッション

## 1. 背景と目的

doc-summary パイプラインが生成する `latest.md`（ライト版）・`latest-detail.md`（詳細版）および
それらの archive に対し、各項目（ハイライト・軽微な更新の新機能/機能改善・新規ページ・大幅更新・新着）に
**日本語ページのセクション URL**（`https://code.claude.com/docs/ja/<page>#<id>`）を
リンクとして付与する。作成時点で ja セクションが存在しない場合は追従対象として記録し、
日次で出現を確認して出現後に追記する（追従処理）。

本計画は req4 watch（`watch.py`）の現状調査で判明したギャップ G0〜G7 を解消し、
**要件1（作成時リンク付与）・要件2（追従処理）** を達成することを目的とする。
要件3（en ページ側の同等対応）は、想定読者が日本人でありニーズが低いため本計画のスコープ外。

## 2. 対象リポジトリと活動

- **実装対象**: repo B `empty-can/LLMs`（ローカル `C:\cc-workspace\LLMs`、ブランチ `bot/doc-summary`）
  - 中核スクリプト: `.claude/skills/update-official-doc-summary/scripts/watch.py`
  - 共通基盤: `.claude/scripts/doc-summary-common.ps1`
  - 生成器: `update-official-doc-summary` Skill（LLM 生成プロンプト）
  - 生成物: `official-doc-update-summary/claude-code-docs/{latest.md, latest-detail.md, archives/, watch/registry.json}`
- **本計画書の置き場**: repo A `cc-relative-info` の `LLMs/work/ja-link-followup/`（計画・追跡用）

## 3. 要件（再掲）と優先度

1. latest.md / latest-detail.md とその archive の各項目に ja セクション URL を付与する。
   項目追加に伴いページ自体が新規作成され内容が該当項目を説明している場合はページ URL でよい。
   対象: ハイライト / 軽微な更新（新機能・機能改善）。
2. 作成時に該当ページ・セクションが無ければ追従項目として記録し、日次で出現確認・出現後に追記する。
3. en ページに対しても 1・2 を行う。→ **本計画スコープ外（優先度低）**。

進め方の方針: **最終成果物への実装しやすさを優先**。依存で順序が決まらないタスクは**規模の小さい方を先**に。
本処理は archive 全件に訴求するもので、当日完了などのタイトな期限はない。

## 5. 機械的不変トークン契約（全フェーズの前提・最重要）

watch パイプラインが依存する以下のトークンは**不変**とし、将来のテンプレート（Phase 7）の
カスタマイズ可能範囲からも除外する。これを破ると追従が壊れる。

- ライト版ブロックマーカー `<!-- light:<section>:start -->` / `<!-- light:<section>:end -->`
- Claude Code Docs リンクの URL 規約: `/docs/en/<slug>(#<anchor>)` と、`/docs/en/`↔`/docs/ja/` 対応、
  ja 見出しは en と同一 Mintlify id を再利用する前提
- ハイライト見出し `## N. <title>`
- ja 注入形（Markdown 維持）: `[日本語](<ja_url>) / [<元ラベル>](<en_url>)`
  - 短ラベルは元ラベル=`English`、長ラベルは元の記述ラベルを保持して ja を前置する

> HTML アンカー化（`target="_blank"`）は **github.com の Markdown サニタイズが `target` を除去する**ため
> 取り下げ。リンク表現は Markdown のまま維持する。

## 6. スコープ判断の記録

- **HTML 化（旧 Phase 0）取り下げ**: github.com で `target` が無効化されるため。Markdown 維持。
- **テンプレート（Phase 7）は #1〜#6 の後**: watch はリンク片・マーカー等の位置非依存トークンに依存し、
  レイアウトに依存しない。テンプレートは生成器側の関心事で watch と直交。§5 の不変契約を守る限り、
  後置で #1〜#6 を阻害しない。生成器改修を伴う Phase 5 と相乗り可。
- **要件3（en 側）スコープ外**: 想定読者が日本人。

### 順序の根拠
- 1→2 は依存で確定する背骨（要件1中核＝ハイライト含む全リンクへの ja 付与がここで成立）。
- 3a・3b・4・5 は背骨への依存が弱い衛星。方針どおり小さい順（3a < 3b < 4 < 5）。
- 3a/3b は check 単体で完結する独立改善。4 は注入形確定後（Phase 2 後）に置くと手戻りが無い。
- 6 は全実装後の一括実行。scan は元々 archive を走査するので同一ロジックが全件に訴求。
- 7 は生成器改修ゆえ Phase 5 と同時期が効率的。

## 8. 各フェーズ詳細（受け入れ条件付き）

### Phase 1 — 基盤パーサ
- `watch.py` に `iter_doc_links(text)` を追加。各リンクを `(form, label, en_url, ja_url, anchor, span)` に正規化。
  3形態を吸収: 短ラベル `[English](url)` / 長ラベル `[<title> (English)](url)` / 既存注入ペア `[日本語](ja) / [...](en)`。
- scan の `EN_LINK_RE` 依存箇所を本関数経由に置換。§5 の不変契約を docstring/コメントで明文化。
- 受け入れ: 既存 latest-detail.md のハイライト主リンク（長ラベル）が検出される。既存注入済み行は二重検出しない。

### Phase 2 — inject 全置換＋元ラベル保持
- `new_frag` を `[日本語](ja) / [<元ラベル>](en)` とし、元ラベルを保持。
- ambiguity guard 廃止 → 当該ファイル内の未注入の同一 en リンクを**全置換**。注入済み（直前に `[日本語](ja) /`）は skip。
- registry の `injected` 意味論を「ファイル内全 en 出現に ja 付与済み」へ再定義（コメント明記）。
- 受け入れ: `env-vars`（2出現）の両方に ja が付く。長ラベルのハイライト主リンクに ja が付く。

### Phase 3a — manual 昇格 CLI
- `check` 系に `promote --only <key>`（または `--key`）を追加し manual→ready へ昇格。
- 受け入れ: 滞留 manual 13件を個別に昇格 → inject 可能になる。

### Phase 3b — セクションスコープ probe
- check で ja body 全文ではなく `id="<anchor>"` 周辺（見出し〜次見出し）にスライスしてから term を判定。
- 受け入れ: 別セクションに同トークンがあっても当該セクション未反映なら pending を維持。

### Phase 4 — live キー世代問題
- scan で「現 live 行に `日本語` が無いのに registry が injected/done」を検出したら pending へ戻す逆チェック。
  （または live エントリを生成世代でキー rotate。実装容易な逆チェックを第一候補）
- 受け入れ: 過去 injected の en-URL が新 live に再出現したとき再び追従対象になる。

### Phase 5 — link-less 追従
- 生成器（Skill プロンプト）が、ページ未存在の項目に**予測 ja slug/anchor を機械可読マーカー**
  （例: `<!-- watch:pending ja_slug=... anchor=... -->`）で埋め込む。
- scan が当該マーカーを registry へ follow-up 登録。check で出現確認。inject がマーカー位置に ja リンクを挿入。
- changelog 由来の恒久 link-less は従来どおり除外（既存ガード流用）。
- 受け入れ: ページ未存在のハイライトが追従キューに入り、ページ公開後に自動でリンクが付く。

### Phase 6 — バックフィル実行＋検証
- live＋全 archive に対し scan→check→inject --apply を実行。レンダリング目視確認。
- 複数行コミットメッセージは一時ファイル＋ `git commit -F`。**push は人手境界（bot ブランチ限定）を維持**。
- 受け入れ: 全 archive で要件1の付与が完了。registry の整合が取れている。

### Phase 7 — テンプレート.md 新設
- `latest.md` / `latest-detail.md` それぞれのレイアウトをメンテナーがスクリプト修正なしに編集できる
  template を新設し、生成器が参照。**可変領域（章順・見出し文言・前書き）と固定領域（§5 不変トークン）を分離**。
- 受け入れ: テンプレート編集だけで体裁が変わり、watch パイプラインが壊れない。

## 9. 委任方針（モデル / effort / inline 判断）

- 原則: SubAgent 起動コストを上回る作業量のフェーズは、最適モデルで SubAgent を立て委任する。
  小規模タスク（Phase 3a）・git/push を伴うオーケストレーション（Phase 6）はメインセッション（Opus）で inline 実行。
- **effort は SubAgent 生成時に指定不可**（Agent ツールは `model` のみ受付）。メイン Opus 側の `/model` で
  事前切替する運用。各フェーズ着手前に推奨を提示する。

| フェーズ | 推奨モデル | 推奨 effort | 備考 |
|---|---|---|---|
| 1 | Sonnet | medium | 仕様明確な機械的パーサ |
| 2 | Sonnet | medium | 文字列置換ロジック |
| 3a | inline (Opus) | — | 小規模、委任コスト超過 |
| 3b | Sonnet | medium | アンカースライス |
| 4 | Sonnet | medium | registry 状態遷移、要注意。仕様を厳密に渡す |
| 5 | Opus | medium〜high | 生成器セマンティクス＋設計判断 |
| 6 | inline (Opus) | — | 実行・検証・git（push 境界） |
| 7 | Opus | medium | 可変/固定境界の設計 |

- **permission 事前列挙**: 各 SubAgent 起動の直前に `agent-permission-runtime.md` §1 の8種別
  （Write/Edit/Bash/PowerShell/MCP/WebFetch/Agent/Read-deny）を列挙する。特に repo B の
  watch.py（`...\skills\...\scripts\`）への Write/Edit 権限が working-dir スコープに含まれるかを着手前に確認（§12）。

## 10. コミット / push 境界

- コミットは各フェーズ完了時に単一コミット（複数行メッセージは `git commit -F <file>`）。
- **push は人手境界**。bot ブランチ `bot/doc-summary` 限定、push トークンは env 変数優先・DPAPI フォールバック。
- 破壊的 git（reset/rebase 等）は明示確認方針。
