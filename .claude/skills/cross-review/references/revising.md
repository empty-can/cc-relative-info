# 反映する側の進め方

共通の決まり（`.claude/skills/cross-review/references/rules.md`）を前提にする。依頼文で、どの作業か（回答／同件調査／反映／差分の点検の結果の直し／1.0 の反映）と、固有の値を受け取る。1 つの依頼で行うのは、依頼文が挙げた作業だけである。

## 1. 回答

対象: 依頼文が挙げる報告書と ID（無ければ、回答の欄が空の CRITICAL・IMPORTANT・SUGGESTION の全部）。

1. 指摘ごとに、指摘された節を対象の文書で自分で読み、典拠（公式の断面の行、実測の出力）を自分で確かめる
2. 回答は回答ファイル（`@@ <ID> 問題点` / `@@ <ID> 修正案` の行の後に本文）に書き、`python -I -X utf8 .claude/skills/cross-review/scripts/report_tool.py fill-answers <報告書> <回答ファイル>` で 1 回だけ流し込む（欄の外の行が消えていないことはスクリプトが確かめる。2 回目からの追記は Edit で欄ごとに行う）。SUGGESTION・POSITIVE には問題点の回答の欄が無いので、`@@ <ID> 修正案` で書く。項目はテンプレートの欄のとおり（同意の程度／根拠／同件調査の要否と型の名前／作業指示者の裁定の要否／判断材料の追加情報／採る案／裁定に回す点／採用推奨案の拡張提案／追加の修正案）
   - 反論は典拠で書く。防衛的に書かない（「意図どおり」だけで済ませない）
   - 設計の選択・扱う範囲の選択で、決めないと文書が膨らむものは「作業指示者の裁定: 要」にし、選択肢と代償を書く
3. セルフレビュー（巡の上限と終わり方は §3.3 と同じくチェックリストに従う。回答に固有の観点: 全件に立場を書いたか／防衛的な書き方になっていないか／判断材料の追加情報は足りるか）
4. 最後の返答: 件数（完全同意・部分同意・当たらない）、同件調査が要る型の一覧（型の名前と、元の指摘の ID）、裁定が要る事項の一覧

## 2. 同件調査（確かめとまとめ）

型が決まった後の拾い出しは、あなたの前に済んでいる。(a) 文字列・正規表現で言い切れる型は `scripts/grep_type.py` が、(b) 意味で判定する型は Haiku の担当 2 体が並列に拾い、`scripts/merge_findings.py` が突き合わせた（「両方／A だけ／B だけ」と「要確認」の印つき）。あなたは型ごとに 1 体で、拾い出しの結果を確かめてまとめる。対象の文書は書き換えない。

1. 依頼文の型の定義を、最初の 1 行で出力に写す
2. 確かめる項目（(b) は「A だけ」「B だけ」「要確認」の全部、(a) は全部）について、該当の文を自分で Read で読み、型に当たるかを決める。「両方」の項目は、抜き取りで数件を読んで確かめる（読んだ項目を書く）
3. 拾い出しに漏れがありそうなら（型の定義の言い換えで当たる箇所など）、自分で Grep して足し、足したことを書く
4. 当たる項目ごとに、在りか（ファイル・行・節と引用）、なぜ同じ型か、直す案（直した後の文）を書く。足場で確かめたものは足場と出力を書く
5. 件数を「直す必要がある／あいまい／当たらない」に分けて数える。読みやすさ・説明の精度だけの項目は「仕上げの回へ」に分けて数える。片方だけの項目のうち当たったものの数も書く
6. 型の定義があいまいで、2 体の食い違いや「要確認」が多かったときは、どこがあいまいだったかを書く（主担当が型を書き直す材料）
7. 出力は依頼文のパス。最後の返答は、依頼文の形

反映する範囲は主担当が決める。同件調査の担当は、範囲を決めない。

## 3. 反映

1 つの文書の反映は、1 体だけで行う。依頼文で直列の順番を渡されたときは、前の担当の反映の後の文書を読み直してから始める。

### 3.1 直す範囲の上限

- 直すのは、依頼文の「反映する範囲」に挙がった項目だけである（CRITICAL・IMPORTANT の直しと、主担当が絞った同件調査の項目）
- 読みやすさ・説明の精度の項目は直さない（仕上げの回で扱う）。見つけたら報告の「仕上げの回へ」に書く
- 新しい未決の選択、新しい節、見出しの変更、アンカーの変更を足さない。新しく【実測】と書くのは、依頼文が挙げた実測の出力か、自分が足場で流した出力があるときだけ。【実測】には場面の ID を添える
- 1 つの事項を 2 か所で述べるときは、片方を正にして、もう片方は節の番号で指す
- 手順（プログラムと運用手順）は、スクリプトと「場面 → 期待する結果」の表を正にする。文書の文は、その表を指す形に直す。扱う状態の範囲のスコープ外のことは、文書の「スコープ外」の節にだけ書く
- 未決の事項について、手順・例・表をどの側で書くかは、依頼文の決定の台帳に従う。台帳に無いものは直さずに「判断してほしいこと」に書く
- 案が誤っている・公式の断面と合わない・ほかの項目と食い違うと分かったら、採らずに、報告に理由を書く

### 3.2 文書の書き方

- 依頼文の「文書の決まり」（そのテーマの用語集・表記・方針）に従う
- 案の文をそのまま貼らない。今の文と前後を読み、つながる文にする。同じ段落に複数の項目が掛かるときは、1 回の直しにまとめる
- 表のセルに条件を詰め込まない。セルは結論にし、条件は表の下の注記へ出す
- 「推測」「未実行」「未確認」のものを断定で書かない
- 1 件直すごとに、直した事項の名前（語）で文書の全体を Grep し、直した文と食い違うほかの節が無いかを確かめる。確かめた語と見つけた箇所を記録する

### 3.3 反復セルフチェック（反映の最後に必ず行う）

- 巡の上限・終了の条件・共通の見ること・報告の書き方は、`.claude/rule-assets/md-self-check/checklist.md` に従う（数字の正はそこだけ）
- クロスレビューに固有の見ること（チェックリストに足す）: (a) 書いた対処で本当に通るか（足場で流せるものは流す） (b) 【実測】の根拠の場面が、文に書いた順・状態と同じか (c) 読み手に残る道があるか（止まった後に次の手が書いてあるか） (d) 直す範囲の上限を超えていないか

### 3.4 報告書への追記

反映を終えたら、報告書の各指摘の「同件調査の結果（版）」「反映した箇所（版）」「回答から変えた点」を Edit で追記する（版は今の報告書の版）。

### 3.5 出力

報告 `<依頼文のパス>`（例 `<作業フォルダ>\30_tmp\<担当名>\反映の報告.md`）:
(1) 項目ごとに直した箇所（節と、直す前・後の文） (2) スクリプトを変えたときは、その差分と、流した場面ごとの結果 (3) 照合の結果（依頼文が挙げる照合のスクリプト） (4) 案から変えた点と理由 (5) 直さなかったものと理由 (6) 食い違いを Grep で確かめた記録 (7) 反復セルフチェックの巡ごとの記録 (8) 仕上げの回へ回したもの (9) 判断してほしいこと

最後の返答は (1)〜(9) の要点を短く。末尾に共通の決まり §5 の 3 項目。

## 4. 差分の点検の結果の直し

依頼文が挙げる差分の点検の報告の指摘（IMPORTANT 相当と、主担当が選んだ SUGGESTION）だけを直す。直し方は §3 と同じ。直した分の差分の範囲（ファイルと節）を報告に書く（主担当がもう一度点検に回すため）。

## 5. 仕上げの回の反映（読みやすさ）

- 内容を変えない直しだけを行う（文の分割、表への置き換え、語の統一、順序の入れ替え、重複の削除）
- 事実、条件、数、推奨、未決の事項、手順の順序を変えない。変わってしまう直しは行わず、「判断してほしいこと」に書く
- 直した箇所ごとに「内容を変えていない理由」を 1 行書く（差分の点検の担当が確かめる）

## 6. 1.0 の反映

作業指示者の態度表明（採用／条件付き採用／差戻し／保留／却下）に従って直す。条件付き採用は条件のとおりに直す。差戻しは、求められた追加の情報・再検討を回答の欄に書く。保留・却下は直さない。作業指示者レビュー（`H-` の指摘）があるときは、その「期待する対応」も同じに扱う。直し方は §3 と同じ。

差分の点検が済んだ後に依頼されたら、全部の報告書の版を 1.0 にし、件数表の 1.0 の列（態度表明を踏まえた現役の件数）と変更履歴を埋める。
